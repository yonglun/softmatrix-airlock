# P1.3c 设计：密钥轮换与批量/紧急吊销

| 项目 | 内容 |
|---|---|
| 日期 | 2026-09-02 |
| 阶段 | P1.3c（补齐 P1.3 剩余范围） |
| 上游依赖 | P1.3a（签发与吊销）、P1.3b（申请与审批流） |
| 对应需求 | Roadmap §P1.3「虚拟 Key 生命周期：申请 → 审批 → 签发 → 吊销（轮换属 LiteLLM Enterprise，由 Airlock 自建实现）」；PRD FR-1.3「完整流程：申请 → 审批 → 签发 → **轮换** → 吊销」「支持批量吊销与紧急全局吊销」 |

## 1. 范围

### 做什么

- **密钥轮换**（手动、按需）：换发客户端凭据 `ak-`，旧凭据在一个可指定的共存窗口内继续可用，窗口一过自动失效。
- **批量吊销**：按组织子树一次吊销。
- **紧急全局吊销**：break glass，吊销全系统密钥。
- **上游封禁的兜底扫描**：让所有吊销路径的上游 `/key/block` 变成最终一致、可自愈。

### 明确的范围外

| 项 | 去向与理由 |
|---|---|
| 定时/自动轮换 | 未排期。机制（共存窗口 + 到期回收）本期建成；「多久轮一次」是策略模型（按组织？按密钥？默认值？谁能改？），天然属于 P1.4 控制台的配置面，没有界面时无法验证是否好用 |
| 上游 `sk-` 的轮换 | 不做，见 D2 |
| 按密钥 ID 列表批量吊销 | 未排期。子树 + 全局已覆盖「某部门泄了」与「全公司泄了」两个真实场景；ID 列表的价值要等控制台有多选界面时才显现 |
| 吊销通知责任人 | 不做，见 D6 |
| 成本中心 / IP 白名单 / 来源应用标识 / 用途备注 / 密级 | PRD FR-1.3 列出的 Key 扩展属性。成本中心已由 PRD §3.3 明确划归 P2（配额引擎）；其余几项不在 Roadmap P1.3 的条目里，属产品完态而非本阶段 |
| 钉钉 / 企业微信通道 | 沿用 P1.3b 的立场：拿不到真实租户实测之前不声称支持，`notifications.channel` 的 CHECK 在物理上挡着 |

## 2. 设计前的实测

沿用 P0 以来的纪律：先对真实 LiteLLM 跑探针，不靠文档推断。本轮四条探针中 P3 直接改变了设计的必要性论证。

| 探针 | 结论 | 对设计的影响 |
|---|---|---|
| P1 | `/key/block` 打不存在的 key → `404 Key not found.` | 扫描把 404 视为「已经不在了」，盖戳收工，不当失败重试（D5） |
| P2 | 对同一把 key 重复 `/key/block` → 200，幂等 | 扫描重试安全，不需要「先查 `/key/info` 再决定是否封」的额外往返 |
| **P3** | `/key/block` 传 `keys` 数组 → **422，只接受单数 `key`** | **上游没有批量封禁接口**。吊销一个 500 把密钥的子树 = 500 次串行调用 → 本地吊销与上游封禁必须拆开（D4），这不是性能优化而是唯一可行解 |
| P4 | 被封禁的 key 在 `/key/info` 里 `blocked: true` | 验收可从上游侧取证 |

另外沿用 P1.3a 探针 E 的既有结论：`/key/regenerate` 返回 500 并要求 Enterprise License，因此轮换必须自建。

## 3. 关键决策

### D1：轮换用「一行两哈希」，不是「两行」

行内加 `prev_key_hash` + `prev_key_expires_at`，轮换时把旧哈希挪到 `prev_`，新哈希写进 `key_hash`。

考虑过另外两种：

- **两行共享同一把上游密钥**：预算连续，但吊销会踩雷——今天 `Revoke` 会 `BlockKey(upstreamKey)`，退休旧行时会把共享的上游密钥一起封掉、连带打死新凭据。每条吊销路径都得加一层「这把上游密钥还被别的活行引用吗」的判断，而这恰恰是最不能出错、也最不该变复杂的代码。
- **两行各自持有上游密钥**：隔离最干净，连上游凭据也一起轮换了。但**预算会在窗口期裂成两个桶**——LiteLLM 的预算挂在上游密钥上，两把密钥就是两份额度，窗口期内有效配额近乎翻倍、spend 历史分叉。这直接破坏了 P1.3 这一整块的核心价值（「密钥与配额映射」）。

一行两哈希同时保住了三件事：一行 = 一个密钥身份 = 一把上游凭据 = 一个预算桶；吊销逻辑**一个字都不用改**；密钥 `ID` 跨轮换稳定，审计轨迹与 `requests.issued_key_id` 外键都不断裂。

### D2：只轮换 `ak-`，不轮换上游 `sk-`

D1 的直接结果，但值得单独写明，因为它是一个安全判断而不只是实现细节。

`sk-` 以 AES-256-GCM 加密存放，只在进程内解密后立刻用于转发，从不离开控制面；`ak-` 则散落在客户端的 `.env`、CI secrets 与几十份配置里。需要被「限定泄漏后可用时长」的是后者。

**代价要如实说**：不能对着合规清单声称「完整凭据轮换」。若将来有客户明确要求上游凭据也定期轮换，那是一件独立的事——它需要处理预算桶迁移，属于 P2 配额引擎的范畴。

### D3：轮换是纯本地操作，零上游调用

`Rotate` 只有一条 UPDATE。因为 `ak-` → `sk-` 的映射完全由 Airlock 持有，换掉客户端那一端根本不需要惊动 LiteLLM。

结果是**轮换不可能因为上游宕机而失败**。这是 P1.3a「本地记录优先」推到尽头的形态：签发时之所以要「先落库 pending 再调上游」，是因为上游必须知道这把新密钥；轮换时上游什么都不需要知道。

### D4：本地吊销与上游封禁分离，用扫描兜底

探针 P3 决定的：上游没有批量封禁，同步做必然超时。

两个端点都只做一次本地 `UPDATE` 就返回。此刻安全属性已经满足——Edge 每请求查库、不做缓存，下一个请求就拒。上游封禁交给周期扫描：捞 `status='revoked' AND upstream_blocked_at IS NULL`，逐把封禁、成功盖戳。

分工按集合是否有界：

| 路径 | 上游封禁方式 |
|---|---|
| 单把吊销（`KeyIssuer.Revoke`） | 内联试一次；成功盖戳，失败留空交给扫描 |
| 离职对账（`RevokeByUsers`，一个人名下那几把） | 同上 |
| 按子树批量 / 全局紧急 | 只做本地 UPDATE，全部交给扫描 |

常见路径依然毫秒级完成上游封禁，无界路径不会超时，而**所有**路径都获得了自愈。

这顺带补上一个既有缺口：今天 `BlockKey` 失败只记一行 WARN，**永不重试**——本地虽然拒了，但「凭据万一泄漏也用不了」那道纵深就此静默消失，且无人知晓。`upstream_blocked_at` 让这件事变得可观测、可收敛。

### D5：到期判断写在 SQL 里，不依赖任何 worker

Edge 的查询是：

```sql
WHERE key_hash = $1
   OR (prev_key_hash = $1 AND prev_key_expires_at > now())
```

窗口一过，旧凭据**在那一刻自己失效**，哪怕清理 worker 从此再没跑过。清理 worker（把过期的 `prev_*` 置空）因此纯属卫生：它失败只会留下难看的死数据，不会留下一把还能用的旧密钥。

这是 P1.3b「用扫描不用定时器」的下一步——那里的论证是「定时器会随进程重启丢失」，这里更进一步：让正确性根本不建立在后台任务之上。

### D6：不复用 P1.3b 的通知 outbox 发吊销通知

被管理员批量吊销的人不会收到任何通知，应用直接开始报错。这是一个真实的产品缺憾，但本期不做。

`notifications.request_id` 是 `NOT NULL` 且外键指向 `requests`（还带 `ON DELETE CASCADE`）。吊销通知没有对应的申请单，要复用就得把它改成可空——那会把「关于某张申请单的通知」这个清晰含义冲淡成「关于任何事的通知」，并弱化那条级联保证。FR-1.3 也没有要求这件事。留到真正需要通用通知能力时，连同它的语义一起设计。

### D7：紧急全局吊销单开一个全局权限

新增 `key:revoke_all`（ScopeGlobal），而不是复用既有的 `platform:configure`。

这是全系统最具破坏性的一次调用。塞进「能配置平台」里，等于谁能改配置谁就能把全公司凭据清零。独立权限意味着授予它是一个单独的、看得见的决定。权限总数 13 → 14，`platform_admin` 经 `allPermissionKeys()` 自动获得，无需手工同步。

吊销**不可逆**：`revoked` 保持终态，没有反向路径。安全靠事前防护——全局权限 + 请求体里必须带精确的确认字符串。理由是「revoked 就是永久死了」是一条有价值的强不变式，一旦可撤销，Edge 的拒绝逻辑与审计叙事都要多一个分支；而误操作的正确解药是重新签发，P1.3b 已经把申请 → 审批 → 领取的链路建完了。

## 4. 数据模型

`api_keys` 加五列：

| 列 | 类型 | 说明 |
|---|---|---|
| `prev_key_hash` | `TEXT` | 共存窗口内仍有效的旧凭据哈希 |
| `prev_key_expires_at` | `TIMESTAMPTZ` | 旧凭据停用时刻 |
| `rotated_at` | `TIMESTAMPTZ` | 最近一次轮换时间，审计用 |
| `upstream_blocked_at` | `TIMESTAMPTZ` | 上游 `/key/block` 确认成功的时刻 |
| `upstream_block_attempts` | `INTEGER NOT NULL DEFAULT 0` | 兜底扫描的尝试次数，到上限即停（见 §5.4） |

```sql
ALTER TABLE api_keys
    ADD COLUMN prev_key_hash           TEXT,
    ADD COLUMN prev_key_expires_at     TIMESTAMPTZ,
    ADD COLUMN rotated_at              TIMESTAMPTZ,
    ADD COLUMN upstream_blocked_at     TIMESTAMPTZ,
    ADD COLUMN upstream_block_attempts INTEGER NOT NULL DEFAULT 0;

-- 两列必须同生同死。少了这条约束，半填的一对会退化成两种糟糕状态之一：
-- expires_at 为空 = 旧凭据永久有效（安全事故），或孤儿到期时间。
ALTER TABLE api_keys ADD CONSTRAINT api_keys_prev_shape_check CHECK (
    (prev_key_hash IS NULL AND prev_key_expires_at IS NULL)
 OR (prev_key_hash IS NOT NULL AND prev_key_expires_at IS NOT NULL)
);

-- Edge 要按 prev_key_hash 查行，两行绝不能声称同一个哈希。
CREATE UNIQUE INDEX api_keys_prev_key_hash_idx
    ON api_keys(prev_key_hash) WHERE prev_key_hash IS NOT NULL;

-- 兜底扫描的驱动索引。
CREATE INDEX api_keys_pending_block_idx
    ON api_keys(status) WHERE upstream_blocked_at IS NULL;
```

回滚（`-- +goose Down`）删掉这两个索引、这条约束与五列。

**既有行的处理**：迁移前已 `revoked` 的密钥，`upstream_blocked_at` 为 `NULL`，会被扫描捞起来重新封禁一遍。这是期望行为——它们当初可能正是封禁失败的那些；探针 P2 已证明重复封禁幂等，P1 已证明打不存在的 key 返回 404 被当作成功，两种情况都能安全收敛。

## 5. 组件与接口

### 5.1 轮换

`internal/control/keyissue.go` 加 `KeyIssuer.Rotate`：

```go
// Rotate 换发客户端凭据，返回新的 ak- 明文（仅此一次）。
// 不调用上游：ak- 到 sk- 的映射完全由控制面持有。
func (i *KeyIssuer) Rotate(ctx context.Context, id string, window time.Duration) (string, *APIKey, error)
```

`KeyStore` 加：

```go
// Rotate 只在 active 时生效，否则返回 ErrKeyNotActive。
Rotate(ctx context.Context, id, newHash, newPrefix string, prevExpiresAt time.Time) error
// RetireExpiredPrevKeys 把过期的 prev_* 两列置空，返回处理条数。纯卫生。
RetireExpiredPrevKeys(ctx context.Context, now time.Time) (int, error)
```

`WHERE id = $1 AND status = 'active'` 是乐观并发守卫，与 P1.3b 的 `Decide`/`MarkExecuted` 同一套：已吊销或仍 pending 的密钥不能轮换，零行受影响时区分「不存在」与「状态不对」。

**窗口内二次轮换**：行里只有一个 `prev_key_hash` 的位置。窗口内再次轮换，上一次轮出来的成为新的 `prev`，最初那把**当场失效**——即「最多只保留一代宽限」。这是刻意的：会连着轮两次通常意味着第一次轮出来的也泄漏了，此时让更老的凭据继续活着恰恰是错的。

**窗口时长**由调用方每次指定：不同密钥的换发节奏差别很大，CI 几分钟就能换完，嵌在已发布客户端里的要几天。给默认值 24h、上限 30d，防止有人填 10 年把轮换变成摆设。默认值与上限都是包内常量，不进配置——它们是产品语义而非部署差异。

### 5.2 Edge 读取

`internal/apikey/postgres.go` 的 `ByHash` 改为：

```sql
SELECT id, key_prefix, org_id, user_id, upstream_key_enc, status, expires_at,
       (key_hash <> $1) AS via_prev
FROM api_keys
WHERE key_hash = $1
   OR (prev_key_hash = $1 AND prev_key_expires_at > now())
```

`via_prev` 供可观测性使用：命中旧凭据时 Edge 打一条结构化日志（key_id、剩余窗口），运维能在窗口结束前看到「这把还在用旧凭据」，避免到期瞬间集体 401。

**刻意只打日志、不写库**：Edge 的鉴权热路径目前零写入，为一个观测需求给每个请求加一次 DB 写不划算。真正需要精确统计时，用量数据本来就在 ClickHouse 里。

### 5.3 批量与紧急吊销

`internal/control/keystore.go` 加：

```go
// RevokeByOrgSubtree 吊销该节点子树下全部 active/pending 密钥，返回条数。
RevokeByOrgSubtree(ctx context.Context, orgPath string) (int64, error)
// RevokeAll 吊销全系统 active/pending 密钥，返回条数。
RevokeAll(ctx context.Context) (int64, error)
```

子树用物化路径前缀匹配，与既有子树语义一致——**必须加分隔符再比前缀**（`path = $1 OR path LIKE $1 || '/%'`），否则 `/root/rd` 会把同前缀兄弟 `/root/rd2` 一起吊掉。这个陷阱在 P1.2b 的权限判定与 P1.3b 的审批人查找里各踩过一次，这里第三次遇到，专门写测试钉住。

HTTP 层（`internal/control/keyapi.go`）：

| 端点 | 访问声明 | 权限 |
|---|---|---|
| `POST /api/keys/{id}/rotate` | `AccessAuthenticated`，判定下沉到处理器 | 路径里只有密钥 ID，中间件拿不到所属节点——与既有的 `DELETE /api/keys/{id}` 同一类例外 |
| `POST /api/orgs/{id}/keys/revoke` | `AccessPermission` + `TargetFromPath("id")` | `key:write` |
| `POST /api/keys/revoke-all` | `AccessPermission` + `TargetGlobal()` | **`key:revoke_all`**（新增，ScopeGlobal） |

轮换的权限判定：调用者必须是**密钥责任人本人**，或在该密钥所属节点上持有 `key:write`。前者让开发者能自助轮换自己的密钥（与 P1.3b 的自助领取一脉相承），后者让管理员能替人处置。

全局端点的请求体必须精确匹配 `{"confirm":"REVOKE ALL KEYS"}`，否则 400 `confirm_required`。

### 5.4 上游封禁兜底扫描

`internal/control/keyissue.go` 加：

```go
// BlockPendingUpstream 给已吊销但尚未确认封禁的密钥补做上游封禁，返回成功条数。
func (i *KeyIssuer) BlockPendingUpstream(ctx context.Context) (int, error)
```

`KeyStore` 配套加 `ListRevokedUnblocked` 与 `MarkUpstreamBlocked`。

单条失败只记日志并继续处理其余的——各密钥彼此独立，一把封不掉不该把整个队列卡住，与 P1.3b worker 的处理方式一致。

**探针 P1 的结论直接落在这里**：上游返回 404 视为成功盖戳（那把密钥本来就不在了）。其余错误留着下轮重试，每次递增 `upstream_block_attempts`；沿用 P1.3b 的尝试次数上限思路，到顶记一条 ERROR 停下来交给人，不让一行坏数据每轮刷日志。扫描的驱动条件因此是 `status='revoked' AND upstream_blocked_at IS NULL AND upstream_block_attempts < N`。

接进既有的进程循环：与 P1.3a 的 `CleanupStalePending`、P1.3b 的审批 worker 并列，共用 `runCtx`，周期由新配置项 `KEY_MAINTENANCE_INTERVAL` 控制（默认 1m，沿用前三个周期配置的正数校验——`time.NewTicker` 在 `d <= 0` 时 panic，且 panic 在没有 recover 的 goroutine 里会崩掉整个进程）。同一个循环里顺带跑 `RetireExpiredPrevKeys`。

## 6. 错误处理

| 场景 | 行为 |
|---|---|
| 轮换一把 `revoked` / `pending` 的密钥 | `409 key_not_active` |
| 轮换不存在的密钥 | `404 key_not_found` |
| 轮换时窗口超过上限 | `400 window_too_long` |
| 非责任人且无 `key:write` 轮换 | `403 permission_denied` |
| 全局吊销缺确认字符串 | `400 confirm_required` |
| 上游封禁失败 | 本地吊销**照常生效**，留给扫描重试；Edge 已经在拒了 |
| 上游封禁返回 404 | 视为成功，盖戳收工 |
| 清理 worker 从未运行 | 无安全影响——到期判断在 SQL 里（D5） |

## 7. 测试策略

- **数据库层**：`prev_shape_check` 拒绝半填的一对；`prev_key_hash` 的唯一索引拒绝两行声称同一哈希。
- **轮换状态机**：轮换后新哈希可用、旧哈希在窗口内可用、窗口外不可用；只有 `active` 能轮换；窗口内二次轮换后最初那把当场失效（钉住「一代宽限」）；乐观并发守卫区分 404 与 409。
- **Edge 读取**：直接对 Postgres 验证「过期的 `prev_key_hash` 查不到」，且这条**不跑任何 worker**——证明 D5 的正确性不依赖后台任务。
- **子树吊销**：同前缀兄弟节点 `/root/rd2` 不被 `/root/rd` 误吊（第三次遇到这个陷阱）。
- **兜底扫描**：上游失败留 `NULL` 下轮重试；404 当作成功盖戳；重复封禁不重复计数；重试到上限后停下。
- **权限**：非责任人无 `key:write` 时轮换 403；`key:revoke_all` 缺失时全局吊销 403；确认字符串错误时 400。
- **机械检查**：既有的 `TestEveryRouteDeclaresAccess` 等自动覆盖三条新路由；`authz` 的权限总数断言 13 → 14。

## 8. 验收标准

对真实运行的 Postgres + LiteLLM + Edge 完整链路验证，不依赖模拟：

1. 轮换一把在用的密钥，拿到新 `ak-` 明文。
2. 新 `ak-` 经 Edge 调用成功。
3. 旧 `ak-` 在窗口内经 Edge 调用**仍然成功**，且 control 日志里出现「仍在使用旧凭据」的记录。
4. 把 `prev_key_expires_at` 改到过去，旧 `ak-` 经 Edge 立刻 401——**期间不运行任何 worker**，证明 D5。
5. 轮换前后 `/key/info` 显示的是**同一把上游密钥**，`spend` 与 `max_budget` 连续（证明 D1 保住了预算桶）。
6. 轮换一把已吊销的密钥 → 409。
7. 按子树吊销：目标子树全部 `revoked`，同前缀兄弟节点毫发无伤。
8. 全局紧急吊销：缺确认字符串 → 400；带上后全系统密钥 `revoked`。
9. 兜底扫描把上述批量吊销的密钥在上游逐一 `blocked: true`，`upstream_blocked_at` 被盖戳。
10. 造一把「本地已 revoked、上游仍活着」的密钥（模拟历史封禁失败），扫描把它收敛掉——验证既有缺口被补上。
11. `internal/edge` 零回归。

11–14 个实施任务。比 P1.3b（19 个）小：没有新包、没有新表、没有 outbox，主体是既有类型上的增量与三条端点。
