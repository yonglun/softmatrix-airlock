## 1. 产品概述

### 1.1 一句话定位

**Airlock 是面向中国企业私有化交付的 AI 网关与治理平台。** 它以 LiteLLM 开源版为模型供应商接入层，自建完整的企业级控制面，把「谁能用哪些模型、能用多少、能说什么、数据能去哪」这四件事变成可配置、可审计、可核算的策略。

### 1.2 命名释义

Airlock（气闸舱）是产品的核心隐喻：企业内网与外部模型之间的受控通道。人和数据进出都必须经过检查，而且**双向都要检查**——请求出去要防泄密，响应回来要防污染。

### 1.3 交付形态

对外商业产品，**私有化交付**。每家企业在自己的 IDC 或 VPC 内独立部署一套。多租户发生在「单一企业内部的组织/部门」层面，不是跨企业的 SaaS 隔离。

### 1.4 目标市场

**中国市场为主，兼容海外模型。** 客户主体在境内，但普遍需要同时接入境外模型（通过代理或海外节点）。这决定了产品必须处理出境代理、出境前脱敏，以及「哪些数据允许发往境外模型」的强制策略管控。

## 2. 背景与问题

企业引入生成式 AI 后，普遍在半年内遇到同一组问题：

1. **成本失控且无法归属。** 各部门各自申请 API Key，账单是一个总数，没人说得清哪个部门、哪个项目花了多少，更没法做预算管理。
2. **数据泄露风险不可见。** 员工把客户名单、源代码、财务数据粘进对话框，企业没有任何拦截手段，也没有事后追溯能力。
3. **境外模型的合规压力。** 数据发往境外模型缺乏管控和留痕，无法应对监管问询。
4. **身份与权限脱节。** AI 工具的账号体系游离于企业 IdP 之外，员工离职后 Key 仍然有效。
5. **模型切换成本高。** 业务代码硬编码了某家供应商的 SDK，换模型要改代码。

现有方案的不足：
- **LiteLLM 开源版**解决了第 5 个问题，但管理控制台、SSO、组织级预算、按 Key/Team 的护栏全部属于其商业授权范围，开源版不具备。
- **LiteLLM 企业版**能力较全，但没有数据出境管控，配额只有两级平铺，控制台不面向中国企业的角色分工，且商业模式上无法作为自有产品对外销售。
- **海外竞品（Portkey / Kong AI Gateway / TrueFoundry）**没有动机做中国的数据主权与合规能力，国产 IdP 与国产模型支持薄弱。
- **专业 LLM 安全产品（Lakera / Prompt Security / WitnessAI）**只解决安全，不解决配额、成本与组织治理。

**Airlock 的机会：把「网关能力 + 组织治理 + 内容安全 + 数据主权」在一个私有化产品里做完整，并针对中国企业的身份、模型、合规环境做深度适配。**

## 3. 目标与非目标

### 3.1 产品目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 业务侧零改造接入 | 现有 OpenAI SDK 代码仅改 base_url 和 key 即可运行 |
| G2 | 成本可归属、可预算、可预测 | 任意组织/成本中心/成员/模型维度的账单与总账单逐分对齐 |
| G3 | 敏感数据不出企业边界 | 配置的密级策略在生产流量下无绕过路径，且逐条留痕 |
| G4 | 身份与企业 IdP 统一 | 员工用企业账号登录，离职后 Key 自动失效 |
| G5 | 安全策略敢在生产开启 | 影子模式可量化误报率，护栏引入的首字延迟增量可测且可接受 |
| G6 | 可被非专家部署与维护 | 干净的无外网机器上，客户 IT 照文档 2 小时内完成部署 |

### 3.2 非目标（Non-Goals）

明确不做，以防范围蔓延：

- ❌ **不做模型训练、微调、推理引擎。** vLLM / SGLang 等作为上游被纳管，不自研。
- ❌ **不做 Prompt 工程 IDE 或实验平台。** 这是 Langfuse / PromptLayer 的领域。
- ❌ **不做向量数据库与 RAG 编排。** Dify / Coze 等平台是 Airlock 的**调用方**，不是竞品。
- ❌ **不自研提示注入检测模型。** 集成成熟检测引擎，只保证接口可插拔。
- ❌ **不做跨企业 SaaS 多租户计费。** 本阶段只做私有化部署下单企业内的多组织治理。
- ❌ **不做聊天产品前端。** Airlock 提供管理控制台与模型试用台，不做面向全员的对话应用。

## 4. 目标用户

五类角色，对应控制台的四个工作台：

| 角色 | 核心诉求 | 主要场景 | 所属工作台 |
|---|---|---|---|
| **AI 平台管理员** | 接入模型、分配资源、保证可用 | 新增供应商、配置模型池与降级链、排查调用失败 | 平台管理 |
| **安全与合规官** | 防泄密、防滥用、能交差 | 制定护栏策略、审查拦截记录、导出合规报告、处理误报申诉 | 安全合规 |
| **部门 / 组织负责人** | 预算花在哪、够不够用 | 查看本组织消耗、审批成员提额、处理超支告警 | 成本财务 |
| **财务 / FinOps** | 成本归属与分摊 | 按成本中心出月度账单、看趋势与预测、评估降本方案 | 成本财务 |
| **开发者 / 业务用户** | 快速拿 Key、知道还剩多少 | 申请 Key、查个人用量、在试用台对比模型 | 我的空间 |

### 5.2 三个真正的差异点

不是「也有」，是「只有」：

1. **数据主权与出境管控。** 数据密级标签绑定到组织与成本中心，策略层强制「某密级数据禁止发往境外模型」，出境前强制脱敏并留台账。海外竞品没有动机做，LiteLLM 也不会做。
2. **三维叠加配额。** 组织树继承 + 角色基线 + 个人覆盖，三者取最严，并支持带过期时间的临时提额审批。竞品普遍只有两级平铺，做不到「实习生无论在哪个部门，单日不超过 50 元」这类横切规则。
3. **中国企业交付适配。** 国产 IdP 开箱即用、国产模型定价表内置（含缓存命中价与思考 token 计费）、离线安装、信创数据库适配路径、中文合规报告模板。

## 6. 系统架构

### 6.1 架构原则

**LiteLLM 只做数据面，所有企业能力自建。**

这条原则同时解决两个问题：
- **法务边界。** LiteLLM 主体是 MIT，但 Admin UI、SSO、Team/Org 预算、按 Key/Team 的 Guardrails 等属于其商业授权范围。Airlock 不使用也不修改这些代码，只用其开源的供应商适配能力，因此可以自由地作为商业产品销售。
- **能力上限。** 三维配额、内容护栏、数据出境管控这些能力 LiteLLM 无论开源版还是企业版都不提供，必须自建才可能实现。

### 6.2 组件拓扑

```
调用方（业务应用 / IDE / Dify / Agent / MCP 客户端）
   │  Airlock 虚拟 Key（ak-xxx）· OpenAI 兼容协议
   ▼
┌──────────────────────────────────────────────────┐
│  Airlock Edge（Go，自研，内联反向代理）             │
│  1 Key 鉴权 → 2 身份/组织解析 → 3 模型可见性        │
│  → 4 配额预扣 → 5 入向护栏 → 6 出境判定             │
│  → 7 转发/流式回传 → 8 出向护栏 → 9 计量与成本核算   │
│  → 10 配额结算 → 11 审计落库                       │
└──────────────────────────────────────────────────┘
   │  内部 master key（单一凭证，网络层锁死）
   ▼
┌──────────────────────────────────────────────────┐
│  LiteLLM Proxy（开源版，纯数据面）                  │
│  供应商协议适配 · 负载均衡 · 重试与 Fallback         │
│  不启用任何 Enterprise 功能                         │
└──────────────────────────────────────────────────┘
   ▼
模型供应商
  境内：通义千问 / 豆包 / DeepSeek / 智谱 / Kimi / 混元
  自建：本地 vLLM / SGLang
  境外：OpenAI / Anthropic / Gemini / Azure / Bedrock

━━━ 控制面（旁路，不在请求关键路径上）━━━

Airlock Console（Next.js）
   ↕
Airlock Control Plane（Go，自研）
   管理 API + BFF · 配置热下发到 Edge
   ↕                        ↕
Casdoor（开源身份基座）      存储层
  钉钉 / 企微 / 飞书          PostgreSQL：配置 · 组织 · 策略
  LDAP / AD / SAML          Redis：配额实时计数 · 策略缓存
  OIDC / CAS                ClickHouse：调用明细 · 审计 · 分析

可插拔护栏引擎（统一 Guardrail Provider 接口）
  正则/词典 · PII 识别引擎 · 小模型分类器 · 第三方商业引擎
```

### 6.3 组件职责边界

| 组件 | 职责 | 明确不负责 |
|---|---|---|
| **Airlock Edge** | 请求路径上的一切管控：鉴权、配额、护栏、出境判定、计量、审计 | 不做供应商协议适配，不做配置管理 |
| **Airlock Control Plane** | 配置管理、审批流、分析查询、License、配置下发 | 不在请求关键路径上，宕机不影响已生效策略的推理调用 |
| **LiteLLM Proxy** | 供应商协议适配、负载均衡、重试、Fallback、流式规范化 | 不做任何鉴权、配额、安全判断 |
| **Casdoor** | 身份认证、IdP 联邦、用户目录 | 不管理 Airlock 的组织树、角色语义与配额 |
| **Console** | 五类角色的操作界面 | 不直接访问数据库，只通过 Control Plane API |

**关键设计**：Control Plane 宕机时，Edge 依靠本地缓存的策略继续正常服务推理请求（降级为「策略不再更新」而非「服务不可用」）。这是私有化交付下的可用性底线。

## 7. 领域模型

### 7.1 核心实体

```
Organization（组织树，可嵌套）
   ├── 继承：配额策略 · 护栏策略 · 默认数据密级 · 模型可见性
   └── Membership ──> User（身份来自 Casdoor）──> Role

CostCenter（项目 / 成本中心）  ← 与组织树正交的第二归属维度

VirtualKey（ak-xxx）
   归属 = Organization + 责任人 User + 可选 CostCenter

ModelCatalog: Provider → ModelPool → Model
   Model 属性：定价规则 · 境内/境外/自建标记 · 能力标签 · 上下文长度

QuotaPolicy · GuardrailPolicy · DataClass · EgressPolicy

UsageRecord（ClickHouse）· AuditEvent（ClickHouse）· AdminAuditLog（PostgreSQL）
```

### 7.2 为什么组织树与成本中心并存

部门树表达的是**管理关系**，但成本分摊在企业里常按**项目**走，而项目普遍跨部门。竞品普遍只有一个归属维度，导致财务口径对不上，报表拿去开会被质疑。

设计上两者都是一等公民：
- Key 同时归属组织和（可选的）成本中心
- 配额可按两个维度分别设置，取最严
- 报表可按任一维度或两维交叉输出

这是低成本高价值的设计——建模复杂度增加有限，但直接决定财务部门是否认可这个系统。

### 7.3 数据密级

四级，可自定义名称与层数：`公开 < 内部 < 秘密 < 机密`

密级判定优先级链（从高到低）：
1. 请求头显式声明（`X-Airlock-Data-Class`）
2. Key 上绑定的声明密级
3. 所属组织的默认密级
4. 内容自动推断（由护栏检测器给出）

高优先级来源存在时不再向下查找。判定依据必须记入出境台账。

## 8. 功能需求

### 8.1 身份与访问控制（L1）

**FR-1.1 身份接入**
- 内嵌 Casdoor 作为身份基座，Airlock 作为 OIDC 客户端接入
- 支持连接器：钉钉、企业微信、飞书、LDAP、Active Directory、SAML 2.0、OIDC、CAS
- 支持客户使用自有的 Casdoor 或 Keycloak 实例（通过标准 OIDC 对接，不强制使用内嵌实例）
- 组织与成员支持从 LDAP / AD / 钉钉通讯录 / 企微通讯录同步，可配置同步周期
- 登录、登出、会话过期均产生审计事件

**FR-1.2 RBAC**
- 内置 5 个角色：平台管理员、安全合规官、组织管理员、开发者、审计员（只读）
- 支持自定义角色，权限模型为「资源 × 操作」矩阵
- 角色在组织节点上授予，支持同一用户在不同组织节点持有不同角色
- 权限判定沿组织树向上继承

**FR-1.3 虚拟密钥生命周期**
- 完整流程：申请 → 审批 → 签发 → 轮换 → 吊销
- 明文仅在签发时显示一次，存储为不可逆哈希
- Key 属性：所属组织、责任人、成本中心、过期时间、IP 白名单、来源应用标识、用途备注、声明密级
- 责任人离职（IdP 侧禁用）时，其名下 Key 自动失效
- 支持批量吊销与紧急全局吊销

**FR-1.4 模型可见性**
- 三级白名单叠加：组织级 → 角色级 → Key 级
- 判定取交集，任一级未授权即不可见
- 不可见的模型在试用台与模型列表中不展示，调用返回明确错误码

### 8.2 模型接入与路由

**FR-2.1 供应商管理**
- 支持添加、编辑、禁用供应商，凭证加密存储
- 每个供应商标记：境内 / 境外 / 自建私有
- 供应商健康检查与可用性展示

**FR-2.2 模型池与路由**
- 模型池：一组等价模型，支持负载均衡与故障转移
- 降级链配置：主模型 → 备用模型 → 低价模型
- 路由策略：轮询、加权、最低延迟、最低成本

**FR-2.3 定价模型**
- 每个模型可配置：输入单价、输出单价、**缓存命中单价**、**思考 token 单价**、批量折扣、最小计费单元
- 支持按时间生效的价格版本（供应商调价时历史账单不受影响）
- 内置国产主流模型定价表，随版本更新

> **设计要求**：定价数据模型必须在 M0 阶段就做对。国产模型计价规则复杂（缓存、思考 token、阶梯价），事后改模型会导致历史账单全部失真。

### 8.3 配额管理

**FR-3.1 计量维度**

四个维度，每个可独立设策略：

| 维度 | 说明 |
|---|---|
| 金额（￥） | 主维度，基于 Airlock 自有定价表核算 |
| Token 数 | 输入 / 输出可分开限额 |
| 请求数 | 防滥用兜底 |
| 速率 | RPM / TPM / 最大并发 |

**FR-3.2 三维叠加判定**

```
有效额度 = min( 组织额度（含祖先链约束）, 角色基线额度, 个人额度 )
```

三者取最严。三个维度的语义定义：

| 维度 | 作用域 | 说明 |
|---|---|---|
| **组织额度** | 组织节点，沿祖先链约束 | 该组织及其子树的总量控制 |
| **角色基线额度** | **全局横切，与组织无关** | 「实习生无论在哪个部门，单日不超过 50 元」这类规则 |
| **个人额度** | 单个用户 | 对特定成员的额外限制 |

三者均为**上限**，参与取最严运算，不存在「覆盖」语义——**临时提额（FR-3.6）是唯一的放宽机制**，且带过期时间。这一设计保证任何时刻的有效额度都可由三条策略推导，不会出现「为什么这个人能超额」的追溯困难。

**FR-3.3 组织树语义**

子组织额度之和与父额度的关系可配置：
- `严格`：子额度之和不得超过父额度（适合预算刚性的国企、金融客户）
- `超售`：允许子额度之和超过父额度，实际消耗时受父额度约束（适合互联网公司的配额池共享）

**FR-3.4 周期**

日 / 周 / 自然月（对齐财务月）/ 自定义窗口。周期边界与重置时间可配置时区。

**FR-3.5 超限行为分级**

| 阈值 | 默认行为 | 可配置项 |
|---|---|---|
| 80% | 邮件 / 钉钉 / 企微告警给责任人与组织管理员 | 阈值、通知渠道、接收人 |
| 95% | 告警升级 + 控制台横幅提示 | 阈值 |
| 100% | **默认降级**：自动路由到指定低价模型池，业务不中断 | 可改为阻断；可指定降级目标池 |
| 硬顶 | 强制阻断，返回结构化错误码 | 可关闭硬顶 |

> **产品默认值为「降级」**。理由：业务不中断对业务方友好，是明确的差异化卖点。但必须在控制台和响应头中明确标示「本次请求已降级到 X 模型」，不能静默替换。

**FR-3.6 临时提额**
- 成员在「我的空间」发起申请，填写理由与所需额度
- 组织管理员审批
- 生成带过期时间的增量额度，到期自动回收
- 申请、审批、回收全程审计

**FR-3.7 实现要求：两阶段预扣-结算**

流式请求事前不知道消耗多少 token，因此配额扣减分两阶段：
1. **预扣**（Edge 第 4 步）：按请求的 `max_tokens` 上限在 Redis 原子预扣
2. **结算**（Edge 第 10 步）：按实际用量结算差额，多退少补

异常中断（连接断开、进程崩溃）由后台对账任务按预扣记录的 TTL 兜底回滚。

**验收要求**：高并发下不得超发。压测场景需覆盖「多个 Key 同时消耗同一组织额度」。

### 8.4 内容护栏（L2）

**FR-4.1 检测能力**

入向（用户 → 模型）：
- PII：身份证、手机号、银行卡、地址、姓名
- 企业凭证与密钥：API Key、密码、证书、内网地址
- 敏感词与合规词库，**支持导入客户自有词库**
- 提示注入与越狱检测
- 系统提示词套取检测

出向（模型 → 用户）：
- PII 回流
- 内部代码与文档片段泄露
- 内容安全分类

**FR-4.2 可插拔引擎**

统一 `Guardrail Provider` 接口，内置实现包括正则/词典引擎、PII 识别引擎、小模型分类器；客户可接入第三方商业引擎或自研引擎。接口需定义：输入契约、超时与失败策略（fail-open / fail-closed 可配置）、批量调用能力。

**FR-4.3 策略编排**

```
策略 = 检测器组合
     × 作用范围（组织 / 角色 / Key / 模型）
     × 动作（放行 / 脱敏 / 改写 / 阻断 / 仅告警）
     × 例外名单
```

策略按组织树继承，子组织可加严不可放宽（是否允许放宽由平台管理员开关控制）。

**FR-4.4 影子模式（必交付项）**

新策略可先以「只记录不拦截」模式运行，控制台展示：
- 若启用会拦截多少请求
- 按检测器分类的命中分布
- 抽样的命中样本，供人工判定误报
- 估算误报率

> **没有影子模式，企业不敢在生产开启护栏。** 这不是选配功能，是护栏能否落地的前提。多数竞品在这一点上做得敷衍，是可以攻击的弱点。

**FR-4.5 误报申诉流**
- 用户对被拦截的请求发起申诉
- 安全合规官在工作台处理，可查看完整上下文
- 一键将该模式加入例外名单
- 全程审计

**FR-4.6 流式护栏**

出向护栏需处理 SSE 流式响应。设计要求：
- 采用滑动缓冲窗口，在延迟与检出率之间取平衡
- 缓冲窗口大小可配置
- 命中时中断流并返回结构化错误，已发送内容需在控制台标记
- **首字延迟（TTFT）增量必须可量化并展示给客户**

### 8.5 数据主权与出境管控（L3）

**FR-5.1 密级体系**

四级密级（可自定义），判定优先级链见 §7.3。

**FR-5.2 出境策略矩阵**

`密级 × 目的地 → 允许 / 脱敏后允许 / 禁止`

在控制台上呈现为一张可直接点选的矩阵表格。目的地维度至少包含：境内供应商、境外供应商、自建私有模型。

**FR-5.3 脱敏后出境**
- 按策略在请求发出前执行脱敏
- 记录脱敏前后的差异摘要（不记录原文，除非审计策略允许）
- 脱敏规则复用护栏检测器

**FR-5.4 出境台账**

每条境外调用逐条留痕，字段包括：时间、发起人、组织、成本中心、目标模型与供应商、判定密级、**密级判定依据**、是否脱敏、脱敏差异摘要、审批人（如涉及审批）。

**FR-5.5 合规报告**

中文模板一键导出：
- 等保测评材料（AI 服务相关部分）
- 生成式 AI 服务管理办法自查表
- 自定义时间范围的出境数据统计

### 8.6 Agent / MCP 治理（L4）

**FR-6.1** MCP Server 注册与纳管，工具级白名单
**FR-6.2** Agent 服务身份与发起人自然人身份绑定，配额与审计追溯到人
**FR-6.3** 工具调用审计与越权检测
**FR-6.4** 多轮会话上下文的累积注入检测

> 此部分排在最后的里程碑。行业标准仍在演进，过早实现容易白做。

### 8.7 审计

**FR-7.1 请求级审计**

全量留痕。**提示词与响应原文的留存策略可配置**：
- 不留存（只记元数据）
- 脱敏后留存
- 全量留存

均可配置留存期限与到期处理（删除 / 归档）。

> 这是中国客户合规谈判中的必争项。不同行业、不同客户对「网关能不能看到我的对话内容」态度差异极大，必须做成配置项而非产品预设。

**FR-7.2 管理操作审计**

所有配置变更单独记录：操作人、时间、变更前后值、来源 IP。

**FR-7.3 防篡改**

审计日志采用哈希链，支持完整性校验与只读导出。

**FR-7.4 审计检索**

支持按人、组织、成本中心、模型、时间、关键词、拦截状态等维度组合检索。

### 8.8 分析与 FinOps

**FR-8.1 多维下钻**：组织 / 成本中心 / 成员 / 模型 / 应用 / 时间，任意组合

**FR-8.2 成本**：账单、趋势、月度预测、突增异常告警

**FR-8.3 性能**：TTFT、TPS、错误率、限流率，按模型横向对比

**FR-8.4 优化建议**

识别可替换的调用模式，给出「这批调用用 DeepSeek 替代 GPT-4o 可月省 ￥X，质量风险评估 Y」的建议。

> 这是 FinOps 的杀手锏，也是最直接的续费理由——产品每年为客户省下的钱要能被量化。

**FR-8.5 定时报表**：按周期推送到钉钉 / 企业微信 / 邮件，支持 CSV / Excel 导出

### 8.9 控制台

**IA 方案：角色工作台（方案 B）**

顶部切换四个工作台，每个工作台是一条完整的任务动线：

| 工作台 | 导航项 |
|---|---|
| **平台管理** | 总览 · 模型供应商 · 模型池与路由 · 虚拟密钥 · 组织与成员 · 角色与权限 · SSO 配置 · 系统与 License |
| **安全合规** | 安全态势 · 护栏策略 · 数据分级 · 拦截记录 · 审计检索 · 出境台账 · 合规报告 |
| **成本财务** | 成本总览 · 配额策略 · 提额审批 · 成本中心账单 · 用量分析 · 优化建议 · 定时报表 |
| **我的空间** | 我的密钥 · 我的用量与余额 · 申请提额 · 模型试用台 |

选择理由：
- 每个角色进来只见自己的世界，认知负担低
- 首页可以真正为该角色定制，而非做一个对谁都不够好的通用首页
- 销售演示时按买家角色讲（安全官看安全工作台、CFO 看成本工作台），说服力强
- 把「谁该看什么」变成产品结构而非权限配置

代价（已接受）：兼多角色的用户需要切换；需设计四套首页；少量功能在两个工作台重复出现。

### 8.10 交付、License 与运维

**FR-9.1 部署形态**
- Helm Chart（K8s 客户）
- docker-compose（单机 / 小客户）
- 离线安装包：镜像 tar + 一键脚本，适配完全无外网的内网环境

**FR-9.2 License**
- 离线许可证文件（无需联网校验）
- 绑定机器指纹 / 节点数 / 席位数
- 到期提醒与宽限期
- 到期后降级为只读，不中断已有推理服务

**FR-9.3 升级**
- 版本化 API
- 数据库迁移脚本，支持回滚
- 跨版本升级路径文档

**FR-9.4 高可用**
- Edge 无状态，可横向扩展
- Control Plane 宕机不影响推理链路
- 存储可使用客户既有实例，也可由安装包内置

**FR-9.5 可观测与自助排障**
- Prometheus 指标暴露
- 健康检查端点
- **自诊断页面**：客户 IT 可自查环境问题（数据库连通性、供应商可达性、证书有效期、License 状态）

> 自诊断页面直接降低售后成本。私有化交付的产品，售后是主要的隐性成本。

## 9. 非功能需求

| 类别 | 要求 |
|---|---|
| **性能** | Edge 引入的额外延迟 < 3ms（P99，不含护栏）；护栏引入的延迟需可量化并可配置上限 |
| **吞吐** | 单 Edge 实例支持 ≥ 500 RPS；可横向扩展 |
| **可用性** | Control Plane 宕机时推理链路继续可用；Edge 支持多实例无状态部署 |
| **分析查询** | 千万级调用记录下，常规多维查询响应 < 2s |
| **数据一致性** | 配额扣减在并发下不超发；账单口径与总账单逐分对齐 |
| **安全** | 供应商凭证加密存储；Key 不可逆存储；审计日志防篡改；LiteLLM 的 master key 在网络层锁死，不可从外部访问 |
| **兼容** | OpenAI 兼容协议；现有 SDK 仅改 base_url 与 key 即可接入 |
| **信创适配** | PostgreSQL 可替换为人大金仓 / openGauss；ClickHouse 在小规模场景可降级为 PostgreSQL 分区表 |
| **国际化** | 界面中文优先，架构上预留多语言能力 |

## 10. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| Edge 数据面 | **Go** | 单二进制交付，私有化部署友好；并发模型适合网关；与 Casdoor 同语言 |
| Control Plane | **Go** | 与 Edge 共享领域模型代码，减少一人维护的心智负担 |
| Console | **Next.js + TypeScript** | 生态成熟，AI 辅助开发效率高，组件库丰富 |
| 身份基座 | **Casdoor（Apache-2.0）** | 原生支持钉钉/企微/飞书等数十种连接器，中文生态友好，私有化交付成熟 |
| 供应商接入 | **LiteLLM 开源版** | 100+ 供应商适配是最不值得自研的部分 |
| 配置存储 | **PostgreSQL** | 事务能力、成熟度、信创替代路径清晰 |
| 实时计数 | **Redis** | 配额预扣需要原子操作与低延迟 |
| 分析存储 | **ClickHouse** | 调用明细是典型的时序 + 高基数聚合场景 |

### 10.1 被否决的方案

| 方案 | 否决理由 |
|---|---|
| **Fork LiteLLM 深度改造** | 长期 rebase 成本高；需人工剔除 enterprise 目录以规避授权风险；改造后难以跟上游 |
| **购买 LiteLLM Enterprise 授权，只重做前端** | 商业模式退化为转售，定价与分发受制于对方条款 |
| **配置投影方案（不做内联代理）** | Team/Org 预算与按 Key/Team 的 Guardrails 本身就是 Enterprise 功能；内容护栏、数据出境管控完全无法实现，等于放弃 L2/L3/L4 |
| **Go 自研全部供应商适配** | 重写几十家供应商适配 + 流式差异 + 参数映射，一人团队不现实，且放弃了选择 LiteLLM 的初衷 |
| **Keycloak 作为身份基座** | 资源占用大、配置复杂；钉钉/企微/飞书需自写 SPI 或走中转 |
| **Python/FastAPI 控制面** | 与 LiteLLM 同生态是优势，但私有化交付的打包与资源占用不如 Go 单二进制 |

## 11. 关键设计决策记录

| 编号 | 决策 | 理由 |
|---|---|---|
| D1 | LiteLLM 仅作纯数据面，不启用任何 Enterprise 功能 | 同时解决授权边界与能力上限两个问题 |
| D2 | Edge 内联反向代理承担全部管控 | 唯一能实现 L2/L3/L4 的架构 |
| D3 | 内嵌 Casdoor，通过标准 OIDC 解耦 | 省下数月的 IdP 对接工作；解耦保证升级不互相牵制 |
| D4 | CostCenter 作为一等公民 | 财务口径对得上，直接影响财务部门是否认可系统 |
| D5 | 配额超限默认降级而非阻断 | 业务不中断，差异化卖点；但必须显式标示，不可静默替换 |
| D6 | 控制台采用角色工作台 IA | 降低认知负担；销售演示按买家角色讲更有说服力 |
| D7 | 影子模式列为护栏的必交付项 | 没有它企业不敢在生产开护栏，护栏能力等于零 |
| D8 | 审计原文留存策略做成配置项 | 客户对此态度差异极大，不能有产品预设 |
| D9 | 定价数据模型在 M0 就做完整 | 事后改会导致历史账单全部失真 |
| D10 | Control Plane 宕机不影响推理链路 | 私有化交付的可用性底线 |

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 流式出向护栏的延迟与体验矛盾 | 首字延迟变差，业务方抵触 | M0 阶段即做原型验证缓冲窗口策略，不等到 M4 才发现方案不可行 |
| LiteLLM 上游 API 变更 | Edge 转发逻辑被打断 | 锁定版本 + 契约测试；Edge 与 LiteLLM 间只用标准 OpenAI 协议，不依赖私有接口 |
| 成本核算不准 | 账单对不上，客户信任崩塌 | 定价模型 M0 就支持缓存命中价、思考 token、阶梯价 |
| 护栏误报引发业务抵触 | 客户停用安全功能，差异化归零 | 影子模式与误报申诉流同期上线，列为必交付项 |
| 一人产能与 L1–L4 全量范围的张力 | 战线过长，什么都做不完 | 里程碑严格切分，每个里程碑独立可验收；接受 L4 排在最后 |
| Casdoor 内嵌带来的运维耦合 | 升级时两个系统互相牵制 | 标准 OIDC 解耦，不改 Casdoor 代码；支持客户使用自有实例 |
| 首批客户因缺少安全能力而拒绝 | v1.0 阶段的 POC 转化率低 | 已接受此风险：v1.0 阶段接触客户的主要目的是获取需求反馈，用真实异议塑造 M4/M5 的产品细节 |

## 13. 验收标准

产品级验收（对应 §3.1 的目标）：

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| A1 | 零改造接入 | 现有 OpenAI SDK 代码仅改 base_url 与 key，可正常调用境内与境外模型（含流式） |
| A2 | 成本归属 | 任意组织/成本中心/成员/模型维度的账单之和与总账单逐分对齐 |
| A3 | 配额正确性 | 三层配额并发压测不超发；超限自动降级到低价模型池且业务不中断，响应头正确标示降级 |
| A4 | 数据出境管控 | 机密级数据发往境外模型被拒绝、留痕，且可导出为合规材料；无绕过路径 |
| A5 | 身份一致性 | 企业用自家钉钉/企微/LDAP 登录；IdP 侧禁用用户后，其名下 Key 立即失效 |
| A6 | 护栏可落地 | 影子模式在真实流量下测出误报率；流式首字延迟增量可量化 |
| A7 | 分析性能 | 千万级记录下多维下钻查询 < 2s |
| A8 | 可部署性 | 干净的无外网机器上，照文档 2 小时内完成部署 |
| A9 | 可升级性 | 一次跨版本升级演练成功，并成功回滚 |

## 14. 术语表

| 术语 | 含义 |
|---|---|
| **Edge** | Airlock 的内联反向代理，请求路径上的管控执行点 |
| **Control Plane** | Airlock 的控制面，负责配置管理与分析查询，不在请求关键路径上 |
| **虚拟 Key** | Airlock 签发给调用方的密钥（`ak-` 前缀），与供应商真实密钥无关 |
| **三维叠加配额** | 组织额度、角色基线额度、个人额度覆盖三者取最严的配额判定模型 |
| **成本中心（CostCenter）** | 与组织树正交的成本归属维度，通常对应项目 |
| **影子模式** | 护栏策略只记录不拦截的运行模式，用于上线前评估误报率 |
| **出境台账** | 所有发往境外模型的调用的逐条留痕记录 |
| **降级** | 配额超限时自动路由到低价模型池，保证业务不中断的行为 |
| **两阶段预扣-结算** | 配额扣减机制：请求前按上限预扣，响应后按实际用量结算差额 |
