## §0 范围与拆分

Roadmap 的 P1.5 里剩下的部分装着两个彼此独立的子系统：

1. **License 校验**——签名格式、到期与席位判定、降级语义、控制台呈现。纯代码特性，几乎全部落在管理面。
2. **交付包**——Dockerfile、生产 `docker-compose`、镜像 digest 钉死、离线镜像 tar、一键安装脚本、部署与运维手册。几乎不动 Go 代码。

两者唯一的耦合点是「部署文档要告诉客户 license 文件放在哪、怎么挂载」。因此**先做 License，交付包拆到 P1.5c**——反过来做的话部署文档要写两遍。

**本文档只覆盖 License 校验。**

### 现状探查（P1.5b 开工前）

- `deploy/docker-compose.yml` 目前只是**开发依赖栈**：postgres / clickhouse / litellm / casdoor / openldap / mailpit 六个服务，**不含 Airlock 自己**，仓库里也没有任何 Dockerfile。所谓「一键部署」目前一键部署的是依赖，不是产品。这是 P1.5c 的主要工作量。
- 镜像多处指向浮动 tag（`casbin/casdoor:latest`、`axllent/mailpit:latest`、`ghcr.io/berriai/litellm:main-stable`）。离线包必须先把这些钉到确定 digest，否则「照文档部署成功」不可复现。同样留给 P1.5c。
- License 相关代码目前**为零**：`internal/config/config.go` 的 `Config` 里没有任何 license 字段。本阶段从零开始。
- 席位的天然定义已经存在：`migrations/20260828000001_identity.sql:8` 的 `status TEXT ... CHECK (status IN ('active','disabled'))`。
- 全仓**只有一条建用户的路径**：`internal/control/userstore.go:76` 的 `INSERT INTO users`，只被登录回调调用。席位闸因此有唯一落点。

## §1 包边界与数据流

新增 `internal/license` 包，只做一件事：**把一段文本变成一个可信的 `License` 值，或者告诉你它不可信**。

```go
package license

type Status string

const (
    StatusValid   Status = "valid"   // 签名有效且未过期
    StatusExpired Status = "expired" // 签名有效但已过期
    StatusTrial   Status = "trial"   // 未配置 license，走内置试用额度
)

type License struct {
    Status    Status
    Customer  string
    LicenseID string
    IssuedAt  time.Time
    ExpiresAt time.Time // Trial 时为零值，表示不设到期
    Seats     int
}

// VerifyWith 用显式公钥验签并解析。测试用它注入临时密钥对。
func VerifyWith(pub ed25519.PublicKey, raw []byte, now time.Time) (License, error)

// Verify 套用编译进二进制的内置公钥。生产路径走这个。
func Verify(raw []byte, now time.Time) (License, error)

// Trial 返回内置试用额度：5 席位，不设到期。
func Trial() License
```

该包**不 import `internal/control` 与 `internal/edge`**，不碰数据库、不碰 HTTP、不读环境变量——收字节，吐值。席位上限是多少由它说了算；「当前用了几个席位」完全不归它管，那是控制面查库的事。

`Makefile` 的 `lint` 加第六条包独立性检查，与现有 `authz` / `litellm` / `notify` / `usage` 四条同样写法：

```make
@echo "检查 license 包的独立性..."
@! go list -deps ./internal/license/... 2>/dev/null | grep -qE 'airlock/internal/(control|edge)' \
    || { echo "违规：internal/license 依赖了 internal/control 或 internal/edge"; exit 1; }
```

### 数据流

只有两条，都在管理面。

**启动时**（`internal/app/control.go` 的 `RunControl`）：读 `AIRLOCK_LICENSE_FILE` → 有文件就 `license.Verify`，没配就 `license.Trial()` → 结果装进 `control.LicenseGate` → 注入 `ServerDeps` 与 `AuthDeps`。

**验签失败时拒绝启动**（文件损坏、签名不对、版本不支持），与 `AIRLOCK_ENCRYPTION_KEY` 非法时的处理一致（`internal/app/control.go` 里 `len(cfg.EncryptionKey) == 0` 直接 return error）。理由：那是配置错误，不是降级场景。静默降级成 trial 只会让人以为 license 生效了，直到某天发现席位数根本不对。

**文件不存在**与**未配置该环境变量**都走 trial，不算错误。

**运行时**：`LicenseGate` 持有解析结果，每次判定用传入的 `now` 与 `ExpiresAt` 现算。**不能只在启动时判过期**——跨过到期日仍在运行的进程必须自己降级，而不是等下次重启。

**数据面 `internal/edge` 零改动。** 既然过期不影响流量（见 §3），Edge 就不需要知道 license 存在，也就不该为它多一次查库或多一个进程级缓存。

## §2 License 文件格式与验签

文件是**一行 ASCII 文本**，两段 base64url（无填充）用 `.` 分隔：

```
eyJ2IjoxLCJjdXN0b21lciI6Li4ufQ.mQ7fJ2v...
└────── payload（JSON） ──────┘ └─ 签名 ─┘
```

payload：

```json
{
  "v": 1,
  "license_id": "AL-2026-0007",
  "customer": "某某银行",
  "issued_at": "2026-09-06T00:00:00Z",
  "expires_at": "2027-09-07T00:00:00Z",
  "seats": 200
}
```

### 验签顺序

**必须先验签，再信任任何字段：**

1. 按 `.` 切成两段，任一段缺失 → `ErrMalformed`
2. 两段各自 base64url 解码，失败 → `ErrMalformed`
3. `ed25519.Verify(pub, payloadBytes, sig)`，失败 → `ErrBadSignature`
4. **到这一步才** `json.Unmarshal(payloadBytes, &p)`
5. `p.V != 1` → `ErrUnsupportedVersion`
6. `p.Seats <= 0` → `ErrInvalidPayload`
7. `now.Before(p.ExpiresAt)` 决定 `StatusValid` 还是 `StatusExpired`

第 4 步的位置是刻意的。反过来做的话，攻击者能拿畸形 payload 去打 JSON 解析器，而那段代码本不该接触未经认证的输入。

### 版本字段

`v` 不是 1 就直接拒绝，报「license 格式版本 N 不受支持，请升级 Airlock」。将来加字段（功能开关、并发上限）时，老版本二进制会明确说不认识，而不是默默忽略新约束——**默默忽略正是 license 机制最典型的失效方式**。

### 公钥

`internal/license/pubkey.go` 里一个 base64 常量，32 字节，编译进二进制。

**刻意不提供任何环境变量或文件来覆盖它。** 一旦可覆盖，客户换成自己的公钥就能签发任意 license，整套机制归零。可测性靠 `VerifyWith` 的显式参数拿到，而不是靠一个生产环境也存在的后门。

### 错误分类

各自独立的错误值、各自独立的测试：

| 错误值 | 触发条件 |
|---|---|
| `ErrMalformed` | 缺 `.` 分隔、base64 非法 |
| `ErrBadSignature` | 签名验证失败（含 payload 被篡改） |
| `ErrUnsupportedVersion` | `v != 1` |
| `ErrInvalidPayload` | JSON 非法、`seats <= 0`、`customer` 为空 |

## §3 判定语义

| | 数据面流量 | 已有用户登录 | 新用户开户 | 管理写操作 | 吊销类操作 |
|---|---|---|---|---|---|
| **Valid** | 放行 | 允许 | 席位未满则允许 | 允许 | 允许 |
| **Expired** | 放行 | 允许 | **拒绝** | **拒绝** | **允许** |
| **Trial** | 放行 | 允许 | 席位未满则允许（上限 5） | 允许 | 允许 |

### 为什么过期不阻断数据面

客户的生产流量是他们的业务命脉。用它当商务筹码会让 POC 阶段的客户直接不敢用；而冻结管理动作足以形成续费压力，且损失完全可回滚。这条决定同时让「时钟错乱导致误判过期」的后果从「全公司业务中断」降到「管理员暂时改不了配置」——因此不额外做时钟校验。

### 为什么过期后吊销类仍放行

刻意开的口子，不是遗漏。吊销密钥（`DELETE /api/keys/{id}`、`POST /api/orgs/{id}/keys/revoke`、`POST /api/keys/revoke-all`）是**止损动作**。客户发现密钥泄漏时，如果因为 license 过期而拦住他撤销，我们就是在把商务纠纷变成对方的安全事故。何况这些操作只会减少系统里可用的凭据，对我们的商业利益毫无损害。

这一条也说明了为什么只读降级**不能**简单实现成「非 GET 一律拦」——见 §4。

### 为什么过期后新用户开户按拒绝处理

开户是写操作，与其它写操作同样对待。已建档用户不受影响（登录走 `Upsert` 的 `ON CONFLICT` 更新分支），所以管理员一定还能登进来看到红条、知道该续费——不会出现「过期了连人都进不去、也没人知道为什么」的死局。

### 席位计数

只数 `status = 'active'` 的用户。被停用的人不占席位，管理员停用一个离职者就能腾出位置给新人——**这句话必须写进运维手册**。

计数**只在「新用户首次登录」这一个时刻查库**（`SELECT count(*) FROM users WHERE status = 'active'`）。登录是低频动作，不需要缓存；每请求数一遍是纯粹的浪费。

### 到期时刻的边界

`expires_at` 是**排他上界**，判定为 `now.Before(ExpiresAt)`。

签发工具接受 `-expires 2027-09-06` 这样的裸日期，把它签成**次日零点 UTC**，语义是「2027 年 9 月 6 日当天仍然可用」。不这么做的话，写在合同里的「授权至 9 月 6 日」会在 9 月 6 日零点就失效，白丢一天。

这与 P1.5a 审计检索里 `internal/control/usageapi.go:77` 的 `parseRangeEnd` 是同一个决策（那次是真的踩过：裸日期解析成当天零点，导致「到 9 月 6 日」把 9 月 6 日整天的数据全部排除）。保持一致。

## §4 落点

### 4.1 路由表的第三个声明位

只读降级不能用「非 GET 一律拦」实现。§3 的吊销豁免就是反例：`DELETE /api/keys/{id}` 是写操作但必须放行。方法推导还有个更深的毛病——将来加端点时没人会想起 license，新写的 `POST` 自动落入「过期即拦」，对不对全凭巧合。

这个仓库对这类问题已有成熟答案。`internal/control/routes.go:13-28` 那段注释写得很清楚：`AccessMode` 的零值刻意是 `AccessUndeclared`，配 `internal/control/routes_test.go:181` 的 `TestEveryRouteDeclaresAccess` 机械兜底。License 用同一套办法：

```go
// LicenseMode 声明一个端点在 license 过期后是否还放行。
//
// 零值是 LicenseUndeclared，新加端点忘了声明会被机械检查拦下——
// 与 AccessMode 同一理由：默认放行会让降级悄悄失效，默认拒绝则会
// 让人以为忘了声明也安全，从而不去想清楚这个端点该不该拦。
type LicenseMode int

const (
    LicenseUndeclared LicenseMode = iota
    // LicenseAlways 过期后仍放行：所有读取、登录登出，
    // 以及吊销类止损操作（见设计文档 §3）。
    LicenseAlways
    // LicenseRequiresValid 过期后拒绝：签发、审批、组织与授予的写入。
    LicenseRequiresValid
)
```

`Route` 加 `License LicenseMode` 字段，现有全部路由逐条标注，新增 `TestEveryRouteDeclaresLicenseMode`。这次标注是一遍性的人工判断——正因为需要人判断，才不能交给方法推导。

**标注结果**（`LicenseRequiresValid` 的完整清单，其余一律 `LicenseAlways`）：

- `POST /api/orgs`、`PATCH /api/orgs/{id}/name`、`PATCH /api/orgs/{id}/parent`、`DELETE /api/orgs/{id}`、`PUT /api/orgs/{id}/key-holder`
- `POST /api/orgs/import/apply`
- `POST /api/grants`、`DELETE /api/grants/{id}`、`PUT /api/users/{id}/primary-org`
- `POST /api/litellm/sync`
- `POST /api/keys`、`POST /api/keys/{id}/rotate`
- `POST /api/requests`、`POST /api/requests/{id}/approve`、`POST /api/requests/{id}/reject`、`POST /api/requests/{id}/claim`

注意 `GET /api/orgs/import/preview` 是只读预览，归 `LicenseAlways`；`POST /api/keys/{id}/rotate` 归 `RequiresValid`（轮换会产生一把新凭据，是签发而非止损）。

### 4.2 判定顺序

判定塞进 `Server.enforce`，顺序是**已登录 → license → 权限**。

license 在权限之前，因为「license 已过期」比「没有权限」更能指明该做什么；而且 license 状态本来就对所有登录用户可见（§5），不存在信息泄漏。

这要求 `enforce` 改成对所有 `AccessMode` 都包一层，不再像 `internal/control/routes.go:98-100` 那样 `Access != AccessPermission` 时直接返回原处理器。

被拦时返回 **402 Payment Required**，错误码 `license_expired`，消息「授权已过期，该操作已暂停」。402 在整个仓库里没有别的用途，语义上恰好就是这件事，不会与既有的 401/403 混淆。

### 4.3 席位闸

单独一处，在 `internal/control/auth.go:124` 那次 `ByExternalID` 上。现有代码是「找到了就查禁用状态，出错且不是 `ErrUserNotFound` 就 500」，`ErrUserNotFound` 是隐式的落空分支；改成显式三分支：

```go
existing, err := a.deps.Users.ByExternalID(r.Context(), identity.Subject)
switch {
case err == nil:
    // 登录时补一次禁用检查，覆盖「刚被禁用但还没到对账周期」的窗口。
    if existing.Status != UserStatusActive {
        writeError(w, http.StatusForbidden, "user_disabled", "该账号已被禁用")
        return
    }
case errors.Is(err, ErrUserNotFound):
    // 新人开户要占一个席位。license 过期或席位已满时拒绝；
    // 已建档用户走上面的分支，不受影响。
    if err := a.deps.License.AdmitNewUser(r.Context(), time.Now()); err != nil {
        writeError(w, http.StatusPaymentRequired, "seats_exhausted", err.Error())
        return
    }
default:
    writeError(w, http.StatusInternalServerError, "internal_error", "查询用户失败")
    return
}
```

用 `writeError` 而不是重定向，跟着这个流程里已有的先例走——`user_disabled` 那条就是这么处理的。

### 4.4 LicenseGate

`internal/control/license.go`：

```go
// ActiveUserCounter 是席位闸需要的全部数据库能力。
type ActiveUserCounter interface {
    CountActive(ctx context.Context) (int, error)
}

type LicenseGate struct {
    lic   license.License
    users ActiveUserCounter
}

func NewLicenseGate(lic license.License, users ActiveUserCounter) *LicenseGate

// Status 按 now 现算当前状态（Valid 的 license 跨过到期日后返回 Expired）。
func (g *LicenseGate) Status(now time.Time) license.Status

// AllowWrite 在 license 过期时返回错误，用于 LicenseRequiresValid 端点。
func (g *LicenseGate) AllowWrite(now time.Time) error

// AdmitNewUser 判断能否为一个新人开户：过期拒绝，席位满拒绝。
func (g *LicenseGate) AdmitNewUser(ctx context.Context, now time.Time) error

// Snapshot 供 GET /api/license 使用，含实时席位占用。
func (g *LicenseGate) Snapshot(ctx context.Context, now time.Time) (LicenseSnapshot, error)
```

每个方法都显式收 `now time.Time`——测试不需要动系统时钟就能跨过到期日，也不会有时序抖动。

`postgresUserStore` 补 `CountActive`：`SELECT count(*) FROM users WHERE status = 'active'`。

## §5 控制台呈现

### 5.1 接口

新增 `GET /api/license`，`AccessAuthenticated` + `LicenseAlways`（过期后当然还得看得见）。

**不加权限门槛**：红条要对所有人显示，否则普通成员只会撞上一串没头没脑的 402，而没人告诉他发生了什么。

返回值按仓库里 view 类型的既有惯例带 json tag，走 snake_case：

```json
{
  "status": "expired",
  "customer": "某某银行",
  "expires_at": "2027-09-07T00:00:00Z",
  "seats": 200,
  "seats_used": 187,
  "days_remaining": -3
}
```

`status` 为 `trial` 时 `customer` 为空、`expires_at` 省略、`days_remaining` 省略。`seats_used` 由 `LicenseGate.Snapshot` 现查一次库；这是低频的页面级调用，不需要缓存。

### 5.2 横幅

`web/src/components/LicenseBanner.tsx`，挂在 `AppShell` 里，四种状态：

| 状态 | 呈现 |
|---|---|
| `expired` | 红色常驻条，不可关闭：「授权已于 YYYY-MM-DD 到期，管理操作已暂停；查询与吊销不受影响，AI 调用不受影响。」 |
| `trial` | 橙色条：「未配置授权文件，当前为试用模式（上限 5 席位）。」 |
| `valid` 且 `days_remaining <= 30` | 黄色条：「授权将于 N 天后到期。」 |
| `valid` 且不临期 | 不显示任何东西 |

红条后半句「AI 调用不受影响」必须写，否则运维第一反应是拔电源。

席位单独提示：`seats_used >= seats` 时补一句「席位已满，新成员将无法登录；停用离职成员可腾出席位」——把解法直接写在问题旁边，省掉一次工单。

### 5.3 前端类型与错误映射

- `web/src/lib/types.ts` 加 `LicenseInfo`
- `web/src/lib/api.ts` 加 `fetchLicense()`，并给 402 加专门映射，让被拦的写操作弹「授权已过期，该操作已暂停」，而不是通用失败提示

## §6 签发工具与私钥保管

`cmd/licensegen`，两种用法：

```bash
# 一次性：生成密钥对。公钥 base64 打到 stdout（贴进 internal/license/pubkey.go），
# 私钥写到 -out 指定的文件，权限 0600。
go run ./cmd/licensegen -genkey -out ~/airlock-license-private.key

# 日常：签发一份 license
go run ./cmd/licensegen -key ~/airlock-license-private.key \
  -customer "某某银行" -id AL-2026-0007 -seats 200 -expires 2027-09-06
```

工具自己先校验再签：`seats > 0`、`expires` 晚于今天、`customer` 与 `id` 非空。`seats: 0` 那种会锁死所有人登录的 license，**在签发端就不该造得出来**。

`-expires` 接受 `YYYY-MM-DD`，签成次日零点 UTC（§3 的排他上界）。

### 私钥处置

三条，事后无法补救，必须写进文档：

1. **私钥永不入库。** `.gitignore` 加 `*.key`；仓库里只存公钥。
2. **私钥丢失 = 再也签发不了新 license。** 已签发的仍然有效（验签只用公钥）。补救办法是换密钥对、改 `pubkey.go`、发新版二进制，并给所有现存客户重签——代价极高，所以私钥必须离线备份。
3. **换公钥是不兼容变更**：老二进制验不了新 license，新二进制验不了老 license。

### 不做的事

**不做吊销列表。** 离线部署的机器根本收不到吊销信息，做了也是摆设。到期时间是唯一的时间约束。YAGNI。

## §7 测试策略

### `internal/license`（纯函数，表驱动全覆盖）

- 合法 license 验签通过，字段解析正确
- **payload 被篡改后验签失败**——造一份合法 license，把 `seats` 从 5 改成 9999、签名原样保留，断言拒绝。**这是整套机制唯一真正承重的断言**：这条过不了，前面所有设计都是装饰
- 用错误的公钥验签失败
- `v = 2` → `ErrUnsupportedVersion`
- base64 非法、缺 `.` 分隔 → `ErrMalformed`
- `seats = 0`、`seats = -1`、`customer` 为空 → `ErrInvalidPayload`
- 到期边界两个点：`expires_at` 前一纳秒为 `StatusValid`，`expires_at` 当刻为 `StatusExpired`
- `Trial()` 返回 5 席位、零值 `ExpiresAt`、`StatusTrial`

### `internal/control`

- `TestEveryRouteDeclaresLicenseMode` 机械检查
- 过期时 `LicenseRequiresValid` 端点返回 402 `license_expired`
- 过期时 `LicenseAlways` 端点照常 200——**含 `DELETE /api/keys/{id}` 这条吊销豁免**
- 席位闸三场景：新人在席位满时被拒 402、老用户在席位满时照常登录、停用一人后新人能进
- 未配置 license 时走 5 席位试用
- `Status(now)` 在跨过到期日后从 Valid 变 Expired（同一个 gate 实例，只换 `now`）

### `cmd/licensegen`

- `-seats 0`、`-expires` 为过去日期、`-customer` 为空时报错退出，不产出文件
- 签出的 license 能被 `license.VerifyWith` 用配对公钥验通过（端到端闭环）

### 前端

- `LicenseBanner` 四种状态各自的渲染
- 席位满时的补充提示

### 不适用

**这一阶段没有组织树路径的判定面**，所以反复出现七次的「同前缀兄弟节点」陷阱（`/root/rd` 是 `/root/rd2` 的字符串前缀但不是祖先）在这里不适用。明确记下来，免得下一个人以为漏测了。

## §9 验收标准

1. 用 `licensegen` 生成密钥对与一份 200 席位、20 天后到期的 license，控制台显示黄色临期横幅，全部写操作正常
2. 换成一份昨天到期的 license 并重启，验证四件事：横幅变红条、`POST /api/orgs` 返回 402、`DELETE /api/keys/{id}` 仍返回 200、Edge 的 AI 调用不受影响
3. 篡改 license 文件任意一个字节，control **拒绝启动**并报签名错误
4. 删除 `AIRLOCK_LICENSE_FILE` 配置，control 以 trial 启动，横幅显示试用，第 6 个新用户登录被拒 402
5. 停用一个 active 用户后，第 6 个新用户能登录成功
6. `make lint` 通过（含新增的 license 包独立性检查），`make test` 全绿
