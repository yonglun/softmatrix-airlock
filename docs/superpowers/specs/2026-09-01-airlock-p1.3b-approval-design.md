# P1.3b 设计：密钥申请与提额审批流

| 项目 | 内容 |
|---|---|
| 日期 | 2026-09-01 |
| 上游依赖 | P1.2b（RBAC）、P1.2c（Org/Team 骨架）、P1.3a（密钥签发与配额下发） |
| 对应需求 | PRD FR-3.6（临时提额）、§8.4 密钥生命周期的「申请 → 审批」 |

## 1. 背景与范围

P1.3a 让密钥能被签发并真正用起来，但签发只有一条路径：**管理员直接调接口**。PRD FR-3.6 要求的是成员自助申请、管理员审批的企业流程，这正是本阶段要补的。

### 两条 PRD 事实决定了本阶段的形状

**其一，PRD §8.3 的分期说明**明确写着：P1 只覆盖 FR-3.1 的计量维度与 **FR-3.6 的审批流**；FR-3.2 三维叠加、**FR-3.5 的降级行为**、FR-3.7 两阶段预扣-结算均为 P2 交付。

**其二，这引出一个 Roadmap 没说清的问题：P1.3b 的告警由什么触发？** FR-3.5 那张表里的 80%/95% 阈值告警，需要实时知道「已花多少 / 预算多少」，而 PRD 把配额判定接管明确放在 P2——**超支告警的触发机制在 P1 阶段并不存在**。

但审批流自身就有天然、此刻就成立的通知需求：申请提交要通知审批人、批准或驳回要通知申请人、提额到期回收要通知双方。因此本阶段的通知服务于**审批事件**，不做超支阈值告警。

### 本阶段范围

- 密钥申请审批流：成员申请 → 管理员审批 → 申请人领取（签发）
- 提额审批流：成员申请提额 → 管理员审批 → 后台执行 → **到期自动回收**
- 审批事件通知：outbox + 周期重试，邮件渠道先行
- 收编两件遗留欠账（见 §7）

### 明确的范围外

| 项 | 去向 |
|---|---|
| 超支阈值告警（FR-3.5 的 80%/95%） | P2（依赖 P2 才有的用量-预算实时比对） |
| 钉钉 / 企业微信渠道 | 未排期，**待拿到真实租户**（见 D3） |
| 降级路由、三维叠加配额、两阶段预扣 | P2（PRD §8.3 已明确分期） |
| 离职对账的多身份来源协调 | 未排期，单独开阶段（见 §7） |
| 密钥轮换 | 未排期（P1.3a 探针 E 已确认 `/key/regenerate` 属 Enterprise） |

## 2. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| D1 | 通知服务于**审批事件**，不做超支阈值告警 | 超支告警需要实时的「已花/预算」比对，而 PRD 把配额判定接管放在 P2。在 P1 硬做等于提前开 P2 的头 |
| D2 | 两类申请共用一张 `requests` 表，用 `kind` 判别 + CHECK 约束强制各自的必填列 | 审批语义（谁能批、状态流转、审计留痕）两者完全相同，是逻辑的大头；用 CHECK 而非 JSONB，保留数据库级约束而不是留一个黑洞。P1.4 控制台的「我的待审批」也因此是一条查询 |
| D3 | 渠道先做邮件；`channel` 的 CHECK 目前只允许 `'email'` | 钉钉/企微在 P1.2 就因拿不到真实租户而未实测，P1.2a 验收明确写过「不在任何交付物里写支持」。把这条纪律写进数据库：在实测之前，系统物理上存不下一条声称由它们投递的记录 |
| D4 | 审批与执行分离：审批只写库，执行交给会重试的 worker | 与 P1.3a「先落库 pending 再调上游」同源。若审批同步调 LiteLLM 而上游宕机，审批人拿到 502、这次审批等于没发生，得靠人重试 |
| D5 | `requests` 表本身就是这条流程的审计轨迹 | FR-3.6 要求「申请、审批、回收全程审计」。谁申请、谁审批、何时、执行结果、何时回收全在行里，不另建审计表 |
| D6 | 到期回收用**周期扫描**，不用定时器 | 为每条批准的提额起 `time.AfterFunc`，进程一重启定时器就没了，临时提额会**静默变成永久**——这正是这类功能最不该出的错。扫描「已过期但未回收」是自愈的 |
| D7 | 通知走 outbox + 周期重试，而非尽力发送 | 在 P1.4 控制台出来之前，通知是这套流程唯一的可用性来源：审批人不看邮件就不知道有待审申请。同时天然留下「发了什么、发没发出去」的审计痕迹 |
| D8 | `new_key` 的执行是「申请人自助领取」，不由 worker 后台签发 | 见 §4，这是明文只返回一次这条约束逼出来的结构 |

## 3. 数据模型

```sql
CREATE TABLE requests (
    id              TEXT PRIMARY KEY,
    kind            TEXT NOT NULL CHECK (kind IN ('new_key','quota_bump')),
    status          TEXT NOT NULL DEFAULT 'pending'
                    CHECK (status IN ('pending','rejected','approved','executed','failed')),
    requester_id    TEXT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    org_id          TEXT NOT NULL REFERENCES organizations(id) ON DELETE RESTRICT,
    reason          TEXT NOT NULL DEFAULT '',

    -- new_key 专用
    key_name        TEXT,
    models          JSONB,

    -- quota_bump 专用
    target_key_id   TEXT REFERENCES api_keys(id) ON DELETE RESTRICT,
    bump_to_budget  NUMERIC,
    bump_expires_at TIMESTAMPTZ,
    prev_budget     NUMERIC,          -- 执行时记下原值，到期照此回收
    reclaimed_at    TIMESTAMPTZ,

    decided_by      TEXT REFERENCES users(id),
    decided_at      TIMESTAMPTZ,
    executed_at     TIMESTAMPTZ,
    issued_key_id   TEXT REFERENCES api_keys(id),
    last_error      TEXT,
    attempts        INTEGER NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),

    CHECK (
      (kind = 'new_key'    AND key_name IS NOT NULL AND models IS NOT NULL
                           AND target_key_id IS NULL)
   OR (kind = 'quota_bump' AND target_key_id IS NOT NULL AND bump_to_budget IS NOT NULL
                           AND bump_expires_at IS NOT NULL AND key_name IS NULL)
    )
);

CREATE TABLE notifications (
    id          TEXT PRIMARY KEY,
    request_id  TEXT NOT NULL REFERENCES requests(id) ON DELETE CASCADE,
    event       TEXT NOT NULL
                CHECK (event IN ('submitted','approved','rejected','executed','reclaimed')),
    channel     TEXT NOT NULL DEFAULT 'email' CHECK (channel IN ('email')),
    recipient   TEXT NOT NULL,
    subject     TEXT NOT NULL,
    body        TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'pending'
                CHECK (status IN ('pending','sent','failed')),
    attempts    INTEGER NOT NULL DEFAULT 0,
    last_error  TEXT,
    sent_at     TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`api_keys` 的既有外键 `api_keys_user_fk`（P1.3a 实施时才发现）意味着 `requester_id` 同样必须指向真实用户行，测试与验收都要先种用户。

## 4. 状态机与执行

```
pending ──reject──> rejected
   │
 approve
   │
   └──> approved ──执行──> executed
                     └─重试耗尽─> failed（仅 quota_bump）
```

「执行」由谁完成取决于 `kind`：`quota_bump` 由 worker 后台执行并在重试耗尽后转 `failed`；`new_key` 由申请人调领取接口同步完成，失败直接返回 502、申请单**停在 `approved` 等待重试**，因此 `new_key` 不会进入 `failed`。原因见下。

### 明文怎么交给申请人：一处刻意的不对称

P1.3a 定死了「`ak-` 明文只在签发响应里返回一次，库里只存哈希」。若新密钥由后台 worker 签发，就**没有响应可以承载这个明文**。因此两类申请的执行方式不同：

- **`quota_bump`**：批准后由 worker 后台执行——读当前 `max_budget` 存入 `prev_budget`，调 `/key/update` 提到 `bump_to_budget`。全程不涉及明文，适合后台做。
- **`new_key`**：批准**只是授权**，不签发。申请人凭已批准的申请单调一次领取接口，**那次调用同步走 P1.3a 的 `KeyIssuer.Issue`，明文在该响应里当场返回一次**，随后申请单转 `executed` 并记下 `issued_key_id`。

这样明文从不落盘、也不进邮件（邮件不是安全信道），完全复用 P1.3a 已验证的签发路径，不需要任何「加密暂存、取一次后清除」的托管机制。代价是新密钥要申请人自己来领——而这本就是「我的空间」该有的交互。

**一个已知的留白**：已批准但长期未领取的申请单会一直停在 `approved`。本阶段不设领取时效，P1.4 控制台把它显示出来即可；真需要过期策略时再加，现在加属于 YAGNI。

## 5. 组件与接口

| 文件 | 职责 |
|---|---|
| `internal/notify/notify.go` | `Message`、`Sender` 接口 |
| `internal/notify/smtp.go` | SMTP 实现 |
| `internal/control/requeststore.go` | `requests` 与 `notifications` 的读写 |
| `internal/control/approval.go` | 状态机、执行、到期回收 |
| `internal/control/requestapi.go` | HTTP 接口 |
| `internal/control/notifier.go` | outbox 投递 worker |

`internal/notify` 做成独立包，不依赖 `internal/control`，并加进 `make lint` 的包独立性检查——与 `internal/authz`、`internal/litellm` 同一待遇。

| 端点 | 访问要求 |
|---|---|
| `POST /api/requests` 发起申请 | `key:request`，目标取 body 的 `org_id` |
| `GET /api/requests` 列出可见申请 | 已登录，按可见范围过滤（同 `GET /api/orgs` 的先例） |
| `POST /api/requests/{id}/approve` | 已登录，**判定下沉到处理器** |
| `POST /api/requests/{id}/reject` | 已登录，**判定下沉到处理器** |
| `POST /api/requests/{id}/claim` | 已登录，**判定下沉到处理器**（只有申请人本人能领） |

后三个路径里只有 request ID，中间件拿不到它归属的节点，判定只能在处理器里做——与 `DELETE /api/keys/{id}`、`DELETE /api/grants/{id}` 是同一类既有例外，不是新开的口子。

### 权限

新增 `key:request`（`ScopeOrg`），加进 `developer` 角色。P1.2b 的隐式开发者基线（D6）因此让**任何有归属的员工都能在自己归属子树内发起申请**，符合「入职即可申请」的直觉。审批复用已有的 `key:write`（`org_admin` 已持有），不新增权限。

## 6. Worker：一个循环，三件事，外加 Nudge

后台 worker 每轮做三次廉价的库扫描：

1. 执行 `status='approved'` 的 `quota_bump`
2. 回收 `kind='quota_bump' AND status='executed' AND bump_expires_at < now() AND reclaimed_at IS NULL`
3. 投递 `notifications` 里 `status='pending'` 的记录

审批动作完成后 `Nudge()` 一下让通知尽快发出，周期扫描兜底——与 P1.2c 同步器的「写时尽力 + 对账兜底」是同一套模式，不是新机制。

**两个有界且需写明的后果**：

1. 回收时把 `max_budget` 恢复成审批时记下的 `prev_budget`。若有人在提额生效期间手工改过这把密钥的预算，回收会覆盖它。这与 P1.3a「Airlock 存意图、不做 Key 级配额漂移对账」的既定取舍一致。

2. **回收可能让密钥立即变为不可用。** 上游的判定是 `spend >= max_budget`（P1.3a 探针 H 已证实）。若用户在提额期间（5 → 50）花掉了 30，回收把预算改回 5 时 `spend=30 > max_budget=5`，该密钥**当场被 429 阻断**，直到 `budget_duration` 周期重置。这在语义上是对的——临时额度到期、且已超出基础额度——但它是一个足够锋利的边角，必须在产品文档与审批界面上讲清楚，不能让用户在生产里撞见才知道。

## 7. 收编的两件遗留欠账

### 吊销纵深对齐

`KeyIssuer.Revoke`（手工吊销）是本地标记 + 上游 `block` 两层；而离职对账走的 `PostgresKeyRevoker.RevokeByUsers` **只做本地 `UPDATE`，不封禁上游**。因为上游密钥从不离开控制面，这不是活的漏洞，但它意味着离职场景少了一层「凭据泄漏时的兜底」。

修法：给 `PostgresKeyRevoker` 注入 `LiteLLMKeyAdmin` 与 `Cipher`，吊销时逐个封禁上游（尽力而为、失败只记日志，与 `KeyIssuer.Revoke` 完全同款）。

顺带修一个相关的小疏漏：它当前的 `WHERE status = 'active'` 漏掉了 `pending`——离职用户名下正在签发中的密钥，上游可能已经建成，应一并吊销。

### LiteLLM User 同步悬案正式关闭

P1.2c 把「LiteLLM `User` 实体的同步」推给 P1.3，P1.3a 实际没做也没在范围外表里说明。**现在正式结论：不需要。**

理由：P1.3a 的密钥只绑 `team_id`，完整链路已实测跑通；成员归属由 Airlock 自己的 `primary_org_id` 管，成本归集走 Airlock 自有的用量台账（PRD §4.2「审计流从第一天起就在自己手里」）。LiteLLM 的 User 实体在 Airlock 的模型里没有对应职责。此条不再挂账。

## 8. 测试策略

| 层次 | 覆盖 |
|---|---|
| CHECK 约束（Postgres 集成） | 两类申请各自的必填列；跨类的非法组合被数据库拒绝；`channel` 只接受 `email` |
| 状态机（fake 依赖） | `pending→approved→executed`；`pending→rejected`；重复审批被拒；重试耗尽转 `failed` |
| 权限 | 无 `key:request` 不能申请；无 `key:write` 不能审批；**非申请人本人不能 claim** |
| 提额执行与回收 | `prev_budget` 被正确记录；过期的被回收、未过期的不碰、已回收的不重复回收 |
| outbox | 审批产生通知记录；投递失败重试；`Nudge` 多次合并成一轮 |
| 吊销纵深 | `RevokeByUsers` 也封禁上游，且覆盖 `pending` 状态 |
| 机械检查 | P1.2b 的两条路由检查自动覆盖新端点；包独立性检查扩到 `internal/notify` |

## 9. 验收标准

验收需要给 deploy 栈加一个 mail 容器（Mailpit 之类），使邮件是真发出去、真收得到，而不是只断言「调了 SMTP 客户端」。

1. 成员发起密钥申请 → `requests` 有 `pending` 行；审批人**在 Mailpit 里收到邮件**
2. 审批通过 → 状态转 `approved`；申请人收到邮件
3. 申请人 `claim` → **明文当场返回一次**；上游 `/key/info` 可见该密钥
4. 非申请人 `claim` 同一张单 → 403
5. 提额申请 → 审批 → worker 执行 → 上游 `max_budget` 变为新值，`prev_budget` 记录原值
6. 手工把 `bump_expires_at` 改到过去 → 下一轮扫描回收，上游 `max_budget` **恢复原值**
7. 停掉 mail 容器 → 通知留在 outbox 并重试；恢复后送达
8. 无 `key:request` 的用户发起申请 → 403
9. 离职对账吊销时上游也被 `block`（新对齐的纵深），且 `pending` 密钥一并吊销
10. `internal/edge` 33 PASS / 0 FAIL，零回归
