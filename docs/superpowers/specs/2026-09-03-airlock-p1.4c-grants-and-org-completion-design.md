## 1. 范围

这一期补上 P1.4 里最后一块**后端齐全、界面完全缺失**的能力：授权。

在此之前，要把一个人变成管理员只能直接写 SQL——P1.4a 与 P1.4b 两次验收里都得手工 `INSERT INTO role_grants`。那不是验收环境的权宜，而是产品真的没有这个入口。Roadmap 对 P1.4 的验收标准是「五类角色各自能在对应工作台完成其核心任务」，而「给人授权」正是平台管理员最核心的任务。

### 做什么

- **平台管理 → 角色与权限页**（新）：左树右表，回答「**谁对这个节点有权**」——直授 + 继承自祖先 + 全局授予，每行标明来源；授予角色、撤销直授。
- **组织与成员页补齐**：改名、移动（换父节点）、密钥边界开关；并显示**该节点的成员**（`primary_org_id` 指向此节点的用户），可加入与移出。
- 后端补三处，见 §4。

**页面归属的划分依据**：`primary_org`（人属于哪个节点）是**成员归属**，归「组织与成员」；`role_grants`（人在哪个节点有什么角色）是**授权**，归「角色与权限」。Roadmap 的页面命名本身就是这么切的，照它走。

### 明确的范围外

| 项 | 去向与理由 |
|---|---|
| LDAP 组织导入（`GET /api/orgs/import/preview`、`POST /api/orgs/import/apply`） | 预览 → 选择 → 应用是一块独立的硬骨头，混进来会让这期失焦。留下一期 |
| LiteLLM 同步状态（`/api/litellm/sync*`） | 同上，且它属于「平台运维」而非「组织与权限」 |
| 自定义角色、编辑角色的权限集 | 后端只有内置角色的只读接口，改不了 |
| 成本总览、审计检索 | 要 ClickHouse 分析接口，P1.5 |

## 2. 设计前的查证

沿用「先查证既有代码、不靠推断」的纪律。四条查证，其中两条直接决定了这一期的形状。

| # | 查证 | 对设计的影响 |
|---|---|---|
| **C1** | `ListGrantsForOrg`（`grantstore.go:186`）是**单节点**查询（`WHERE org_id = $1`），既不含祖先节点的授予，也不含全局授予（后者另有 `ListGlobalGrants`） | 「这个节点上挂了哪些授予」**不等于**「谁对这个节点有权」。照搬这个接口做页面会制造危险的错觉。直接决定 D1 |
| **C2** | `POST /api/grants` 有反提权闸：`resolver.CanGrant` 拦住「不能授予自己不持有的权限」（403 `escalation_denied`）。而 `GET /api/roles` **只返回** `{ID, Name, Description, IsBuiltin}`、**不含权限集**（P1.4a 的 C3 已经记过一次） | 前端**算不出**「我能授哪些角色」。判定只能留在服务端。直接决定 D2 |
| **C3** | `UserStore.ListActive`（`model.go:99`）已经存在，只是没有 HTTP 出口 | 「列出用户」的补口很薄：一条路由 + 一个 handler，不需要新的 store 方法 |
| **C4** | 组织页三个补齐各自都已有服务端守卫：`HandleMove` 会**再查一次目标父节点**的 `org:write`（403），`store.Move` 挡环（`ErrOrgCycle`）；`HandleSetKeyHolder` 在取消标记时若该节点下有未吊销密钥则 409 `org_has_live_keys` | 前端只需如实呈现这些错误，不必自己判定。沿用 P1.4a 的 D5 |

## 3. 关键决策

### D1：角色与权限页回答「谁对这个节点有权」，而不是「这个节点上挂了哪些授予」

页面展示**有效权限视图**：本节点直授 + 继承自祖先节点 + 全局授予，三类合成一张表，每行标注来源。

C1 揭出的问题是：只答「直授」的页面会系统性地少告诉管理员一批人，而那批人恰恰是权限最大的那批——祖先节点上的 `org_admin` 对该节点有完全权限，全局 `platform_admin` 更是对任何节点都有。管理员看着一个空荡荡的节点以为没人管，实际上有好几个人能在这里签发密钥、吊销凭据。**权限界面最不该做的事就是制造这种错觉。**

**只有直授行可以就地撤销。** 继承与全局的行显示「需在 *X* 上撤销」的说明文字，而不是按钮。这不是省事：在这一页撤销一条继承来的授予，实际改动的是**另一个节点**上的授予，会同时波及那个节点下所有其它子树。把这种操作做成就手可点的按钮，等于邀请人误伤。

空态文案定为「该节点上没有任何人有权」——因为是有效视图，这句话说得准；若换成直授视图，同一句话就是谎话。

### D2：可授角色由服务端给出

`GET /api/roles` 增加可选参数 `?grantable_at=<orgID>`，服务端用已有的 `resolver.CanGrant` 逐个角色算一遍，只返回调用者在该节点确实能授予的角色。不带参数时行为不变。

C2 决定了这一条：前端拿不到角色的权限集，本就无法自行判断。让它判断意味着把授权判定复制一份到前端——那条路 P1.4a 的 D2 已经明确否决过，理由此处同样成立。

代价是每次请求要跑 N 次 `CanGrant`（内置角色只有 6 个，可忽略）。收益是下拉里不会出现注定拿 403 的选项。

### D3：`GET /api/users` 返回全库活跃用户，不按调用者的可见子树裁剪

两个页面都要它：角色与权限页拿它把 `user_id` 还原成人名、并在授予时选人；组织与成员页拿它按 `primary_org_id` 过滤出该节点的成员。权限门槛设为 `grant:read`。

**不裁剪是有意识的选择，不是疏漏。** 按可见子树裁剪听起来更安全，实际会挡住正当操作：要把某人授权到自己的子树上，那个人此刻多半还**不在**你的子树里，甚至 `primary_org_id` 为空。企业内部控制台向「有权管理授权的人」展示员工名录是正常的。

### D4：有效权限视图用独立路由，不用查询参数

`GET /api/orgs/{id}/effective-grants`，而不是给现有的 `GET /api/orgs/{id}/grants` 加 `?effective=true`。

P1.4b 的 `?subtree=true` 之所以能做成参数，是因为**返回形状完全相同**（还是那串 `keyView`）；而有效视图要多带 `source` 与来源节点，形状不同。一个端点两种形状是坏味道。现有路由保持不动。

### D5：错误一律透传后端中文

沿用 P1.4a 的 D5。本期会真实用到的：`ErrOrgCycle`（移动成环）、403「没有在目标父节点下添加子节点的权限」、409「该节点下还有未吊销的密钥，请先吊销后再取消密钥边界标记」、403 `escalation_denied`。

## 4. 后端补口

三处。

### B1：`GET /api/orgs/{id}/effective-grants`

汇聚三类授予并标注来源。响应是新的视图类型（带 json tag，snake_case）：

| 字段 | 含义 |
|---|---|
| `id` | 授予 ID（撤销时用；仅 `direct` 行有意义） |
| `user_id` / `role_id` | 授予的主体与角色 |
| `source` | `direct` / `inherited` / `global` |
| `source_org_id` | 授予实际挂在哪个节点（`global` 时为空） |
| `created_at` | 授予时间 |

节点选择：`direct` 取 `org_id = {id}`；`inherited` 取该节点**祖先链**上的授予；`global` 取 `org_id IS NULL`。祖先链必须按分隔符匹配，不能用裸字符串前缀——见 §6 的同前缀兄弟节点。

权限沿用现有的 `GET /api/orgs/{id}/grants`（`grant:read` on `{id}`）。

### B2：`GET /api/roles?grantable_at=<orgID>`

不带参数时返回全部角色（行为不变）。带参数时对每个角色调一次 `resolver.CanGrant(调用者, roleID, orgID)`，只返回为真的。

### B3：`GET /api/users`

复用 `UserStore.ListActive`，返回 `[]*User`。`User` 结构体没有 json tag，因此序列化为 **PascalCase**——与 `whoami` 里的 `user` 一致，前端类型可直接复用 P1.4a 已定义的 `User`。权限门槛 `grant:read`（全局目标）。

> **wire 形状不一致仍然存在**：`User`/`Org`/`RoleGrant` 是 PascalCase，带 json tag 的视图类型（`keyView`、`requestView`、本期新增的有效授予视图）是 snake_case。P1.4a 已记为遗留事项，本期不改——统一它要动 P1.2a/b 的处理器与测试。前端 `types.ts` 继续如实适配。

复用 P1.4b 抽出的 `OrgTree`。

### 角色与权限页（`/platform/grants`）

左侧 `OrgTree`，右侧随选中节点变化：

- `[授予角色]` 按钮 → `GrantModal`：人选自 `GET /api/users`（带搜索），角色选自 `GET /api/roles?grantable_at=<选中节点>`
- `GrantsTable`：用户、角色、**来源**、授予时间、操作
  - 来源用 Tag 区分「直授」「继承自 *X*」「全局」
  - **仅 `source === 'direct'` 的行渲染「撤销」按钮**；其余行渲染「需在 *X* 上撤销」的说明文字
- 空态：「该节点上没有任何人有权」

### 组织与成员页（`/platform/orgs`，补齐）

选中节点后右侧多出两块：

- **节点属性**（`OrgNodeProps`）：名称 + 改名、父节点下拉 + 移动、密钥边界开关
- **成员**（`OrgMembers`）：列出 `primary_org_id` 指向该节点的用户（姓名、邮箱、状态），可加入（选人 → `PUT /api/users/{id}/primary-org` 带 `org_id`）、可移出（同一接口带 `org_id: null`）

**一处要如实标注的不对称**：`PUT /api/users/{id}/primary-org` 的路由用 `TargetFromBody("org_id")` 取判定目标。把人**移进**某节点只需该节点的 `member:assign`；而**移出**（`org_id` 传 `null`）时目标退化为 nil，判定变成**全局** `member:assign`。这是既有路由的行为，本期不改（改它要动权限语义，超出范围），但界面上要让这个 403 的原因说得通，不能让人对着按钮困惑。

## 6. 测试策略

沿用 P1.4a/b 的三层：Go 单测 / 集成测试（真实 Postgres）、前端 Vitest（纯逻辑与条件渲染）、手工端到端验收。不引入 Playwright。

**Go 侧**

- 有效权限查询：直授 / 继承 / 全局三类都出现且来源标注正确；空节点返回空切片
- **同前缀兄弟节点**：`/root/rd` 的有效视图里不能出现挂在 `/root/rd2` 上的授予。这是本项目**第六次**专门测这个陷阱（前五次：P1.2b 权限判定、P1.3b 审批人查找、P1.3c 子树吊销、P1.4a 待审列表、P1.4b 子树密钥查询）。祖先链匹配必须带分隔符
- `?grantable_at`：platform_admin 拿到全部；只在某节点持 `org_admin` 的人**拿不到** `platform_admin`；不带参数行为不变
- `GET /api/users`：返回活跃用户；无 `grant:read` → 403
- 路由机械检查：三条新路由入表，`Handler()` 不 panic

**前端 Vitest**

- `userLabel` / `byID` 纯函数
- **撤销按钮只在 `source === 'direct'` 的行出现**——这是安全相关行为，不是样式细节，值得一条测试钉住

## 7. 验收标准

对真实运行的 Postgres + Casdoor + control 完整链路验证，每项记录真实输出。

1. 有效权限视图里直授、继承、全局三类来源齐全且标注正确
2. **同前缀兄弟节点的授予不混入**（第六次踩这个陷阱的证据）
3. 只有直授行有撤销按钮；撤销后该行消失
4. 以 org_admin 身份，可授角色下拉**不含** `platform_admin`
5. 越权授予直接打接口 → 403 `escalation_denied`（证明下拉过滤只是便利，闸在服务端）
6. 组织节点改名成功
7. 组织节点移动：成功一次；移到自己子树内 → 挡住；移到无权的父节点 → 403
8. 密钥边界开关：标记成功；该节点下有未吊销密钥时取消 → 409 并显示后端中文
9. 成员加入该节点、从该节点移出
10. `internal/edge` 33 PASS / 0 FAIL，零回归

### 操作纪律

- 手工 E2E 与 `make test` **不能共用同一个数据库**（P1.3b 踩过）。一旦启动 control 开始手工验收，就不再跑 `go test`，直到全部手工步骤记录完毕。
- **移动与删除节点会打乱夹具**，验收顺序上把第 7 项排在第 1–5 项之后。本期没有 P1.4b 那种「必须排在最后」的全局破坏性操作。
