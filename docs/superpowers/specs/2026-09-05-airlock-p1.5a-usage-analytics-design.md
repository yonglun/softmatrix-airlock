## 0. 为什么 P1.5 要拆

Roadmap 的 P1.5 装着三块彼此独立的东西：**分析与审计**、**交付包**（docker-compose、离线镜像、安装脚本、部署与运维手册）、**License 校验**。任何一块单独交付都成立，三者没有代码耦合，硬做成一期会让设计文档与验收同时失焦。

本文档只覆盖**分析与审计**。交付包与 License 拆到 P1.5b。

分析与审计**必须在同一期**：它们读同一张 `usage_records` 表、共用同一套 ClickHouse 读取层，拆开会把接入工作做两遍。

## 1. 范围

### 做什么

- **控制面首次接入 ClickHouse 读取层**：`internal/usage` 增加只读的 `Reader`（该包今天只有 `Sink`）
- **用量与成本报表接口**：按组织 / 成员 / 模型 / 时间四个维度聚合下钻
- **审计检索接口**：按时间、组织、成员、模型、状态过滤调用流水
- **成本总览页**（成本财务工作台）
- **审计检索页**，点亮至今从未出现的**安全合规工作台**

| 项 | 理由 |

## 2. 设计前的查证

沿用「先查证既有代码、不靠推断」的纪律。四条查证，其中第一与第四条直接改变了设计。

| # | 查证 | 对设计的影响 |
|---|---|---|
| **C1** | `cost:read_all` 与 `audit:read` **都是 `ScopeGlobal`**（`permission.go:69-70`），全库**没有任何按节点的成本权限**；而成本财务工作台的可见条件是「在任意位置持有 `key:write`」（`workbench.go:29`），因此**每个 org_admin 都看得到这个工作台** | 若成本页只认全局 `cost:read_all`，org_admin 点进去必然 403——正是 P1.4a D3 明令要避免的「空壳工作台」，而且他也无从知道自己部门花了多少钱。直接决定 D1 |
| **C2** | `usage_records` 维度齐全（`org_id`/`user_id`/`key_id`/`provider`/`model`/四类 token/`cost_micro`/`status_code`/`latency_ms`/`ttft_ms`/`stream`/`error_type`），按月分区、`ORDER BY (org_id, ts, request_id)` | 报表与审计读同一张表、共用读取层；`org_id` 是排序键首列，**按组织过滤天然走主键前缀** |
| **C3** | 控制面**完全没有 ClickHouse 连接**，`internal/usage` 只写不读（只有 `NewClickHouseSink`/`InsertBatch`/`Close`）；`orgstore.go:259` 还留着一句「控制面因此完全不需要 ClickHouse 连接」。`CLICKHOUSE_DSN` 已在 `config.go:18/50`，只是 `RunControl` 从没用过 | 这一期会推翻那句注释。接入是加连接与读取层，不用动配置层。注释要同步订正 |
| **C4** | **内置 `finops` 角色只有 `cost:read_all` + `org:read`，没有 `key:write`** | 结合 C1：**持 `finops` 角色的人今天根本看不到成本财务工作台**，而看得到的 org_admin 反而没有成本权限。这是一个既存缺陷，本期顺带修掉 |

## 3. 关键决策

### D1：新增按节点的 `cost:read`；`audit:read` 维持全局

新增 `cost:read`（`ScopeOrg`），加进内置角色 `org_admin` 的权限集。`cost:read_all`（`ScopeGlobal`）保留原义：看全公司。

成本接口的判定：

- 持全局 `cost:read_all` → 不限范围
- 否则取 `Scopes(cost:read)` 的节点列表 → 只能看这些节点的子树
- 两者皆无 → 403

**`audit:read` 不动，维持 `ScopeGlobal`。** 审计是合规职能，默认不该让每个部门管理员翻全司调用流水；`security_officer` 本来就是全局角色。成本与审计在这里刻意不对称，理由是两者的性质不同——成本是部门负责人日常要看的经营数据，审计是合规调查工具。

内置角色的权限集由 `SyncBuiltinRoles` 在每次启动时幂等同步，因此改 Go 注册表即可，不需要迁移脚本。

### D2：工作台规则同步修正

```
成本财务  requires: key:write            →  key:write | cost:read | cost:read_all
安全合规  （今天整个不出现）              →  requires: audit:read
```

第一条顺带修掉 C4 那个既存缺陷：`finops` 角色的人从今往后看得到成本财务工作台。第二条让安全合规工作台第一次出现，且只对真正持有审计权限的人出现——不产生空壳工作台，与 P1.4a D3 一致。

### D3：读取层放在 `internal/usage`，并加一条边界检查

`Reader` 与既有的 `Sink` 同包：`usage_records` 的结构知识该集中在一个包里，而 `internal/usage` 目前只依赖 `internal/pricing`，是干净的数据层。

同时给 `make lint` 加一条检查，保持 `internal/usage` 不依赖 `internal/control` 与 `internal/edge`——与既有的「authz / litellm / notify 包的独立性」检查同一风格。没有这条约束，一个只写数据层很容易在后续被反向拖进业务依赖。

### D4：子树过滤在 Postgres 侧解析，再交给 ClickHouse

`usage_records` 只有 `org_id`，没有路径——路径是 Postgres 的知识。判定链是：

```
Scopes(cost:read) → 节点列表 → OrgStore.Subtree(每个节点) → org_id 集合 → ClickHouse 的 org_id IN (...)
```

**复用既有的 `OrgStore.Subtree`**（`orgstore.go:137`），它已经用了带分隔符的安全前缀匹配（`path = $1 OR path LIKE $1 || '/%'`）。同前缀兄弟节点的陷阱在这条路径上**已经被处理过**，本期是复用而不是重造；测试的作用是钉住这个性质，而不是发现它。

**要如实说的伸缩上界**：子树很大时 `IN` 列表会很长（几千个节点就是几千个 ID）。本期规模可接受，`org_id` 又是排序键首列、过滤走主键前缀。但这是已知边界——真到那个量级时正确的做法是往 ClickHouse 冗余一列 path，而不是继续加长 `IN`。

### D5：时间范围必须有界

缺省最近 7 天；跨度上限 92 天（一个季度），超出返回 400。

ClickHouse 上的无界扫描要付真金白银的代价，这道闸放在入口，而不是指望调用方自觉。上限取 92 天是因为它覆盖「看上个季度」这个最常见的长跨度需求，同时把单次查询的分区数限制在 4 个以内（表按月分区）。

### D6：CSV 由服务端生成，导出的是全量筛选结果

两个接口都支持 `?format=csv`，返回 `text/csv` 与 `Content-Disposition` 附件头。

不采用「前端把已加载的 JSON 拼成 CSV」：那样只能导出当前这一页，与「导出去自己分析」的用意相悖。前端只负责把当前筛选条件拼成同一个 URL 再加 `format=csv`，同源加 HttpOnly cookie 会自动带上凭据。

CSV 同样受 D5 的时间跨度上限约束——导出不是绕过限制的后门。

### D7：ClickHouse 是可选依赖

`CLICKHOUSE_DSN` 为空时控制面照常启动，这两个接口返回 503「用量分析未启用」。

与既有的「未配 `LITELLM_MASTER_KEY` 则同步 no-op、状态接口回答未启用」是同一个模式。与 `AIRLOCK_ENCRYPTION_KEY` 那种「不配就拒绝启动」的区别在于：加密是签发的正确性前提，分析是可选功能。这也让 P1.5b 的最小部署不被迫捆上 ClickHouse。

## 4. 后端：读取层与接口

### 4.1 `internal/usage` 新增 `Reader`

只读，与 `Sink` 用同一个 ClickHouse 驱动。对外暴露两组查询：

**聚合查询**

| 入参 | 含义 |
|---|---|
| `From` / `To` | 时间范围，必填且有界（见 D5） |
| `GroupBy` | `org` / `user` / `model` / `day` 之一 |
| `OrgIDs` | 空表示不限范围；非空表示只统计这些 org_id |

返回行：维度值、请求数、输入 token、输出 token、成本（`Micro`）。

**明细查询（审计）**

| 入参 | 含义 |
|---|---|
| `From` / `To` | 同上 |
| `OrgID` / `UserID` / `Model` | 各自为空表示不过滤 |
| `OnlyErrors` | 为真时只返回 `status_code >= 400` |
| `Limit` / `Offset` | 翻页，`Limit` 有硬上限 |

返回行：时间、request_id、org_id、user_id、key_id、model、状态码、耗时、ttft、四类 token、成本、error_type。

### 4.2 两个接口

```
GET /api/usage/summary?from=&to=&group_by=org|user|model|day&org_id=&format=csv
GET /api/audit/records?from=&to=&org_id=&user_id=&model=&only_errors=&limit=&offset=&format=csv
```

- **成本接口**：`AccessAuthenticated`，判定下沉到处理器（D1 的三分支）。带 `org_id` 参数时进一步收窄到该子树，但收窄结果必须仍在调用者的可见范围内
- **审计接口**：`AccessPermission` + `audit:read` + `TargetGlobal()`，中间件即可判完，处理器不再重复判定

金额一律以 `Micro` 传输（`1 Micro = 1e-6 元`），换算成元由前端做——服务端不做四舍五入，避免多处各舍一次导致对不上账。

**成本总览页**：时间范围（预设「最近 7 天 / 30 天」+ 自定义）、维度切换（组织 / 成员 / 模型 / 按天）、聚合表（维度值、请求数、输入 token、输出 token、成本）、导出 CSV。

维度值要还原成人话：组织维度用 `/api/orgs` 换成节点名；成员维度**复用 P1.4c 建的 `/api/users` 与 `lib/users.ts` 的 `userLabel`**——那两样正是为「把 ID 还原成人名」造的，这里是它们的第二个消费者。

**审计检索页**：过滤条件（时间范围、组织、成员、模型、只看失败）、明细表（时间、组织、成员、模型、状态码、耗时、token、成本）、翻页、导出 CSV。

**新工作台**：`security` 的 id 必须与后端 `workbench.go` 的常量一致——服务端决定「显示哪些」，前端只决定「显示成什么样」，这是 P1.4a D2 定下的分工。

**错误处理**：沿用 P1.4a D5，后端的中文错误原样透传。本期会真实用到的：时间跨度超限（400）、无成本权限（403）、用量分析未启用（503）。

## 6. 测试策略

沿用 P1.4a/b/c 的三层：Go 单测与集成测试、前端 Vitest、手工端到端验收。不引入 Playwright。

**Go 侧**

- `Reader` 的聚合与过滤：四个维度各自分组正确；时间范围边界；`org_id IN` 过滤生效。**对真实 ClickHouse 测**——先插入几条已知记录再断言聚合结果，这是唯一能证明 SQL 写对的方式
- 时间范围守卫：缺省 7 天；跨度超过 92 天 → 400
- 成本接口的三种可见性：全局 `cost:read_all` 不限范围；只持节点 `cost:read` 只看到自己子树；两者皆无 → 403
- **同前缀兄弟节点**：`cost:read` 授在 `/root/rd` 的人看不到 `/root/rd2` 的成本——**第七次**测这个陷阱。这次靠复用 `OrgStore.Subtree`，测试是钉住性质而非重新实现
- CSV 输出：`Content-Type`、`Content-Disposition`、表头与行数
- `CLICKHOUSE_DSN` 未配置时两个接口回 503，且控制面照常启动
- 权限注册表：`cost:read` 是 `ScopeOrg`；`org_admin` 内置角色含 `cost:read`
- 工作台规则：持 `cost:read_all` 但无 `key:write` 的人看得到成本财务（C4 的修复）；持 `audit:read` 的人看得到安全合规；两者皆无的 org_admin 看不到安全合规
- 路由机械检查覆盖两条新路由；`Handler()` 不 panic

**前端 Vitest**

- `money.ts`：Micro → 元的换算与格式化（含 0 与大数）
- `analytics.ts`：导出 URL 拼装——筛选条件必须原样带进 `format=csv` 的 URL，漏掉任何一个条件都会导出成与页面不一致的数据

## 7. 验收标准

对真实运行的 Postgres + ClickHouse + Casdoor + Edge + control 完整链路验证，每项记录真实输出。

1. 经 Edge 打出真实调用后，四个维度的报表数字与直接查 ClickHouse 的结果一致
2. 时间范围守卫：缺省 7 天生效；跨度 93 天 → 400
3. 全局 `cost:read_all` 看到全部组织的成本
4. 只在某节点持 `cost:read` 的人只看到自己子树的成本
5. **同前缀兄弟节点的成本不串台**（第七次踩这个陷阱的证据）
6. 既无 `cost:read` 也无 `cost:read_all` → 403
7. CSV 导出的内容与页面一致，且是**全量筛选结果**而非当前页
8. 审计检索的过滤（组织 / 成员 / 模型 / 只看失败）与翻页正确
9. 安全合规工作台按 `audit:read` 出现或不出现；**持 `finops` 角色的人终于看得到成本财务工作台**（C4 的修复证据）
10. `internal/edge` 33 PASS / 0 FAIL，零回归

### 操作纪律

- 手工 E2E 与 `make test` **不能共用同一个数据库**（P1.3b 踩过）。启动 control 开始手工验收后就不再跑 `go test`，直到手工步骤全部记录完毕。
- **本期额外一条**：验收要先造真实用量数据，**产生数据的那几次 Edge 调用必须在报表验收之前做完**。中途再打调用会让已经记录下来的数字对不上——这与 P1.4c 记下的「验收步骤之间会互相消费夹具」是同一类坑，只是这次被消费的是「数字的确定性」。
