## 1. 范围

### 做什么

- Next.js + TypeScript 骨架，静态导出后嵌进 Go 二进制，由 `control` 同源服务。
- 登录态：SPA 启动探测 `whoami`，未登录跳既有的 Casdoor 流程，登录后回到原路径。
- 布局与四工作台切换，可见性由服务端判定。
- 三个真实页面打通端到端：组织与成员、我的申请、提额审批。
- 补两处后端：`whoami.workbenches`、`GET /api/requests/to-approve`。

### 明确的范围外

| 项 | 去向与理由 |
|---|---|
| 平台管理的其余页面（模型供应商、模型池、SSO、License、总览） | P1.4b 及以后。它们**今天没有任何后端接口**，本期做不了端到端 |
| 我的密钥、我的用量与余额、模型试用台 | P1.4b/P1.5。「我的密钥」还需要先补 `GET /api/keys/mine`——现有的 `GET /api/orgs/{id}/keys` 是按节点查且要 `key:read`，普通开发者既不知道查哪个节点也多半没有该权限 |
| 成本总览、配额策略 | P1.5（要 ClickHouse 分析接口） |
| 安全合规工作台 | 本期整个不出现，见 D3。审计检索要等 P1.5 |
| SSR / 服务端组件 | 见 D1。静态导出不提供 |
| TanStack Query 等数据层 | 未排期。三个页面看不出模式，等页面多起来再定 |
| i18n 库 | 未排期，见 D6 |
| Playwright 自动化 E2E | 未排期，见 D7 |

## 2. 设计前的查证

本阶段不涉及 LiteLLM，因此没有上游探针；但同样沿用「先查证既有代码、不靠推断」的纪律。四条查证直接改变了设计：

| # | 查证 | 对设计的影响 |
|---|---|---|
| **C1** | `airlock_session` 是 **HttpOnly** cookie，由 `control` 在自己 origin 上下发（`auth.go:168`）；`sanitizeRedirect`（`auth.go:231`）**只接受同源绝对路径**，`//host` 与外部 URL 一律打回 `/` | 前端不可能跑在另一个 origin 上直连 `control` —— 登录回跳根本回不来。直接决定 D1 |
| **C2** | `whoami` 的 `global_permissions` 用 `resolver.Permissions(ctx, s, nil)` 算；target 为 nil 时**只返回全局授予的权限**，隐式基线也被跳过（`resolver.go:118`） | 只在某节点持 `org_admin` 的用户，`global_permissions` 是**空数组**。用它判定工作台会对最需要平台管理的人隐藏掉它。直接决定 D2 |
| **C3** | `GET /api/roles` 只返回 `{ID, Name, Description, IsBuiltin}`，**不含权限集** | 前端无法自行把角色映射成权限，判定只能放服务端。佐证 D2 |
| **C4** | `GET /api/requests` 只返回「我发起的」（`requestapi.go:127` 调 `ListByRequester`）；`RequestStore` 没有任何审批人视角的查询 | 「提额审批」页**没有后端**。P1.3b 当时明确写着这笔留给 P1.4，本期必须补上。见 §5.2 |

另有一条影响范围的观察：查完 31 条现有路由后，四工作台里**接口齐全的只有四块**——组织与成员、角色与权限、虚拟密钥、申请与审批。模型供应商、模型池、成本总览、审计检索、试用台全部没有后端。这是本期只做三个页面的根据。

## 3. 关键决策

### D1：静态导出，嵌进 Go 二进制，单一 origin

`next build` 以 `output: 'export'` 产出纯静态文件，经 `//go:embed` 打进二进制，`control` 同时服务页面与 API。

考虑过另外两种：**Next.js 自带 Node 服务当 BFF**、**前面架反向代理**。两者都能保住同源，也都能保留 SSR 与服务端组件。否决它们的理由是同一条：PRD 在技术选型里两次把「单二进制交付、私有化部署友好」列为 Go 的选型理由，P1.5 还要求在**完全无外网**的机器上两小时内装完。多一个 Node 运行时或多一层代理配置，都是砸在这条主张上的成本。

而 SSR 在这里换来的东西很薄：控制台是登录后的内部管理界面，没有 SEO 需求，首屏时间也不是卖点。

**代价要如实说**：放弃了服务端组件与 middleware。若将来出现公开页面或极重的首屏，需要迁移到 B/C 方案——那时从 A 迁出去是可行的，反过来从 B 退回 A 才更难。

### D2：工作台可见性由服务端判定，`whoami` 增加 `workbenches`

C2 与 C3 合起来堵死了前端自行判定：`global_permissions` 会漏掉节点级授予，而 `/api/roles` 又不给权限集。

考虑过让 `/api/roles` 返回权限集、由前端推导，否决理由是它把「沿祖先链取并集」这套判定复制进 TypeScript。这个项目一直把 `authz` 包的注册表当作权限集的唯一真相来源——`SyncBuiltinRoles` 的注释就是这么写的，`ValidatePermissions` 还会在启动时拒绝未注册的权限。劈成两半必然漂移。

服务端用既有的 `resolver.Scopes(ctx, s, perm) (global bool, nodes []string, err)` 回答「这个用户在**任意位置**持有这条权限吗」。必须是「任意位置」：只管一棵子树的组织管理员，正是平台管理的目标用户。

### D3：工作台只在「其中有本期已实现、且该用户能用的页面」时才出现

这条规则替代了「工作台 → 权限集合」的朴素映射，消掉一个否则一定会踩的坑：若把平台管理定义成「`org:write` 或 `grant:write` 或 `key:write` 或 `platform:configure` 任一」，一个只有 `key:write` 的人会看到平台管理、点进去却只有一个 403 的组织页——空壳工作台。

让可见性严格等于「有页面可用」，本期的映射就是：

| 工作台 | 本期页面 | 出现条件 |
|---|---|---|
| 我的空间 | 我的申请 | 恒可见（登录即可） |
| 平台管理 | 组织与成员 | 任意位置持有 `org:write` |
| 成本财务 | 提额审批 | 任意位置持有 `key:write` |
| 安全合规 | —— | 本期不出现 |

代价是这张表随 P1.4b/c 加页面要跟着长。这是它本来就该有的样子，且只在 `internal/control/workbench.go` 一处。

安全合规本期整个不出现：与其给一个点进去空无一物的 tab，不如等 P1.5 有了审计检索再放出来。

### D4：演示动线用 `new_key` 而不是 `quota_bump`

`quota_bump` 需要一把已存在的密钥作 `target_key_id`，而「我的密钥」页不在本期范围内。`new_key` 不依赖任何前置数据，且恰好把最有意思的交互逼出来：明文只返回一次，领取后再也拿不到。

PRD 的「我的空间」导航项叫「申请提额」，本页实际覆盖的是 `new_key` 申请，因此命名为「我的申请」。这个偏差在此记录，P1.4b 补上 `quota_bump` 入口后可以合并。

### D5：错误提示直接用后端返回的 `message`

后端统一返回 `{"error":{"code":"...","message":"..."}}`，而那些 message 本来就是写给人看的中文（「该节点下还有子节点」「共存窗口超过上限（最长 30 天）」）。前端只对 `401` 做特殊处理（跳登录），其余一律原样显示 `message`。

不在 TS 里维护一份平行文案表：那样文案会在两处漂移，而后端那份是随业务逻辑一起改的、更不容易忘。

### D6：不引入 i18n 库

PRD 要求「界面中文优先，架构上预留多语言能力」。本期的兑现方式是：antd 上 `zh_CN` 语言包，用户可见文案集中在一个模块里、不散落进组件内部。这就是那个「预留」——真要加第二语言时，替换的是这一个模块。

现在装 next-intl 之类是纯成本：它要求的目录结构与路由前缀会立刻影响每一个页面，而第二语言在可预见的排期里根本不存在。

### D7：不引入 Playwright

本期的自动化测试花在真有分支的地方：Go 侧的嵌入接缝与工作台映射、前端的错误映射与路由守卫。浏览器端到端仍走既有的手工验收并记录进 `findings/`。

Playwright 值得做，但它要拖进一整套浏览器工具链（下载 Chromium，与「完全无外网」的交付环境有张力），而这一期真正要回答的是「骨架能不能立起来」——那件事手工看一眼比写自动化快得多。等页面多起来、回归成本真的显现时再引入。

## 4. 架构与交付形态

```
web/                        前端源码
  next.config.ts            output:'export'；dev 期 rewrites 代理 /api /auth → :8081
  src/app/                  App Router
  src/lib/                  api.ts（fetch 封装）、session.tsx（whoami context）
  dist/                     构建产物；提交 .gitkeep，内容进 .gitignore
  embed.go                  package web，//go:embed all:dist
```

`internal/control` 新增 `static.go`，从 `web` 包拿到 `fs.FS` 并注册兜底路由。

### 三个必须处理的接缝

**构建自举。** `//go:embed` 要求目标在编译期存在，而 `dist/` 是构建产物、进 `.gitignore`。目录为空时 `go build ./...` 会直接失败，新克隆的仓库编译不过。做法：提交 `web/dist/.gitkeep`（`all:` 前缀会纳入点开头的文件，因此 embed 至少匹配到一个），同时 `control` 启动时检查 FS 里有没有 `index.html`——没有就打一条明确的 WARN，并对页面请求回一句「控制台未构建，请先执行 `make console`」，而不是让人对着莫名其妙的 404 排查。`make build` 改为先 `make console` 再 `go build`。

**SPA 深链回落。** 注册兜底路由：命中真实静态文件就发文件，否则回 `index.html`。

这里有两处必须按实测结果来写，写计划时对 `net/http.ServeMux` 跑了一次探针，两条都推翻了先前的直觉：

- **兜底必须是不带方法的 `"/"`，不能是 `"GET /"`。** `Handler()` 里已有 `mux.Handle("/api/", ...)`，而 `"GET /"` 与 `"/api/"` 互相重叠又互不包含，Go 1.22 的 ServeMux 会在**注册时直接 panic**：`GET / matches fewer methods than /api/, but has a more general path pattern`。改成方法无关的 `"/"` 后，`"/api/"` 是它的严格子集，冲突消失。这是个会让服务起不来的坑。
- **拼错的 `/api/xxx` 不会掉进兜底。** 外层 mux 上的 `"/api/"` 会先接住它，再进内层 mux——内层没匹配就回 Go 默认的 `404 page not found`（text/plain）。所以不存在「API 路径拿到 HTML」这回事。真正的问题小得多：那个 404 不是项目统一的 `{"error":{...}}` 形状，前端 `api.ts` 解析会拿到意外结构。修法是在**内层** mux 注册一条方法无关的 `"/api/"` 兜底返回 JSON 404；实测它既能接住拼错的路径与用错的方法（`DELETE /api/orgs`），也不会抢走更具体的真实路由。

**开发期。** `next dev` 跑 :3000，用 `next.config` 的 rewrites 把 `/api/*` 与 `/auth/*` 代理到 :8081。这不只是图方便：登录回调走 `sanitizeRedirect`，它只吐同源**路径**、不带主机名；不代理的话登录完会落在 :8081 而不是 :3000，整个流程断掉。

## 5. 后端补口

### 5.1 `whoami.workbenches`

`internal/control/workbench.go` 放 D3 的映射与判定：

```go
// Workbenches 返回该用户可见的工作台列表。
//
// 判定口径（设计文档 D3）：一个工作台只在「其中至少有一个本期已实现、
// 且该用户有权使用的页面」时才出现——可见性严格等于「有页面可用」，
// 因此不会出现点进去只有 403 的空壳工作台。
func Workbenches(ctx context.Context, r *authz.Resolver, s authz.Subject) ([]string, error)
```

用 `resolver.Scopes` 判断「任意位置是否持有」。`whoami` 的响应增加 `workbenches` 字段（纯增量，不动既有字段）。

### 5.2 `GET /api/requests/to-approve`

C4 发现的缺口，也是 P1.3b 主动欠下、点名留给 P1.4 的那笔。按当时定的口径「复用 `GET /api/orgs` 的先例、按可见范围过滤」：

- `resolver.Scopes(ctx, s, PermKeyWrite)` 拿到 `(global, nodes)`
- `global` 为真 → 返回全部 `pending`
- 否则 → 返回 org 落在这些节点**子树内**的 `pending`

`RequestStore` 增加 `ListPendingForOrgPaths(ctx, paths []string) ([]*Request, error)`。

**子树匹配必须加分隔符再比前缀**：`/root/rd` 是 `/root/rd2` 的前缀，但 `rd2` 不在 `rd` 的子树里。这个陷阱前三次分别出现在 P1.2b 的权限判定、P1.3b 的审批人查找、P1.3c 的子树吊销，这是第四次。

单开一条路由而不是给 `GET /api/requests` 加 query 参数，是为了让既有的路由机械检查（`TestEveryRouteDeclaresAccess`、`TestDefaultRoutesCoverAllOrgEndpoints`）照常覆盖它。声明为 `AccessAuthenticated`，过滤在处理器内做——与 `GET /api/orgs`、`GET /api/requests` 同一类。

## 6. 前端结构

**登录态**：SPA 启动打 `GET /api/whoami`。200 就把用户与 `workbenches` 放进 React context；401 就跳 `/auth/login?redirect_to=<当前路径>`。前端从不碰 cookie（HttpOnly，本来也碰不到），"没登录"这个判断完全由那次 401 给出。

**路由守卫**：用户手敲一个自己没有的工作台路径时，重定向到他第一个可用的工作台，而不是白屏。

**三个页面**：

| 工作台 | 页面 | 动作 | 用到的接口 |
|---|---|---|---|
| 平台管理 | 组织与成员 | 树展示、建、改名、移动、删 | `GET/POST /api/orgs`、`PATCH .../name`、`PATCH .../parent`、`DELETE /api/orgs/{id}` |
| 我的空间 | 我的申请 | 提交 `new_key`、列出我的、领取 | `POST /api/requests`、`GET /api/requests`、`POST /api/requests/{id}/claim` |
| 成本财务 | 提额审批 | 待审列表、批准、驳回 | `GET /api/requests/to-approve`（新增）、`POST .../approve`、`POST .../reject` |

**组件库 Ant Design**：这一期要的树（可展开、可移动）、表格（分页、展开行）、表单（校验）它都开箱即用，`zh_CN` 是官方内置。选它而不是 shadcn/ui 的理由是本期目标是把骨架打通、不是做视觉差异化；shadcn 需要自己攒树与表格，那份成本与"验证骨架"这个目标无关。视觉差异化更适合等页面齐了统一做主题。

## 7. 测试策略

**Go 侧**（进现有 `make test`）：

- 嵌入接缝：深链回落到 `index.html`；`/api/orgs` 没被静态处理器抢走；**拼错的 `/api/xxx` 与用错方法的 `DELETE /api/orgs` 都返回统一形状的 JSON 404**；`dist` 缺 `index.html` 时给出明确提示。另外钉一条「`Handler()` 不 panic」的测试——兜底路由若被写成 `"GET /"`，服务在注册路由时就会崩，这条测试会当场抓住。
- 工作台映射：只在某节点持 `org_admin` 的用户能看到平台管理（正是 `global_permissions` 会漏掉的情形）；只有隐式基线的开发者只看到我的空间；安全合规对谁都不出现。
- `to-approve` 的可见范围：**同前缀兄弟节点不误伤**（`rd2` 的审批人看不到 `rd` 的申请单）。

**前端**（Vitest + React Testing Library）：工作台切换按 `whoami.workbenches` 渲染、访问无权工作台时的重定向、`api.ts` 的错误映射（401 跳登录 / 其余原样显示后端 message）、提交表单的校验。

**手工 E2E 验收**，记录进 `findings/`。沿用既有纪律：手工验收期间不跑 `go test`——`cleanTables` 会把手工搭的数据清掉。

## 8. 验收标准

对真实运行的 Postgres + Casdoor + control 完整链路验证：

1. 单二进制启动后访问 `:8081`，未登录 → 跳 Casdoor
2. 登录后回到**原路径**（深链也回对地方，验证 `redirect_to`）
3. 平台管理员看到 3 个工作台；**只在某节点持 `org_admin` 的用户同样能看到平台管理**；只有隐式基线的开发者只看到我的空间
4. 组织与成员：建 / 改名 / 移动 / 删；删有子节点的节点 → 409，且页面显示的就是后端那句中文
5. 我的申请：提交 `new_key` 申请 → 列表里出现 pending
6. 提额审批：审批人在待审列表看到这张单子 → 批准
7. 回我的申请：领取 → `ak-` 明文显示一次；刷新后不再出现
8. 无关子树的审批人**看不到**这张单子
9. 深链刷新 `/platform/orgs` 不 404；拼错的 `/api/xxx` 返回统一形状的 JSON 404
10. `make test` 全绿（Go + 前端）；`internal/edge` 零回归

## 9. 规模预估

14–17 个实施任务。比 P1.3c（14 个）略大，多出来的是前端脚手架与三个页面；但后端只补两处，没有新表、没有迁移。
