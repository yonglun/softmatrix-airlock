## §0 开工前的实测

以下每一条都在本机验证过，不是推断。

### 0.1 架构不匹配是本阶段最大的坑

构建机是 `arm64`（`uname -m`），本地已拉的六个镜像全部是 arm64（`docker image inspect --format '{{.Architecture}}'`）。直接 `docker save` 出来的 tar **在客户常见的 x86_64 服务器上起不来**，报 `exec format error`——这个错误与"部署失败"看起来毫无关系，是最容易把人引向错误方向的一类。

六个镜像**都有 amd64 变体**（逐个 `docker manifest inspect` 确认），所以从 arm64 机器打 amd64 包可行，但**必须显式 `--platform`**，不能靠默认行为。

### 0.2 本地 RepoDigest 就是 index digest（架构无关）

```
$ docker image inspect postgres:17 --format '{{index .RepoDigests 0}}'
postgres@sha256:67f41722b7a8cbdb868a44a4995c846eddfdc2973bccb291ce937dce88ad5675
$ docker buildx imagetools inspect postgres:17
MediaType: application/vnd.oci.image.index.v1+json
Digest:    sha256:67f41722b7a8cbdb868a44a4995c846eddfdc2973bccb291ce937dce88ad5675
```

两者一致，且 MediaType 是 `image.index`。**结论：按这个 digest 钉死是架构无关的**，同一份 compose 既能配 amd64 包也能配 arm64 包，Docker 自己从 index 里挑对应架构的 manifest。这让"一个脚本出两种架构的包"几乎零成本。

### 0.3 两个浮动 tag 已经漂走了

| 镜像 | 本地（实测跑通的） | registry 当前 |
|---|---|---|
| `ghcr.io/berriai/litellm:main-stable` | `20b5044b…` | `c8756e7b…` |
| `casbin/casdoor:latest` | `f332047c…` | `1c442481…` |
| `postgres:17` | `67f41722…` | 一致 |
| `clickhouse/clickhouse-server:25.3` | `b627d7a9…` | 一致 |

就在最近几天内漂的。这是钉死的理由本身。两个旧 digest **仍然可拉取**（`docker buildx imagetools inspect <digest>` 成功），所以钉"跑通过的那一份"是可行的。

### 0.4 仓库现状

- **没有任何 Dockerfile，也没有 `.dockerignore`**，从零开始。
- 现有 `deploy/docker-compose.yml` 只是**开发依赖栈**：postgres / clickhouse / litellm / casdoor / openldap / mailpit 六个服务，**不含 Airlock 自己**。
- 单二进制这件事已经提前做对了：`cmd/airlock/main.go:1-3` 写着「单二进制分发是为了杜绝私有化交付时 edge 与 control 版本错配」，三个子命令 `edge`/`control`/`migrate`。
- `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build ./cmd/airlock` **交叉编译成功**。
- 两个进程都有 `/healthz`：`internal/edge/server.go:32`、`internal/control/routes.go:238`。

### 0.5 ClickHouse 表只由 initdb 钩子创建

`deploy/clickhouse/init/01_usage.sql` 建 `airlock.usage_records`，而 `grep "CREATE TABLE" internal/usage/*.go` **无匹配**——Go 从不创建它。`docker-entrypoint-initdb.d` **只在数据卷为空的首次启动时执行**。

后果：安装失败后重跑（卷还在），表不会被建出来，Edge 的用量写入直接失败。Postgres 那边的 `CREATE DATABASE litellm; CREATE DATABASE casdoor;` 同理。

### 0.6 SMTP 没有「关闭」模式

`config.go` 里 `SMTPAddr: or(getenv("SMTP_ADDR"), "localhost:1025")` 有默认值，而 LDAP / ClickHouse / LiteLLM 三个可选依赖都是「留空即禁用」。无外网机器上没有 mail relay 时，`ApprovalWorker.DeliverPending` 会重试到 `maxDeliverAttempts` 耗尽再标 `failed`，outbox 里堆满看起来像真故障的记录。

## §1 交付物边界与目录布局

### 1.1 生产栈六个服务

**airlock-control、airlock-edge、postgres、clickhouse、litellm、casdoor。**

Casdoor 随包交付作为默认 IdP：无外网机器上根本接不到客户现有的 Azure AD / Okta，不自带就无法完成登录，「2 小时装成功」的验收直接不成立。

**openldap 与 mailpit 不进交付物**——它们是开发夹具。openldap 里的 `bootstrap.ldif` 是假数据，交给客户极易被误当成生产配置；mailpit 是假 SMTP。客户接自己的 LDAP（留空即禁用）与 SMTP relay（见 §5）。

### 1.2 目录布局

打包脚本跑在**我们这台有网的机器**上，安装脚本跑在**客户那台没网的机器**上。混在一个目录里迟早有人在客户现场跑错脚本，所以分开放：

```
Dockerfile                    ← 新增（仓库根）
.dockerignore                 ← 新增
scripts/build-release.sh      ← 新增：打包用，需要外网
deploy/
  docker-compose.yml          ← 开发栈，一个字不动
  postgres/ clickhouse/ litellm/ openldap/   ← 开发栈用，不动
  release/                    ← 新增：交付包的源材料
    docker-compose.yml        生产栈，镜像按 digest 钉死
    .env.example              生产配置模板
    install.sh                客户那边跑，不需要外网
    schema/postgres-init.sql
    schema/clickhouse-init.sql
    litellm/config.yaml
docs/deploy/
  deployment.md               ← 新增：部署文档
  operations.md               ← 新增：运维手册
```

开发栈与生产栈**分两套文件**，不用 compose profiles 合并：两边受众不同、跑法也不同（开发从源码跑 Airlock，生产跑镜像），合在一起只会两边都难读。

### 1.3 交付物形态

`make release` 调 `scripts/build-release.sh`，产出：

```
airlock-<版本>-linux-amd64.tar.gz
  ├── images.tar        五个镜像：postgres / clickhouse / litellm / casdoor + airlock 自己
  ├── docker-compose.yml
  ├── .env.example
  ├── install.sh
  ├── schema/
  ├── litellm/config.yaml
  ├── VERSION           版本号、目标架构、五个镜像各自的 digest
  └── docs/             deployment.md + operations.md
```

`VERSION` 记全 digest 是为了支持：客户报障时第一件事是确认他装的是哪一版的哪些镜像，而在无外网机器上没有别的办法查证。

### 1.4 版本号从哪来

`scripts/build-release.sh` 接 `--version` 参数，缺省时取 `git describe --tags --always`。这个值同时用在三处，必须一致：镜像 tag（`airlock:<版本>`）、二进制里的 `main.version`、tar 包名与 `VERSION` 文件。

**工作区不干净时拒绝打包**，除非显式传 `--allow-dirty`。从带未提交改动的树里打出来的包无法复现——客户报障时我们拿不出与他手上一模一样的代码，这是最典型的支持噩梦。`--allow-dirty` 打出的版本号追加 `-dirty` 后缀，让它在 `VERSION` 文件和启动日志里一眼可见。

## §2 Airlock 镜像

### 2.1 三阶段 Dockerfile

前两阶段用 `--platform=$BUILDPLATFORM` **跑在构建机的原生架构上**，只有最终镜像是目标架构：

```dockerfile
FROM --platform=$BUILDPLATFORM node:22-alpine AS console
# npm ci && npm run build → web/dist

FROM --platform=$BUILDPLATFORM golang:1.25-alpine AS build
ARG TARGETARCH
ARG VERSION
COPY --from=console /src/web/dist ./web/dist
RUN CGO_ENABLED=0 GOOS=linux GOARCH=$TARGETARCH \
    go build -trimpath -ldflags "-s -w -X main.version=$VERSION" -o /airlock ./cmd/airlock

FROM alpine:3.21
RUN apk add --no-cache ca-certificates tzdata
# 非 root 运行
ENTRYPOINT ["/usr/local/bin/airlock"]
```

`CGO_ENABLED=0` 交叉编译已实测通过（§0.4），所以这条路零代价。换成让 QEMU 模拟 amd64 跑 Next.js 构建，时间会从分钟级变成十几分钟，且 QEMU 偶发段错误会把人引向完全错误的排查方向。

### 2.2 基础镜像选 alpine

带 shell 与基础工具。验收标准写了「每个错误都有明确排查指引」，而无外网现场排查连通性时能 `docker exec` 进去看一眼是极大的优势——客户机器上拉不到任何调试容器。代价是镜像大几 MB、攻击面比 distroless 大。

`ca-certificates` 不能省：OIDC 要连客户的 IdP，多半是 HTTPS，缺了它就是一个极难查的 `x509: certificate signed by unknown authority`。

### 2.3 版本标记（Go 改动之一）

`cmd/airlock/main.go` 目前没有任何版本信息。交付给客户之后，「你装的是哪一版」是每次支持对话的第一个问题，而无外网机器上没有别的办法回答。

- `cmd/airlock/main.go` 加 `var version = "dev"`，由 `-ldflags -X main.version=` 注入
- 新增 `airlock version` 子命令，打印版本后退出
- `edge` 与 `control` 的启动日志各带上 `version`

### 2.4 .dockerignore

排除 `.git`、`web/node_modules`、`bin/`、`.claude/`、`docs/`，以及**宿主机的 `web/dist`**——它由 console 阶段重新生成，带进去只会让构建缓存失效，还可能把一份过期的控制台塞进镜像。

## §3 生产 compose

### 3.1 镜像按 index digest 钉死

钉的是 **P1.1–P1.5b 全程实测跑通的那一份**，不是今天 registry 上恰好的那一份。钉一个从没跑过的 digest 等于钉了一个未验证的配置。

```yaml
postgres:17@sha256:67f41722b7a8cbdb868a44a4995c846eddfdc2973bccb291ce937dce88ad5675
clickhouse/clickhouse-server:25.3@sha256:b627d7a9bc0e0c1bac26cdbe9d2fc6316faa29c5d8a174f28f5abd57d0fa6ba2
ghcr.io/berriai/litellm:main-stable@sha256:20b5044b619055374061a6d5b7b08754cad75aeabbf82ddf4f69cc0cf80ddaf4
casbin/casdoor:latest@sha256:f332047c325588fb047bc1a34b0ce473f12ac044c0255a520f30f521fd7c249b
```

保留 tag 前缀（`postgres:17@sha256:…`）而不是只写 digest：解析时以 digest 为准，tag 纯粹是给人读的注释，让人一眼知道这是什么、大概哪个版本。

### 3.2 每个服务都设 `pull_policy: never`

这是离线故事的关键一笔。镜像缺失时 compose **立刻**失败并说清缺哪个，而不是在无外网机器上卡五分钟 DNS 超时，再抛一个和「镜像没导入」看着毫无关系的错误。

### 3.3 Airlock 两个服务共用一个镜像

```yaml
airlock-control:
  image: airlock:<版本>
  command: ["control"]
  pull_policy: never
  depends_on:
    postgres: {condition: service_healthy}
    clickhouse: {condition: service_healthy}
  healthcheck:
    test: ["CMD", "wget", "-q", "-O-", "http://localhost:8081/healthz"]

airlock-edge:
  image: airlock:<版本>
  command: ["edge"]
  pull_policy: never
```

靠子命令区分角色，edge 与 control 的版本天然一致（`main.go` 那条注释的原始意图）。两个进程都有 `/healthz`（§0.4），所以 compose 的 healthcheck 与安装脚本的成功判定都有实打实的着力点，不用靠「睡 30 秒然后祈祷」。

### 3.4 schema 初始化不走 initdb 钩子

生产 compose **不挂** `docker-entrypoint-initdb.d`，改由 `install.sh` 在容器健康之后显式执行 `schema/` 下的两个文件（§4.2 第 5 步）。

- ClickHouse 那份本来就是 `IF NOT EXISTS`，天然幂等
- Postgres 的 `CREATE DATABASE` 没有 `IF NOT EXISTS`，用 `SELECT 1 FROM pg_database WHERE datname='litellm'` 守卫后再建

这样安装失败重跑是安全的。initdb 钩子在卷非空时会**静默跳过**，那是最难查的一类故障（§0.5）。

## §4 打包与安装脚本

### 4.1 `scripts/build-release.sh`（我们这边，需要外网）

1. `docker buildx build --platform $PLATFORM` 出 airlock 镜像，注入 `VERSION`
2. 按 digest `docker pull --platform $PLATFORM` 四个第三方镜像——**必须显式传 `--platform`**（§0.1）
3. `docker save` 全部五个镜像到 `images.tar`
4. 生成 `VERSION`：版本号、目标架构、各镜像 digest
5. 连同 compose、install.sh、schema、litellm 配置、文档打成 tar.gz

`--platform` 默认 `linux/amd64`，传参可换 `linux/arm64`。因为 digest 是架构无关的（§0.2），两种架构共用同一份 compose，只有 `images.tar` 不同。

### 4.2 `deploy/release/install.sh`（客户那边，不需要外网）

按顺序做五件事，**每一步失败都打印该怎么办，而不是只抛一个退出码**：

1. **前置检查**
   - docker 与 compose 插件是否存在及版本
   - `uname -m` 与 `VERSION` 里记的架构是否一致——不一致直接停下并说明「这个包是给 x86_64 的，当前机器是 aarch64，请索取 arm64 版本」。这道检查专治 `exec format error`（§0.1）
2. **导入镜像**：`docker load -i images.tar`，逐个校验 digest 与 `VERSION` 记录一致
3. **配置**：`.env` 不存在则从模板生成，并**自动生成随机的数据库口令与 `AIRLOCK_ENCRYPTION_KEY`**——模板里的开发默认值绝不能进生产。生成后明确提示哪几项必须人工填（OIDC 三件套、上游供应商密钥、license 文件路径）
4. **起栈并等健康**：`docker compose up -d`，轮询各服务 healthcheck；超时则把对应容器最后 50 行日志直接打出来，而不是只说「启动超时」
5. **初始化 schema 并自检**：执行 `schema/` 下两个文件，然后打 `/healthz`、确认 `usage_records` 表确实存在，最后打印控制台地址与下一步该做什么

重跑安全：第 3 步不覆盖已有 `.env`，第 5 步幂等，第 2 步重复 load 无副作用。

## §5 SMTP 留空即禁用（Go 改动之二）

三处改动：

- `internal/config/config.go`：去掉 `SMTP_ADDR` 的默认值 `localhost:1025`
- `internal/notify`：新增 `DisabledSender`，`Send` 记一条 info（带收件人与主题）后返回 nil
- `internal/app/control.go`：`cfg.SMTPAddr == ""` 时用它，并 `slog.Warn("未配置 SMTP_ADDR，邮件通知未启用")`——与 LDAP / ClickHouse / LiteLLM 那三条 warn 并排

`internal/config/config_test.go:143` 断言了 `localhost:1025` 这个默认值，需要一并更新成「留空即为空」。

### 一个如实说明的副作用

返回 nil 会让 outbox 那行被 `MarkSent` 标成「已送达」，而实际没有邮件发出。审计上看，禁用邮件时 `notifications.status='sent'` 略有误导。

另一条路更糟：返回错误的话，`ApprovalWorker.DeliverPending`（`internal/control/approvalworker.go:200-210`）会重试到 `maxDeliverAttempts` 耗尽再标 `failed`，outbox 里堆满看起来像真故障的失败记录，运维每天都要来问一次。

彻底干净的做法是把入队时硬编码的 `Channel: "email"`（`approval.go:111`、`approvalworker.go:120`）改成从 sender 取，禁用时记成 `channel='none'`，记录就诚实了。但那要动审批流的两处入队点，属于本阶段之外的改动。**这一版按「返回 nil + 启动 warn + 运维手册写明」处理，把改 channel 记为后续可做项。**

## §6 文档

两份放 `docs/deploy/`，打包时原样复制进 tar。文件名用 ASCII，中文标题写在文档内部——避免在打包时维护一份改名映射。

### 6.1 `deployment.md` 部署文档

从拿到 tar 到能登录控制台：前置要求（OS、Docker 版本、CPU / 内存 / 磁盘、需要放通的端口）、安装步骤、**哪几项配置必须人工填**（OIDC 三件套、供应商密钥、license 文件）、装完的验证清单。

### 6.2 `operations.md` 运维手册

装完之后的事：备份与恢复、升级、日志在哪、如何吊销密钥、如何续期 license 与加席位、如何看用量、SMTP 未配置时通知的行为（§5）。

### 6.3 故障排查表

验收标准里「每个错误都有明确排查指引」落在这张表上。不是泛泛的「检查网络」，而是具体的现象→原因→动作。以下每条都是**已经实测知道会发生**的：

| 现象 | 原因 | 动作 |
|---|---|---|
| `exec format error` | 包的架构与机器不符 | 索取对应架构的包；`uname -m` 对照 `VERSION` |
| compose 立刻报镜像不存在 | `images.tar` 未导入或导入失败 | 重跑 install.sh 第 2 步（`pull_policy: never` 让它快速失败而不是超时） |
| `x509: certificate signed by unknown authority` | 客户 IdP 用内部 CA | 挂载 CA 证书进容器 |
| `usage_records` 表不存在 | 卷非空导致 initdb 跳过（旧版遗留） | 重跑 install.sh 的 schema 步骤（幂等） |
| Edge 返回上游 401 | 供应商密钥未配或无效 | 检查 `.env` 里的供应商密钥 |
| 控制台顶部红条、写操作 402 | license 过期 | 换新 license 文件后重启 control |
| 新成员登录报「席位已满」 | 席位用尽 | 停用离职成员，或续期扩容 |
| 审批邮件没收到 | 未配 `SMTP_ADDR` | 预期行为不是故障，见 §5 |

## §7 测试与验收

### 7.1 自动化测试

只有两处 Go 改动可测，照常写单元测试：

- **版本标记**：`airlock version` 打印注入的版本；未注入时为 `dev`
- **SMTP 禁用**：`config.Load` 在 `SMTP_ADDR` 留空时得到空字符串（更新 `config_test.go:143` 的旧断言）；`DisabledSender.Send` 返回 nil 且不发起任何网络连接

`make lint` 与 `make test` 保持全绿。

### 7.2 端到端验收

**必须如实说明的局限：构建机是 arm64，amd64 的包无法在这里端到端跑起来**（容器根本起不来）。验收因此拆成两半：

**A. 安装流程（在 arm64 包上验）**
打一个 `--platform linux/arm64` 的包，在本机走完整流程：`docker load` → `install.sh` → 等健康 → schema 初始化 → 登录控制台 → 打一次数据面请求。验证的是脚本、compose、健康检查、文档步骤的正确性。

**B. 架构正确性（在 amd64 包上验）**
打默认的 amd64 包，`docker load` 后逐个 `docker image inspect --format '{{.Architecture}}'` 确认五个镜像全是 amd64，并确认 `VERSION` 里记的 digest 与实际加载的一致。验证的是打包脚本的 `--platform` 处理。

两半合起来能覆盖，但**没有任何一步在真实的 x86 无外网机器上跑过**——这一点写进验收记录，不含糊过去。真正的 x86 首装仍然是首个客户现场的风险点。

### 7.3 另外要实测的两条

1. **架构检查确实拦得住**：人为把 `VERSION` 里的架构改掉，确认 `install.sh` 报错并给出「请索取对应架构的包」的指引
2. **重跑 install.sh 是安全的**：第二次执行不覆盖 `.env`、不破坏已有数据、schema 步骤幂等

## §8 明确不做的事

- **不做 Helm / K8s 部署清单。** Roadmap 第 66 行写明「完整的 License、Helm、升级回滚体系应在功能稳定后建设，否则随功能变更反复返工」。
- **不做自动升级与回滚。** 运维手册写清楚手工升级步骤即可。
- **不把 openldap / mailpit 做成可选 profile。** 那等于把刚排除的开发夹具放回来，且客户很可能就这么一直用下去。
- **不改审批流的 channel 字段。** 见 §5，记为后续可做项。
