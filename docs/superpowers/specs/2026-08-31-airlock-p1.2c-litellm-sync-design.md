## 1. 背景与范围

P0 已经实测确定了拍平方案：Airlock 支持任意深度组织树，LiteLLM 只有 `Organization → Team` 两层，因此根下第一层映射为 Organization、持有 Key 的节点映射为 Team、中间层不建实体。本阶段把这个方案实现为一套持续运行的同步机制。

Roadmap 原本把 RBAC 与本阶段一起放在 P1.2，已在 P1.2b 设计中拆分（该文档 §2 D1）。

### 本阶段范围

- Airlock 组织树 → LiteLLM `Organization` / `Team` 两类实体的映射
- 持续同步：写时尽力推送 + 周期对账兜底
- 漂移检测与收敛
- 标记「哪些节点是密钥与预算边界」的能力

### 明确的范围外

| 项 | 去向 |
|---|---|
| LiteLLM `User` 实体的同步 | P1.3（随 Key 签发一起做，届时才知道 Key 到底怎么绑） |
| 预算额度的配置与下发 | P1.3 |
| 自建配额引擎（中间层硬拦截） | P2 |
| `is_key_holder` 的管理界面 | P1.4（本阶段只提供 API） |
| 取消标记后回收 Team | P1.3（见 §6「一个刻意留下的不对称」） |

## 2. 设计前的实测

P0 的教训是「LiteLLM 文档声称的与实际行为是两回事」（当时实测发现编造的 `parent_team_id` 被静默丢弃）。本次设计同样先对本地 LiteLLM 跑了一批探针，其中三条**推翻或显著改变了原本的设计假设**：

| 探针 | 结论 | 对设计的影响 |
|---|---|---|
| A / E | `/organization/new` 与 `/team/new` **都接受调用方自带的 ID** | 直接用 Airlock 节点 UUID 作实体 ID，映射退化为恒等式，不需要映射表（D5） |
| B / C | `alias` 完全不去重，同名连建两次得到两个不同实体 | alias 绝不能当幂等键 |
| F | 用已存在的 `organization_id` 重复创建 → **500 Internal server error** | 拒绝了，但状态码无法区分「已存在」与「真故障」。同步必须先查后建，不能靠错误码兜底 |
| G | 用已存在的 `team_id` 重复创建 → 400，错误信息明确 | 团队侧行为干净，与组织侧不对称 |
| D | 删除 Organization **静默级联删除其下全部 Team**，返回 200 | 删除必须极度保守（D4），并需要一个安全性证明（§6） |
| H | `/organization/update` 修改 alias 正常生效 | 改名同步路径可用 |
| K | `/team/update` 可以修改 `organization_id`，**原地改挂且 `team_id` 不变** | 跨子树移动叶子是无损更新，不需要删了重建，Key 归属不受影响 |
| I | 同一个 ID 既做 Organization 又做 Team、且 Team 挂在自己身上 —— **合法** | depth-2 节点自身是密钥边界时无需特殊处理 |
| J | Team 挂到不存在的 `organization_id` → **400 拒绝**（有真实外键校验） | 同步存在硬顺序约束：必须先建完 Organization 才能建 Team |

## 3. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| D1 | 只同步 Organization + Team，不同步 User | Key 生命周期在 P1.3。现在同步只会造出一批没有任何 Key 挂靠的空 User，且「用户归属变更、用户禁用」还要再设计一套同步与对账，范围明显失控 |
| D2 | `organizations` 增加 `is_key_holder` 布尔列；标记者建 Team，与是否叶子无关 | 「叶子」是错误判据：给叶子加子节点会逆转判定，逼着同步删掉一个可能已绑 Key 的 Team，而组织扩张是最正常的操作。且 `api_keys.org_id` 本就不限制叶子 |
| D3 | 写时尽力推送 + 周期对账兜底；对账是正确性保证，写时同步只是延迟优化 | 无法原子提交「Postgres 事务 + HTTP 调用」。若先调 LiteLLM 成功、本地事务再回滚，就留下本地无记录的孤儿实体且无干净补救路径。把正确性押在对账上，双写不一致就不存在 |
| D4 | 对账只补建与纠正，**绝不删除**；仅「用户显式删节点」才尽力删对应实体 | 探针 D 证明删 Organization 会静默级联删光其下 Team，而那些 Team 上可能绑着在用的 Key。与 P1.2a「导入永不删除」是同一条纪律 |
| D5 | 直接用 Airlock 节点 UUID 作 LiteLLM 实体 ID | 探针 A/E 证明可行。映射成为恒等式，省掉一张会和现实漂移的对照表 |
| D6 | 不持久化任何同步状态 | 对账每轮全量比对两侧，本来就能回答「同步好了没有」。多存一份派生状态就多一处漂移源，与 D5 同理 |
| D7 | 写时同步实现为「异步触发一次完整对账」，而非独立的增量同步逻辑 | 单一代码路径，零重复实现；且天然解决「移动节点改变整棵子树深度」这个增量同步很难做对的场景 |

## 4. 映射规则

```
集团（depth 1，允许多根）         → 不建实体，只存在于 Airlock
└── 研发中心（depth 2）           → Organization（id = 节点 UUID，alias = 节点名）
    └── 平台产品部（depth 3）      → 不建实体
        └── 网关组（depth 4）      → 不建实体
            └── 数据面小组         → 若 is_key_holder，则 Team
                                     organization_id = path 第 2 段（即「研发中心」）
```

- **Organization 判据**：`path` 恰好 2 段。多根场景下各根的子节点各自成为一个 Organization，规则天然适用。
  **所有** depth-2 节点都建 Organization，不管其下当前有没有被标记的后代——这是刻意的：depth-2 是业务线层级，数量通常只有个位到十几个（远小于叶子数），且 P1.3 配置组织级预算时本来就需要它们全部存在。
- **Team 判据**：`is_key_holder = true`，任意深度。`organization_id` 取该节点 `path` 的第 2 段。
- **中间层与根层不建实体**，沿用 P0 结论：伪造出的中间层实体既表达不了父子关系，也不会被 LiteLLM 的预算引擎读取，只会污染上游实体列表。

### 两个退化情况

| 情况 | 行为 | 实测依据 |
|---|---|---|
| depth-2 节点自身被标记 | 它既是 Organization 又是 Team，`Team.organization_id` 指向自己。两类实体在 LiteLLM 是不同的表，ID 相同不冲突 | 探针 I |
| depth-1 根节点被标记 | 无 depth-2 祖先，其 Team 不挂任何 Organization | LiteLLM 允许无组织的 Team |

根节点被标记时，它头上没有组织级预算天花板。这是真实的能力缺口，**必须在客户文档里讲清楚，不能默默降级**——与 P0 对中间层「软限制」的处理纪律一致。

### 顺序约束

一轮同步必须**先处理完全部 Organization，再处理 Team**（探针 J：Team 挂到不存在的 organization_id 会被 400 拒绝）。

## 5. 数据模型与组件

### 数据模型：只加一列

```sql
ALTER TABLE organizations ADD COLUMN is_key_holder BOOLEAN NOT NULL DEFAULT false;
```

不新增映射表（D5），不新增同步状态字段（D6）。「当前差异」由一个只读接口现算现返，形状照抄 P1.2a 已有的导入预览。

### 包边界

**新增 `internal/litellm`**：纯 LiteLLM Admin API 客户端。只认识 `Organization` / `Team` 两个结构体与其增删改查方法，完全不知道 Airlock 的组织树、`is_key_holder` 或路径语义。可以对着 `httptest` 服务器测完全部错误分支，不碰 Postgres。

**对账算法放 `internal/control/litellmsync.go`**，通过在 control 内定义的窄接口依赖上述客户端——与 P1.2a 的 `IdentitySource` / `LDAPIdentitySource` 是同一个模式。

`internal/control` 目前已有 36 个文件，客户端单独成包也是为了不让它继续膨胀。

### 对账算法

```
ReconcileOnce():
  1. 算期望态（纯本地，纯函数）：
       wantOrgs  = 所有 depth==2 的节点             → {id, alias}
       wantTeams = 所有 is_key_holder 的节点         → {id, alias, orgID = path 第 2 段}
  2. 拉现状：ListOrganizations() + ListTeams()
       ← 任一失败则整轮中止，不做任何写入
  3. Organization 阶段：缺则建；alias 不符则改；多出来的只告警
  4. Team 阶段（顺序约束）：只处理 orgID 确实已存在的；
       缺则建；alias 或 organization_id 不符则改；多出来的只告警
  5. 返回 {OrgsCreated, OrgsUpdated, TeamsCreated, TeamsUpdated, Extra, Errors}
```

两条安全性质：

- **拉取现状失败 → 整轮中止。** 绝不能因为「查不到」就当成「不存在」，那会对已存在的实体重复创建。这条直接照搬 P1.2a 对账「IdP 返回空集合视为故障」的纪律。
- **单个实体失败 → 记录并继续处理其余实体。** 这一条与 P1.2a 相反：离职对账的几步是有序且安全攸关的，而这里各节点彼此独立，一个坏节点不该把整棵树卡住。失败项下一轮自动重试。

### 写时尽力：不写第二条代码路径

写操作成功后**异步触发一次完整对账**，而不是实现一套独立的增量同步：

```go
type Syncer struct {
    trigger chan struct{} // 容量 1
}
func (s *Syncer) Nudge()            // 非阻塞；已有待跑的一轮就直接丢弃
func (s *Syncer) Run(ctx, interval) // select { <-ticker.C, <-trigger }
```

周期对账与写时同步跑同一个函数，没有任何重复实现。容量 1 的 channel 天然把连续写操作合并成一轮。

这个选择顺带解决了一个真问题：**移动节点会改变整棵子树的深度**，进而改变哪些节点是 Organization、以及后代 Team 该挂到哪个 Organization 名下。增量同步需要为此重算整棵子树；触发全量对账则完全不必考虑。

### 新增接口

全部按 P1.2b 的路由表声明访问要求：

| 端点 | 访问要求 |
|---|---|
| `PUT /api/orgs/{id}/key-holder` | `org:write`，目标取路径 `{id}` |
| `GET /api/litellm/sync/status` | `platform:configure`（全局） |
| `POST /api/litellm/sync`（手工触发一轮） | `platform:configure`（全局） |

`GET /api/litellm/sync/status` 返回当前差异，不做任何写入：`{enabled, missing_orgs[], missing_teams[], mismatched[], extra[], last_error}`。`extra` 就是 §6 里那些「多出来但不删」的实体——它们必须**可见**，否则 D4 的保守策略会退化成静默积累垃圾。同步未配置时 `enabled` 为 false，其余为空。

后两个复用 `platform:configure` 而不新增权限：这是平台与上游网关的集成状态，本就只该平台管理员看到，不值得为它改动权限注册表与 6 个内置角色。

### 配置

| 变量 | 说明 |
|---|---|
| `LITELLM_BASE_URL` | 管理 API 地址。**不复用 `EDGE_UPSTREAM_BASE_URL`**——那是 Edge 热路径的配置，本阶段坚持对 Edge 零改动 |
| `LITELLM_MASTER_KEY` | 管理 API 的高权限密钥。**未配置则同步整体禁用**，启动时 WARN，照搬「未配置 LDAP_URL，离职对账未启用」 |
| `LITELLM_SYNC_INTERVAL` | 对账周期。沿用 P1.2b 补的正数校验：非正值直接拒绝启动，而不是 panic |

## 6. 失败模式与漂移

### 删除传播为什么是安全的

D4 只允许「用户显式删节点」时删对应实体，而探针 D 证明删 Organization 会级联删光其下 Team。这两条放在一起需要证明，否则就是在赌。

Airlock 的 `Delete` 守卫已保证被删节点**无子节点（`ErrOrgHasChildren`）、无 Key（`ErrOrgHasKeys`）、无归属用户（`ErrOrgHasUsers`）**。因此：

| 被删节点 | LiteLLM 侧实体 | 删除行为 | 是否波及不该删的实体 |
|---|---|---|---|
| depth-2，非 key holder | `Organization(X)` | 删 Organization | 否——无子节点，其下不可能有被标记的后代 |
| depth-2，是 key holder | `Organization(X)` + `Team(X)` | 删 Organization，级联带走 Team | 否——这两个本就都该删 |
| 深层 key holder | `Team(X)` | 删 Team | 否 |

三种情况下级联都不波及任何不该删的实体，因为「无子节点」意味着它下面根本不存在其它被标记的节点。**这个结论依赖 `ErrOrgHasChildren` 守卫成立，验收要专门复验一次该守卫。**

### 一个刻意留下的不对称

`is_key_holder` 由 `true` 改回 `false` 时，**对账不会删掉那个 Team**（D4）。它会留在 LiteLLM 侧，并在状态接口里显示为「多出来的实体」。

这是有意的：P1.2c 还没有 Key 生命周期，无法判断那个 Team 上是否已绑着在用的 Key。等 P1.3 把 Key 管起来后再决定能否安全回收。现在宁可留一个**可见的**垃圾，也不冒删掉线上密钥归属的风险。

### 其余失败模式

| 场景 | 行为 |
|---|---|
| LiteLLM 完全不可用 | 对账整轮中止并记 error；**组织树读写完全不受影响**（D3）；恢复后下一轮自动收敛，无需人工干预 |
| LiteLLM 侧多出 Airlock 不认识的实体 | 只在状态接口报告，不删除（D4）。可能是别的系统建的，也可能是本地删了节点而对账不删所致 |
| 单个实体操作失败 | 记录并继续；下一轮重试 |

## 7. 安全

- `LITELLM_MASTER_KEY` 能创建和删除任意组织、团队与密钥，是全系统权限最高的凭据。只从环境变量读、不落库、**不得出现在任何日志或错误响应中**（客户端返回错误时必须剥掉请求头）。
- 三个新端点全部纳入 P1.2b 的路由表与机械检查。`platform:configure` 是全局作用域权限，因此「把 `platform_admin` 授予在某个节点上」的用户仍然调不动同步——该性质由 P1.2b 的 D4 保证，验收复验一次。

## 8. 测试策略

| 层次 | 覆盖 |
|---|---|
| `internal/litellm` 单测（httptest） | 正常路径、4xx、5xx、超时、响应体畸形。**重点是探针 F 的「重复创建 Organization 返回 500」**——客户端不能把它误当成通用故障 |
| 对账算法单测（fake 客户端） | 缺则建 / 不符则改 / 多出来只告警；拉取现状失败整轮中止；单实体失败不阻塞其余；Organization 严格先于 Team；orgID 不存在的 Team 被跳过而非硬撞 400 |
| 映射规则单测（纯函数） | 多根；depth-1 被标记（Team 不挂 Org）；depth-2 既是 Org 又是 Team；Move 改变深度后期望态随之变化 |
| Nudge 单测 | 连续多次 Nudge 只跑一轮 |
| 路由级 | 三个新端点的「无授予 / 授予足够 / 节点级授予拿不到全局权限」三态 |
| 机械检查 | P1.2b 的两条自动覆盖新端点，无需额外工作 |

映射规则是纯函数（组织树 → 期望态），完全脱库可测，与 `internal/authz` 一样是本阶段最有价值的测试面。

## 9. 验收标准

对着真实 LiteLLM 逐项验证，每项记录真实输出：

1. 建三层树并标记一个 key holder → 两侧实体正确，`Team.organization_id` 指向正确的 depth-2 节点
2. 改名 → 两侧 alias 收敛一致
3. 跨子树移动被标记节点 → `organization_id` 原地改挂，`team_id` **不变**
4. 把一个 depth-3 节点移成 depth-2 → 它成为新 Organization，其后代 Team 改挂到它名下
5. 手工改掉 LiteLLM 侧某 Team 的 alias → 下一轮对账改回
6. 手工删掉 LiteLLM 侧某 Organization → 下一轮对账补建，且其下 Team 一并补回
7. **停掉 LiteLLM** → 组织树读写完全不受影响，对账记 error；重新起来后自动收敛
8. LiteLLM 侧多出一个 Airlock 不认识的实体 → 只在状态接口报告，**不被删除**
9. 删除一个被标记的节点 → 其 Team 被删除；且复验 `ErrOrgHasChildren` 确实拦得住有子节点的删除
10. 节点级 `org_admin` 调 `POST /api/litellm/sync` → 403
11. `internal/edge` 33 PASS / 0 FAIL，零回归

## 10. 规模预估

约 14–18 个任务，比 P1.2b（21 个）小一圈：判定逻辑那一大块本阶段不存在，且映射规则是纯函数。
