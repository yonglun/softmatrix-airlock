## 1. 排期假设

本 Roadmap 的周数估算基于以下假设，任何一条不成立都需要重新排期：

- **产能**：1 人主导 + AI 辅助开发，全职投入
- **切片原则**：每个里程碑结束都是一个能演示、能验收的状态，不存在「做到一半没法看」的阶段
- **技术选型已定**：Go 控制面与数据面 + Next.js 前端 + 内嵌 Casdoor + LiteLLM 纯数据面
- **不含**：客户定制开发、售前支持、市场活动占用的时间

累计约 **32–40 周**到 v2.0 与产品化完成。这是乐观但不荒谬的估算。

### 最可能超期的三个点

1. **M1 · Casdoor 各家 IdP 连接器的实际踩坑。** 文档上支持和真实企业环境里跑通是两回事，尤其是老旧的 AD 与自建统一认证平台。
2. **M4 · 流式护栏的延迟调优。** 缓冲窗口与检出率的平衡没有标准答案，需要反复实测。
3. **M3.5 之后 · 第一次真实客户部署。** 私有化交付的环境问题只有在真实客户机房才会暴露。

## 3. 排序逻辑

**为什么是这个顺序：**

1. **M0–M3 是不可跳过的核心路径。** 没有身份就没有组织，没有组织就没有配额，没有配额就没有可分析的归属维度。这四步严格依赖，不能重排。

2. **M3.5 插在中间是刻意的。** Airlock 是对外销售的产品。v1.0 的能力已经追平 LiteLLM Enterprise 且前端与配额模型更强——这时候就该开始接触客户拿真实反馈，而不是闷头做到 v2.0 才见人。M4/M5 的产品细节应该被真实客户的异议塑造，而不是被闭门想象塑造。

   **已决策**：v1.0（尚无内容护栏）即开始客户 POC。接受首批客户可能因缺少安全能力而拒绝的风险，因为此阶段接触客户的主要目的是获取需求反馈。

3. **M4 必须在 M5 之前。** 出境管控依赖脱敏能力，而脱敏是护栏检测器的一部分。反过来做会返工。

4. **M6 产品化在 M5 之后。** 完整的 License、Helm、升级回滚体系应该在功能定型后做，否则会随功能变更反复返工。M3.5 已经提供了做 POC 所需的最小能力。

5. **M7 放最后。** Agent/MCP 治理的行业标准仍在演进，过早实现容易白做。可根据客户需求提前。

## 4. 里程碑详情

### M0 · 地基（3–4 周）

**目标**：打通「调用方 → Edge → LiteLLM → 模型」的最短链路，验证核心架构假设。

**交付物**
- Go 单仓骨架：`cmd/edge`、`cmd/control`、`internal/`、`web/`
- PostgreSQL schema 与数据库迁移框架
- LiteLLM 以容器形式部署，接入 3 家供应商（DeepSeek、通义千问、OpenAI）
- Edge 最小管线：Key 鉴权 → 转发 → 用量落 ClickHouse
- **完整的定价数据模型**：支持输入/输出单价、缓存命中价、思考 token 计费、阶梯价、按时间生效的价格版本
- Control Plane 最小 API：创建 Key、查询用量
- **流式出向护栏的缓冲窗口原型**（只验证可行性与延迟影响，不做完整功能）

**验收标准**
- 用 Airlock 签发的 `ak-` 密钥调通国产与海外模型，含流式响应
- 用量可查询，成本核算结果与供应商账单一致
- 流式缓冲窗口原型给出首字延迟增量的实测数据

**依赖**：无

**风险**：定价模型如果做得不够完整，后续所有历史账单会失真——这是本阶段最重要的一件事，不要因为「先跑通」而简化。

---

### M1 · 身份与组织（4–5 周）

**目标**：企业能用自己的身份体系登录，管理员能建组织、发密钥、控制模型可见性。

**交付物**
- Casdoor 内嵌部署，Airlock 作为 OIDC 客户端接入
- **实测通过**的连接器：钉钉、企业微信、飞书、LDAP/AD
- 组织树（可嵌套）、成员管理、通讯录同步
- RBAC：5 个内置角色 + 自定义角色，组织节点级授予
- CostCenter 实体与归属关系
- 虚拟 Key 完整生命周期：申请 → 审批 → 签发 → 轮换 → 吊销
- 模型可见性三级白名单（组织 / 角色 / Key）
- Console 骨架：Next.js + 四工作台切换 + 登录态 + 布局系统

**验收标准**
- 企业用自家钉钉账号登录 Airlock
- 管理员创建组织、分配角色、签发 Key
- 成员只看得到被授权的模型，调用未授权模型返回明确错误码
- IdP 侧禁用某用户后，其名下 Key 立即失效

**依赖**：M0

**风险**：各家 IdP 的真实环境差异极大。**每个连接器都必须在真实环境实测**，不能只看 Casdoor 文档声称支持。建议尽早找到可测试的真实环境。

---

### M2 · 配额引擎（4–5 周）

**目标**：实现组织 / 角色 / 个人三维叠加的配额管理，这是产品的第一个真正差异点。

**交付物**
- 四计量维度：金额、Token、请求数、速率（RPM/TPM/并发）
- 三维叠加判定：`min(组织额度, 角色基线, 个人覆盖)`
- 组织树语义：`严格` 与 `超售` 两种模式
- 周期管理：日 / 周 / 自然月 / 自定义窗口，含时区
- **Redis 两阶段预扣-结算**，含异常中断的对账兜底任务
- 超限行为分级：80% 告警 → 95% 升级 → 100% 降级或阻断 → 硬顶阻断
- 降级路由：自动切换到低价模型池，响应头显式标示
- 临时提额申请与审批流，带过期时间的增量额度自动回收
- 告警通道：钉钉、企业微信、邮件
- Console：**成本财务工作台**（配额策略、提额审批）+ **我的空间**（个人用量与余额、申请提额）

**验收标准**
- 设置组织/角色/个人三层配额，判定结果符合「取最严」语义
- **并发压测不超发**，场景需覆盖「多个 Key 同时消耗同一组织额度」
- 超限自动降级到低价模型池，业务不中断，响应头正确标示降级信息
- 提额申请到期后额度自动回收，全程可审计

**依赖**：M1（需要组织树与角色）

**风险**：两阶段预扣-结算在异常路径（连接断开、进程崩溃、上游超时）下的正确性是本阶段最容易出错的地方。需要专门的故障注入测试。

---

### M3 · 审计与分析（4–5 周）

**目标**：让成本说得清、行为查得到、合规交得了差。

**交付物**
- ClickHouse 明细表设计与异步批量写入管线
- 审计留存策略配置：不留存 / 脱敏后留存 / 全量留存，含留存期限与到期处理
- 审计日志哈希链与完整性校验，只读导出
- 管理操作审计（配置变更前后值、操作人、来源 IP）
- 审计检索：按人、组织、成本中心、模型、时间、关键词组合查询
- **成本财务工作台完整版**：多维下钻、成本中心账单、趋势、月度预测、突增异常告警
- 性能指标：TTFT、TPS、错误率、限流率，按模型横向对比
- 优化建议：模型替换的成本节省估算与质量风险评估
- 定时报表：推送到钉钉/企微/邮件，CSV/Excel 导出
- Console：**安全合规工作台**初版（仅审计检索，护栏相关页面在 M4 补全）

**验收标准**
- 千万级记录下多维下钻查询响应 < 2s
- 各维度账单之和与总账单**逐分对齐**
- 审计日志完整性校验通过；篡改任一条记录后校验失败
- 定时报表按配置周期正确送达

**依赖**：M2（需要配额与成本归属数据）

---

### ▶ 版本节点：v1.0 可售

此时 Airlock 在能力上已覆盖 LiteLLM Enterprise 的主要功能，且在以下方面明显更强：
- 全新的角色工作台控制台（vs LiteLLM 的通用管理界面）
- 三维叠加配额 + 双归属维度（vs 两级平铺）
- 国产 IdP 原生支持
- 国产模型的完整定价支持

尚不具备：内容护栏、数据出境管控、Agent 治理。

---

### M3.5 · 最小交付包（2 周）

**目标**：让 v1.0 真的能装进客户机房，开始 POC。

**交付物**
- docker-compose 一键部署
- 离线镜像包（镜像 tar + 一键安装脚本）
- 基础 License 校验（到期时间 + 席位数）
- 部署文档与运维手册

**验收标准**
- 在一台干净的、**完全无外网**的机器上，照文档 2 小时内部署成功
- 部署过程中的每一个错误都有明确提示与排查指引

**依赖**：M3

**产出**：可开始客户 POC。**M4/M5 的产品细节应根据 POC 反馈调整。**

---

### M4 · 内容护栏 L2（5–6 周）

**目标**：做出企业敢在生产环境开启的护栏。

**交付物**
- `Guardrail Provider` 可插拔接口（含超时与 fail-open/fail-closed 策略）
- 内置检测器：正则/词典引擎、敏感词库（支持导入客户自有词库）
- 集成开源 PII 识别引擎
- 集成小模型分类器（提示注入、越狱、内容安全分类）
- 策略编排引擎：检测器组合 × 作用范围 × 动作 × 例外名单，按组织树继承
- **影子模式**（必交付项）：只记录不拦截，展示命中分布、抽样样本、估算误报率
- 拦截记录与误报申诉流
- **流式出向护栏**：滑动缓冲窗口，可配置窗口大小，命中时中断并标记
- Console：**安全合规工作台补全**（安全态势、护栏策略、拦截记录、误报申诉处理）

**验收标准**
- 影子模式在真实流量下跑出可信的误报率数据
- 流式首字延迟增量**可量化并在控制台展示**
- 护栏引擎故障时按配置的 fail-open/fail-closed 策略正确降级
- 误报申诉可一键加入例外，全程审计

**依赖**：M3.5（POC 反馈应影响本阶段的策略设计）

**风险**：这是整个 Roadmap 中工程复杂度最高的阶段。M0 的缓冲窗口原型数据在此阶段兑现价值——如果原型显示延迟不可接受，需要在本阶段开始前重新设计方案。

---

### M5 · 数据主权 L3（3–4 周）

**目标**：实现头号差异化卖点。

**交付物**
- 四级密级体系（可自定义名称与层数）
- 密级判定优先级链：请求头 → Key 声明 → 组织默认 → 内容自动推断
- 供应商境内/境外/自建标记
- 出境策略矩阵（密级 × 目的地），控制台上呈现为可点选的表格
- 脱敏后出境（复用 M4 的检测器）
- 出境台账：逐条留痕，含密级判定依据与脱敏差异摘要
- 合规报告导出：等保测评材料、生成式 AI 服务管理办法自查表

**验收标准**
- 机密级数据发往境外模型被拒绝、留痕，且可导出为合规材料
- **无绕过路径**：需专门做绕过测试（改请求头、换 Key、直连 LiteLLM 端口等）
- 脱敏后出境的差异摘要准确反映脱敏内容，但不泄露原文

**依赖**：M4（脱敏能力）

---

### ▶ 版本节点：v2.0 差异化成立

竞品对标表里「只有 Airlock 有」的两个格子（数据主权与出境管控、三维叠加配额）被真正填上。此时产品具备完整的差异化叙事。

---

### M6 · 产品化交付（4 周）

**目标**：从「能装」到「好卖好维护」。

**交付物**
- Helm Chart（K8s 部署）
- 完整 License 体系：机器指纹绑定、节点数、席位数、到期宽限期、到期后降级为只读
- 版本化 API 与数据库迁移，含回滚脚本与跨版本升级路径文档
- 高可用配置：Edge 多实例、Control Plane 主备、存储外接
- 备份与恢复流程
- **自诊断页面**：数据库连通性、供应商可达性、证书有效期、License 状态
- 信创数据库适配验证（人大金仓 / openGauss）

**验收标准**
- K8s 与单机双形态均可交付
- 一次跨版本升级演练成功，并成功回滚
- 自诊断页面能定位至少 8 类常见环境问题
- 在信创数据库上完整跑通功能回归

**依赖**：M5

---

### M7 · Agent / MCP 治理 L4（5–6 周）

**目标**：抢 2026 年 AI 治理的新战场。

**交付物**
- MCP Server 注册与纳管，工具级白名单
- Agent 服务身份与发起人自然人身份绑定
- 工具调用审计与越权检测
- 多轮会话上下文的累积注入检测

**验收标准**
- Agent 的每次工具调用可追溯到发起的自然人
- 越权的工具调用被拦截并告警
- 配额与审计正确归属到自然人而非服务账号

**依赖**：M6

**说明**：行业标准仍在演进。可根据客户需求提前，也可在标准更清晰后再做。

---

## 5. 持续性工作

不占用里程碑，但持续进行：

- **供应商扩展**：随客户需求接入新的模型供应商
- **定价表维护**：供应商调价时更新内置定价表
- **性能优化**：随真实负载调优
- **客户定制**：POC 与交付过程中的客户特定需求
- **检测器更新**：敏感词库、注入攻击模式库的持续更新

---

## 6. 后续演进方向（v2.0 之后，暂不排期）

- 多集群纳管（集团型客户的多地部署统一管理）
- 语义缓存（降低重复调用成本）
- A/B 路由与模型效果评估
- 与企业数据分类分级系统的对接（自动获取密级而非自行推断）
- 国际化与出海版本
