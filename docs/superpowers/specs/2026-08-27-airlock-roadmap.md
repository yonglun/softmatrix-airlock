## 1. 排期假设

- **产能**：1 人主导 + AI 辅助开发，全职投入
- **切片原则**：每个阶段结束都是能演示、能验收的状态
- **技术选型已定**：Go（Edge + 控制面）+ Next.js + 内嵌 Casdoor + LiteLLM
- **不含**：客户定制开发、售前支持、市场活动占用的时间

到 v2.0 与产品化完成累计约 **33–40 周**，**但客户 POC 在第 14 周左右即可开始**。

### 最可能超期的三个点

1. **P1.2 · Casdoor 各家 IdP 连接器的实际踩坑。** 文档上支持和真实企业环境跑通是两回事，老旧 AD 与自建统一认证平台尤其麻烦。
2. **P4 · 流式护栏的延迟调优。** 缓冲窗口与检出率的平衡没有标准答案，需反复实测。
3. **P1 结束后的第一次真实客户部署。** 私有化交付的环境问题只有在真实客户机房才会暴露。

## 3. 排序逻辑

**1. P0 不可跳过，但只要半天到一周。**
整个 P1 的配额方案建立在「LiteLLM 开源版的层级预算真的可用」这个事实上。LiteLLM 代码里存在 `premium_user` 运行时校验，文档标注与代码实际行为不一定一致。**用文档推断当地基是不可接受的**，必须实测。

**2. P1 用 LiteLLM 原生能力换时间。**
这是本次重排的核心。既然 `Org → Team → User → Key` 四级预算属开源，第一版就不必写配额引擎——那是 5–6 周的工作量，且是整个项目里正确性要求最高、最容易出错的部分（并发下的预扣结算）。把它推到 P2，第一版的工程风险大幅下降。

**3. Edge 从 P1 就存在，但只做透明直通。**
多花约 2 周，换取**接入端点与密钥格式永不变更**。私有化交付的产品，让已上线客户重新配置全部接入点的迁移代价极高。同时审计流从第一天起就在自己手里，不受 LiteLLM spend log 粒度限制。

**4. P2 紧接 P1，因为 P1 的能力缺口最扎眼的就是配额。**
P1 交付后立刻会遇到的客户异议是「我们部门树有五层」「超预算不能直接断」。这两条都在 P2 解决，所以 P2 排在护栏之前。

**5. P4 必须在 P5 之前。**
出境管控依赖脱敏能力，而脱敏是护栏检测器的一部分。反过来做会返工。

**6. P6 产品化在功能定型后做。**
完整的 License、Helm、升级回滚体系应在功能稳定后建设，否则随功能变更反复返工。P1.5 已提供做 POC 所需的最小交付能力。

**7. P7 放最后。** Agent/MCP 治理的行业标准仍在演进，过早实现容易白做。可按客户需求提前。

## 4. 阶段详情

### P0 · 可行性验证（0.5–1 周）

**目标**：用实测替代推断，确认 P1 的两个地基假设成立。

**任务**
1. **LiteLLM 管理端点无 License 可用性实测。** 起一个干净的 LiteLLM 开源容器（不配置任何 License），逐个验证：
   - `/organization/new`、`/organization/update`、组织成员管理
   - `/team/new`、`/team/member_add`、`/team/member_update`
   - `/user/new`、`/user/update`
   - `/key/generate`（带 `max_budget`、`budget_duration`、`models`、`tpm_limit`、`rpm_limit`）
   - `/key/update`（临时提额场景）
   - spend 查询端点
   - **记录每个端点的实际行为**：可用 / 报 `premium_user` 错误 / 静默降级
2. **组织层级映射方案验证。** 确认 Org → Team → User 三层的预算继承与叠加语义，验证「Airlock 任意深度组织树拍平到这三层」的可行方案与信息损失程度。
3. **流式缓冲窗口原型。** 验证出向护栏的缓冲策略对首字延迟的实际影响，产出实测数据。

**验收标准**
- 产出一份端点可用性清单，明确哪些能用、哪些被门禁
- 产出组织树拍平方案与已知信息损失说明
- 产出流式缓冲窗口的延迟实测数据

**分支决策**
- 若管理端点**全部可用** → 按本 Roadmap 执行
- 若**部分被门禁** → P1 配额范围收缩为「仅 Key 级预算」，并把 P2 的优先级提到 P1 之后立即执行
- 若**大面积被门禁** → P2 提前并入 P1，回退到 v1.0 Roadmap 的排期

---

### P1 · 控制面 + SSO + 新前端 + 透明 Edge（12–15 周）

**目标**：交付第一个可售、可装进客户机房的完整产品。

#### P1.1 骨架与透明 Edge（2–2.5 周）

- Go 单仓骨架：`cmd/edge`、`cmd/control`、`internal/`、`web/`
- PostgreSQL schema 与迁移框架
- LiteLLM 容器化部署，接入 3 家供应商（DeepSeek、通义千问、OpenAI）
- **透明直通 Edge**：`ak-` 密钥校验 → 映射到 LiteLLM 密钥 → 转发（含流式）→ 用量与审计落 ClickHouse
- **完整定价数据模型**：输入/输出单价、缓存命中价、思考 token 计费、阶梯价、按时间生效的价格版本

> **定价模型必须一次做对。** 国产模型计价规则复杂，事后修改会导致全部历史账单失真。这是 P1.1 里最重要的一件事，不要因为「先跑通」而简化。

**验收**：`ak-` 密钥调通国产与海外模型（含流式）；用量落库；成本核算与供应商账单一致。

#### P1.2 身份与组织（3–4 周）

- Casdoor 内嵌部署，Airlock 作为 OIDC 客户端接入
- **实测通过**的连接器：钉钉、企业微信、飞书、LDAP/AD
- Airlock 侧任意深度组织树、成员管理、通讯录同步
- RBAC：5 个内置角色 + 自定义角色，组织节点级授予
- **组织树 ↔ LiteLLM Org/Team/User 的映射与同步机制**（按 P0 验证的方案）

**验收**：企业用自家钉钉账号登录；管理员创建组织、分配角色；组织变更能正确同步到 LiteLLM 侧。

> **风险**：每个 IdP 连接器都必须在真实环境实测，不能只看 Casdoor 文档声称支持。建议尽早锁定可测试的真实环境。

#### P1.3 密钥与配额映射（2–2.5 周）

- 虚拟 Key 生命周期：申请 → 审批 → 签发 → 吊销（轮换属 LiteLLM Enterprise，由 Airlock 自建实现）
- 模型可见性白名单（映射到 LiteLLM `models` 参数）
- 配额配置界面：金额、Token、请求数、RPM/TPM/并发，映射到 LiteLLM 各级 `max_budget` / `budget_duration` / 限流参数
- **提额审批流**（Airlock 自建）：申请 → 审批 → 调 `/key/update` 提额 → 到期回收
- 告警通道：钉钉、企业微信、邮件
- IdP 侧用户禁用 → 其名下 Key 自动失效

**验收**：配额在 LiteLLM 侧正确生效并阻断；提额申请到期后额度自动回收，全程可审计。

#### P1.4 控制台（3–4 周）

- Next.js 骨架、登录态、布局系统、四工作台切换
- **平台管理**：总览、模型供应商、模型池、虚拟密钥、组织与成员、角色与权限、SSO 配置
- **我的空间**：我的密钥、我的用量与余额、申请提额、模型试用台
- **成本财务**：成本总览、配额策略、提额审批
- **安全合规**：仅审计检索（护栏页面在 P4 补全）

**验收**：五类角色各自能在对应工作台完成其核心任务，无需跳转到其他工作台。

#### P1.5 基础分析与交付包（1.5–2 周）

- 基础多维报表：按组织 / 成员 / 模型 / 时间的用量与成本下钻（读 ClickHouse）
- CSV / Excel 导出
- docker-compose 一键部署
- 离线镜像包（镜像 tar + 一键安装脚本）
- 基础 License 校验（到期时间 + 席位数）
- 部署文档与运维手册

**验收**：干净的、**完全无外网**的机器上，照文档 2 小时内部署成功；部署过程中每个错误都有明确排查指引。

### ▶ 版本节点：v1.0（约第 14 周）

**可以开始客户 POC。**

销售叙事成立：全新的企业级控制台 + 真正的企业 SSO + 组织化的配额与成本归属，已经明显超过 LiteLLM 开源版能给客户的东西。

**必须如实说明的能力缺口**（见 PRD §3.3）：
1. 深层组织的预算只能展示聚合、不能强制执行（受 LiteLLM 三层结构限制）
2. 超限只能阻断，不能降级
3. 无角色维度配额、无成本中心
4. 无内容护栏、无数据出境管控
5. 审计仅到调用元数据粒度

**已决策**：接受首批客户可能因缺少安全能力而拒绝的风险。此阶段接触客户的**主要目的是获取需求反馈**，用真实异议塑造 P2–P5 的产品细节，而非闭门想象。

### P2 · 自建配额引擎（5–6 周）

**目标**：摆脱 LiteLLM 的层级限制，实现产品的第一个真正差异点。

**交付物**
- 三维叠加判定：`min(组织额度, 角色基线, 个人额度)`，均为上限，无覆盖语义
- **任意深度组织树的配额强制执行**（Edge 接管判定，不再受 LiteLLM 三层限制）
- 角色基线额度（全局横切维度）
- **CostCenter** 实体与双维归属、双维配额、双口径报表
- 组织树语义：`严格` 与 `超售` 两种模式
- **Redis 两阶段预扣-结算**，含异常中断的对账兜底任务
- 超限行为分级：80% 告警 → 95% 升级 → 100% **降级** 或阻断 → 硬顶
- 降级路由：自动切换到低价模型池，响应头显式标示
- LiteLLM 侧预算退化为兜底防线（保留但不再是主判定点）

**验收标准**
- 五层深度的组织树，各级预算均能正确强制执行
- **并发压测不超发**，场景需覆盖「多个 Key 同时消耗同一组织额度」
- 超限自动降级到低价模型池，业务不中断，响应头正确标示降级信息
- 角色基线规则生效：同一用户在不同组织下均受其角色上限约束

**依赖**：P1

> **风险**：两阶段预扣-结算在异常路径（连接断开、进程崩溃、上游超时）下的正确性，是整个项目里最容易出错的地方。需要专门的故障注入测试。

---

### ▶ 版本节点：v1.5

配额能力全面超越所有竞品（任意深度组织树 + 角色横切维度 + 双归属维度 + 超限降级）。这是最容易向客户讲清楚、也最容易被验证的差异化。

### P3 · 审计与分析深化（4–5 周）

**目标**：让行为查得到、合规交得了差、成本优化说得出数。

**交付物**
- 审计留存策略配置：不留存 / 脱敏后留存 / 全量留存，含留存期限与到期处理
- 审计日志哈希链与完整性校验，只读导出
- 管理操作审计（配置变更前后值、操作人、来源 IP）
- 审计检索：按人、组织、成本中心、模型、时间、关键词、拦截状态组合查询
- 成本财务工作台完整版：多维下钻、成本中心账单、趋势、月度预测、突增异常告警
- 性能指标：TTFT、TPS、错误率、限流率，按模型横向对比
- **优化建议**：模型替换的成本节省估算与质量风险评估
- 定时报表：推送到钉钉/企微/邮件

**验收标准**
- 千万级记录下多维下钻查询响应 < 2s
- 各维度账单之和与总账单**逐分对齐**
- 审计日志完整性校验通过；篡改任一条记录后校验失败

**依赖**：P2（需要成本中心与完整归属维度）

---

### P4 · 内容护栏 L2（5–6 周）

**目标**：做出企业敢在生产环境开启的护栏。

**交付物**
- `Guardrail Provider` 可插拔接口（含超时与 fail-open/fail-closed 策略）
- 内置检测器：正则/词典引擎、敏感词库（支持导入客户自有词库）
- 集成开源 PII 识别引擎
- 集成小模型分类器（提示注入、越狱、内容安全分类）
- 策略编排引擎：检测器组合 × 作用范围 × 动作 × 例外名单，按组织树继承
- **影子模式**（必交付项）：只记录不拦截，展示命中分布、抽样样本、估算误报率
- 拦截记录与误报申诉流
- **流式出向护栏**：滑动缓冲窗口，可配置窗口大小，命中时中断并标记
- Console：安全合规工作台补全（安全态势、护栏策略、拦截记录、误报申诉处理）

**验收标准**
- 影子模式在真实流量下跑出可信的误报率数据
- 流式首字延迟增量**可量化并在控制台展示**
- 护栏引擎故障时按配置的 fail-open/fail-closed 策略正确降级
- 误报申诉可一键加入例外，全程审计

**依赖**：P3；**P1 阶段的客户 POC 反馈应直接影响本阶段的策略设计**

> **风险**：这是整个 Roadmap 中工程复杂度最高的阶段。P0 的缓冲窗口原型数据在此兑现价值——如果原型显示延迟不可接受，需在本阶段开始前重新设计方案。

---

### P5 · 数据主权 L3（3–4 周）

**目标**：实现头号差异化卖点。

**交付物**
- 四级密级体系（可自定义名称与层数）
- 密级判定优先级链：请求头 → Key 声明 → 组织默认 → 内容自动推断
- 供应商境内/境外/自建标记
- 出境策略矩阵（密级 × 目的地），控制台上呈现为可点选的表格
- 脱敏后出境（复用 P4 的检测器）
- 出境台账：逐条留痕，含密级判定依据与脱敏差异摘要
- 合规报告导出：等保测评材料、生成式 AI 服务管理办法自查表

**验收标准**
- 机密级数据发往境外模型被拒绝、留痕，且可导出为合规材料
- **无绕过路径**：需专门做绕过测试（改请求头、换 Key、直连 LiteLLM 端口等）
- 脱敏后出境的差异摘要准确反映脱敏内容，但不泄露原文

**依赖**：P4（脱敏能力）

---

### ▶ 版本节点：v2.0

竞品对标表里「只有 Airlock 有」的两个格子（数据主权与出境管控、三维叠加配额）被真正填上。产品具备完整的差异化叙事。

### P6 · 产品化交付（4 周）

**目标**：从「能装」到「好卖好维护」。

**交付物**
- Helm Chart（K8s 部署）
- 完整 License 体系：机器指纹绑定、节点数、席位数、到期宽限期、到期后降级为只读
- 版本化 API 与数据库迁移，含回滚脚本与跨版本升级路径文档
- 高可用配置：Edge 多实例、Control Plane 主备、存储外接
- 备份与恢复流程
- **自诊断页面**：数据库连通性、供应商可达性、证书有效期、License 状态
- 信创数据库适配验证（人大金仓 / openGauss）

**验收标准**
- K8s 与单机双形态均可交付
- 一次跨版本升级演练成功，并成功回滚
- 自诊断页面能定位至少 8 类常见环境问题
- 在信创数据库上完整跑通功能回归

**依赖**：P5

### P7 · Agent / MCP 治理 L4（5–6 周）

**目标**：抢 2026 年 AI 治理的新战场。

**交付物**
- MCP Server 注册与纳管，工具级白名单
- Agent 服务身份与发起人自然人身份绑定
- 工具调用审计与越权检测
- 多轮会话上下文的累积注入检测

**验收标准**
- Agent 的每次工具调用可追溯到发起的自然人
- 越权的工具调用被拦截并告警
- 配额与审计正确归属到自然人而非服务账号

**依赖**：P6

**说明**：行业标准仍在演进。可根据客户需求提前，也可在标准更清晰后再做。
