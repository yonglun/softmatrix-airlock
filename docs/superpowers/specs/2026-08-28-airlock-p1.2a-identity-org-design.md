## 1. 范围

### 1.1 P1.2 的切分

Roadmap 的 P1.2「身份与组织」包含五条工作流。本设计只覆盖前半：

| # | 工作流 | 归属 |
|---|---|---|
| 1 | Casdoor 内嵌 + OIDC 接入 + 登录态 | **P1.2a（本设计）** |
| 2 | 钉钉/企微/飞书/LDAP 连接器实测 | 机会性插入（见 §7.3） |
| 3 | 任意深度组织树 + 成员管理 + 通讯录导入 | **P1.2a（本设计）** |
| 4 | RBAC（5 内置角色 + 自定义 + 树上继承） | P1.2b |
| 5 | 组织树 ↔ LiteLLM Org/Team 映射与同步 | P1.2b |

切分依据：P1.2a 做完即可独立验收——用真实账号登录、建组织树、管成员。P1.2b 依赖 P1.2a 的用户与组织数据。

### 1.2 本阶段明确不做

- ❌ RBAC 与权限判定（P1.2b）——P1.2a 只有 bootstrap 管理员这一种权限概念
- ❌ 向 LiteLLM 同步组织结构（P1.2b）
- ❌ 控制台前端（P1.4）——P1.2a 只交付管理 API，验收走 HTTP 调用
- ❌ 密钥申请审批流（P1.3）

## 2. 进程与部署形态

### 2.1 单二进制 + 子命令

```
bin/airlock                        # 唯一分发物
├── airlock edge                   # 数据面：ak- 鉴权 → 转发 → 计费（P1.1 已有）
├── airlock control                # 管理面：OIDC 登录、组织树、成员（P1.2a 新增）
└── airlock migrate                # 数据库迁移（从 edge -migrate-only 提取）
```

**决策理由**：私有化交付中，分发两个二进制会带来版本错配事故（客户升级漏拷一个文件，edge 与 control 版本不一致）。单文件在物理上杜绝这种情况，同时运行时仍是两个进程，故障隔离不受影响——满足 PRD 决策 D10「Control Plane 宕机不影响推理链路」。

**被否决的方案**：
- 管理 API 挂进 Edge 进程 —— 违反 D10，管理面慢查询会拖垮推理链路。
- `cmd/edge` + `cmd/control` 两个独立二进制 —— Go 惯例做法、完全可行，但把版本错配风险留给了客户运维纪律。

### 2.2 代码结构改动

| 动作 | 说明 |
|---|---|
| 新增 `cmd/airlock/main.go` | 只做子命令分发，不含业务逻辑 |
| `cmd/edge/main.go` 的 `run()` → `internal/app/edge.go` | 逻辑整体搬迁，行为不变 |
| 新增 `internal/app/control.go` | 管理面进程装配 |
| 新增 `internal/app/migrate.go` | 迁移子命令 |
| 删除 `cmd/edge/` | 由 `cmd/airlock` 取代 |
| Makefile 的 `build` / `migrate` 目标 | 同步更新 |

**包依赖边界（靠 review 守，编译器不管）**：
- 共享：`internal/config`、`migrations`、`internal/apikey`、`internal/pricing`、`internal/usage`
- `internal/control` **不得** import `internal/edge`
- `internal/edge` **不得** import `internal/control`

### 2.3 对 P1.1 已验收内容的影响

`make migrate` 当前指向 `go run ./cmd/edge -migrate-only`，改为 `go run ./cmd/airlock migrate`。需同步更新：
- `Makefile`
- `docs/superpowers/findings/2026-08-27-p1.1-acceptance.md` 中引用该命令处

Edge 的 HTTP 行为、鉴权逻辑、计费链路**零改动**。P1.1 的 26 个 `internal/edge` 测试必须全部保持绿色（§7.2 验收项 7）。

## 3. 身份接入

### 3.1 Casdoor 是配置，不是代码依赖

Airlock 只实现**标准 OIDC 客户端**（authorization code flow + PKCE）。代码中不出现 `casdoor` 字样，不引入 Casdoor SDK。

| 形态 | 实现方式 |
|---|---|
| 内嵌 Casdoor | `deploy/docker-compose.yml` 增加一个 Casdoor 服务 + 预置 application 配置 |
| 客户自有 IdP（Casdoor / Keycloak / 其他 OIDC） | 改三个环境变量，代码零改动 |

新增配置项：

```
OIDC_ISSUER              # 如 http://localhost:8000
OIDC_CLIENT_ID
OIDC_CLIENT_SECRET
OIDC_REDIRECT_URL        # 如 http://localhost:8081/auth/callback
AIRLOCK_BOOTSTRAP_ADMIN  # email 或 OIDC sub，见 §3.4
CONTROL_LISTEN_ADDR      # 默认 :8081
RECONCILE_INTERVAL       # 离职对账周期，默认 5m，见 §6.1
```

**这条边界的价值**：钉钉/企微/飞书的对接全部发生在 Casdoor 内部，是连接器**配置**问题，不是 Airlock 的**代码**问题。这正是 PRD 决策 D3 选择 Casdoor 而非自建连接器的全部意义——新增一家 IdP 不需要改 Airlock 一行代码。

### 3.2 会话：服务端 session

登录成功后 control 签发 `HttpOnly + Secure + SameSite=Lax` cookie，对应一条 Postgres 中的 session 记录。

**为什么不用无状态 JWT**：§5 的离职失效要求能**主动踢人下线**。无状态 JWT 在过期前无法撤销，除非维护黑名单表——那已等价于 session 表且更复杂。session 表还顺带满足 PRD FR-1.1 的「登录、登出、会话过期均产生审计事件」。

代价是每个管理面请求多一次 session 查询。管理面 QPS 为个位数量级，可忽略，**且完全不碰 Edge 热路径**。

**两套鉴权彻底独立**：Edge 认 `ak-` 密钥，control 认 session cookie，互不感知、互不影响。

### 3.3 OIDC claims 映射

| OIDC claim | Airlock 字段 | 说明 |
|---|---|---|
| `sub` | `users.external_id` | 唯一标识，跨 IdP 稳定 |
| `email` | `users.email` | |
| `name` / `preferred_username` | `users.display_name` | 取先有的那个 |

每次登录刷新 `email`/`display_name`/`last_login_at`。

### 3.4 Bootstrap 管理员

组织树和角色初始为空，第一个人凭什么能登进去建组织——这是真实的落地卡点。

**方案**：配置项 `AIRLOCK_BOOTSTRAP_ADMIN`（email 或 OIDC sub）。该用户首次登录时自动标记为平台管理员并写审计。

**安全约束**：`AIRLOCK_BOOTSTRAP_ADMIN` 为空、且系统中一个管理员都没有时，`airlock control` **启动即报错退出**。不允许出现「谁都能登、登进去就是管理员」的窗口期。

P1.2a 尚无完整 RBAC，「平台管理员」暂时用 `users` 表上的一个布尔位表达；P1.2b 引入 `role_grants` 后迁移为正式角色。

## 4. 数据模型

### 4.1 新增表

```sql
CREATE TABLE users (
    id              TEXT PRIMARY KEY,
    external_id     TEXT NOT NULL UNIQUE,      -- OIDC sub
    email           TEXT NOT NULL,
    display_name    TEXT NOT NULL DEFAULT '',
    status          TEXT NOT NULL DEFAULT 'active'
                    CHECK (status IN ('active','disabled')),
    is_platform_admin BOOLEAN NOT NULL DEFAULT false,  -- P1.2b 迁移为 role_grants
    primary_org_id  TEXT REFERENCES organizations(id) ON DELETE RESTRICT,
    last_login_at   TIMESTAMPTZ,
    reconciled_at   TIMESTAMPTZ,               -- 最近一次与 IdP 对账时间
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX users_primary_org_idx ON users(primary_org_id);
CREATE INDEX users_status_idx ON users(status);

CREATE TABLE sessions (
    id            TEXT PRIMARY KEY,            -- session token 的 sha256，不存原值
    user_id       TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    expires_at    TIMESTAMPTZ NOT NULL,
    last_seen_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    ip            TEXT NOT NULL DEFAULT '',
    user_agent    TEXT NOT NULL DEFAULT '',
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX sessions_user_idx ON sessions(user_id);
CREATE INDEX sessions_expiry_idx ON sessions(expires_at);
```

`sessions.id` 存哈希不存原值——与 `api_keys.key_hash` 同一原则：数据库泄露不等于会话被劫持。

### 4.2 `organizations` 增列

```sql
ALTER TABLE organizations
  ADD COLUMN external_source TEXT,   -- 'dingtalk'/'wecom'/'feishu'/'ldap'；手工建的为 NULL
  ADD COLUMN external_id     TEXT,
  ADD COLUMN updated_at      TIMESTAMPTZ NOT NULL DEFAULT now();

CREATE UNIQUE INDEX organizations_external_idx
  ON organizations(external_source, external_id)
  WHERE external_source IS NOT NULL;
```

用于导入时识别「这是同一个 IdP 节点」，实现幂等重复导入。

### 4.3 `api_keys.user_id` 加外键

当前 `api_keys.user_id` 是裸 `TEXT`、无外键。P1.2a 将其指向 `users(id)`。

> **⚠️ 涉及删数据**：P1.1 端到端验收往 `api_keys` 写入过一行 `user_id='user1'`，该用户在 `users` 表中不存在，直接加外键会失败。迁移需先清理这行验收残留数据。
>
> 这一步在实施计划中**单列为一个步骤并显式说明**，不与 schema 变更混在一起悄悄执行。执行前需确认目标库中该行确为 P1.1 验收残留、而非真实业务数据。

### 4.4 刻意不建 `org_memberships` 表

**决策**：P1.2a 只用 `users.primary_org_id` 表达归属，不建多归属关系表。

**理由**：「一个人在多个组织节点」的真实语义是**权限**（我在 B 部门有管理权），而非**归属**（我是 B 部门的人）。前者由 P1.2b 的 `role_grants(user, org, role)` 表达，后者一个人只有一个。计费归属由主组织唯一确定，花名册的第二归属不产生实际作用。

**已接受的代价**：若日后确认需要「一人同时在多个组的花名册里」，需补一张表。判断该需求不会出现。

## 5. 组织树管理

### 5.1 基本操作

复用 P1.1 已有的 `organizations` 表（`parent_id` 邻接表 + `path` 物化路径）。管理 API 提供：

| 操作 | 约束 |
|---|---|
| 创建节点 | 指定 `parent_id`（根节点为 NULL）；同级重名允许（靠 ID 区分） |
| 改名 | 不影响 `path`（`path` 由 ID 构成） |
| 移动子树 | 需重算被移动子树所有后代的 `path`，单事务内完成 |
| 删除节点 | **有子节点、有关联 Key、有历史用量记录时一律拒绝**，返回明确原因 |
| 查询子树 | 用 `path` 前缀匹配（已有 `text_pattern_ops` 索引） |

删除保护既有 schema 层的 `ON DELETE RESTRICT`，也要有应用层的友好报错——直接把 Postgres 的外键错误抛给用户不可接受。

### 5.2 导入：三步，绝不一键覆盖

流程：**拉取 → 差异预览 → 确认应用**。

差异分三类，默认动作不同：

| 差异类型 | 判定依据 | 默认动作 | 理由 |
|---|---|---|---|
| **新增** | IdP 有、Airlock 无此 `external_id` | ✅ 默认勾选 | 纯增量，安全 |
| **改名** | `external_id` 相同、`name` 不同 | ⬜ 默认不勾选 | Airlock 侧可能**故意**改过名，不该被 HR 系统覆盖 |
| **消失** | Airlock 有此 `external_id`、IdP 已无 | ⬜ 默认不勾选，仅标记 `orphaned` | 该节点下可能挂着 Key、历史账单、子节点 |

**核心原则：导入永不删除任何东西。** 「消失即删除」是这类同步功能最经典的事故来源——HR 系统一次组织调整就能删掉半个计费结构。最多标记为孤儿，由管理员人工判断。

**已接受的代价**：会累积需要人工清理的孤儿节点。这是刻意用「需要人工维护」换「不可能误删」。

### 5.3 幂等

同一份 IdP 数据重复导入不产生重复节点——依据 `(external_source, external_id)` 唯一索引。

## 6. 离职对账

### 6.1 机制

后台 reconciler，默认 5 分钟一轮（可配 `RECONCILE_INTERVAL`）：

1. 从 IdP 拉取全量用户状态（私有化场景用户量为千级，全量比增量简单且不会漏）
2. Airlock 中为 `active` 但 IdP 中已禁用/已删除 → `users.status = 'disabled'`
3. **级联**：
   - 吊销该用户名下所有 `api_keys`（`status = 'revoked'`）
   - 删除其所有 `sessions`（立即踢下线）
4. 全程写审计事件

登录时额外做一次校验，覆盖「刚被禁用但还没到对账周期」的情况。

### 6.2 为什么不在 Edge 热路径校验

P1.1 定下的性能预算是「Edge 引入的额外延迟 < 3ms（P99）」。每请求增加一次用户状态查询会直接冲击该预算。分钟级窗口期是为保住热路径性能而**刻意接受**的代价。

**已接受的风险**：离职到 Key 失效之间有最长一个对账周期的窗口。若客户要求秒级，需在 P2 重新评估（届时 Edge 已有配额引擎与 Redis，可复用其缓存层做低成本的状态校验）。

### 6.3 反向恢复不自动

IdP 中重新启用某人，`users.status` 恢复 `active`，但**已吊销的 Key 不会自动复活**。吊销在产品语义上不可逆，需重新走申请流程。

此行为必须写入运维文档，否则会被当作 bug 上报。

## 7. 测试与验收

### 7.1 测试策略

| 对象 | 策略 | 理由 |
|---|---|---|
| OIDC 流程 | 单测用极简 mock OIDC provider（覆盖 authorize / token / userinfo 三个端点） | 每个单测都起 Casdoor 容器会拖垮 `make test` |
| 真实 Casdoor | 仅在集成验收时起容器跑一遍完整登录 | |
| 组织树 / 导入 | Postgres 集成测试，复用已有 docker-compose | |
| 离职对账 | 单测用 mock IdP 客户端，验证级联吊销与踢下线 | |

### 7.2 验收标准

| # | 验收项 |
|---|---|
| 1 | 用 Casdoor 本地账号完成 OIDC 登录并拿到有效 session |
| 2 | bootstrap 管理员机制生效；未配置且无管理员时 `airlock control` 启动即报错退出 |
| 3 | 建三层组织树；改名、移动子树正确；删除有子节点的节点被拒绝并给出明确原因 |
| 4 | 从 LDAP 导入组织树，新增/改名/消失三类差异分类正确，默认勾选行为符合 §5.2 |
| 5 | 重复导入不产生重复节点 |
| 6 | 禁用一个用户 → 一个对账周期内其 Key 变 `revoked`、session 被清除、审计有记录 |
| 7 | **Edge 热路径零改动**：`internal/edge` 的 26 个测试全绿，P1.1 延迟基线无回归 |
| 8 | `airlock edge` / `airlock control` / `airlock migrate` 三个子命令均可用；`make build` 产出单一 `bin/airlock` |

### 7.3 连接器实测的诚实边界

**没有真实钉钉/企微/飞书租户时，验收文档中一律标注「未实测」，不写「支持」二字。**

这条纪律来自 P1.1 的教训：`gpt-5.6-luna` 那个 usage 块形状的 bug（`choices` 非空而非空数组）只有真实上游能暴露，所有单测的 mock 都用了「标准」形状因而全部漏掉。IdP 连接器同理——Casdoor 文档声称支持，与在某个客户的真实钉钉租户里跑通，是两件事。

若期间取得真实租户，按工作流 2 机会性插入实测，并将结果补入验收文档。

## 8. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| IdP 连接器真实环境踩坑 | Roadmap 已将其列为 P1.2 最可能超期项 | 尽早取得任一真实租户；无租户时诚实标注未实测，不把「支持」写进交付物 |
| 子命令重构碰坏 Edge | P1.1 已验收的数据面回归 | `internal/edge` 测试全绿作为硬性验收项；`run()` 逻辑整体搬迁而非重写 |
| 移动子树时 `path` 重算出错 | 组织树数据损坏，影响计费归属 | 单事务内完成；专门的测试覆盖多层嵌套移动 |
| 导入积累孤儿节点 | 长期需人工清理 | 已接受，是「不可能误删」的对价；控制台提供孤儿节点筛选视图（P1.4） |
| 对账窗口期内离职者仍可调用 | 最长一个周期的越权使用 | 已接受；登录时补一次校验；客户要求秒级则 P2 重评 |

## 9. 关键决策记录

| 编号 | 决策 | 理由 |
|---|---|---|
| D1.2a-1 | 单二进制 + 子命令，而非两个独立二进制 | 私有化交付杜绝版本错配 |
| D1.2a-2 | Airlock 只做标准 OIDC 客户端，不依赖 Casdoor SDK | 新增 IdP 是配置问题而非代码问题；客户自有 IdP 免费支持 |
| D1.2a-3 | 服务端 session，不用无状态 JWT | 离职要能主动踢下线；JWT 黑名单等价于 session 表且更复杂 |
| D1.2a-4 | 不建 `org_memberships` 表 | 多节点的真实语义是权限（P1.2b 的 role_grants），非归属 |
| D1.2a-5 | 导入永不删除，最多标记孤儿 | 「消失即删除」是同步功能最经典的事故源 |
| D1.2a-6 | 离职分钟级对账，不在 Edge 热路径校验 | 保住 P1.1 的 < 3ms 延迟预算 |
| D1.2a-7 | 吊销不可逆，IdP 恢复不自动复活 Key | 产品语义明确优于「聪明」的自动化 |
