## 1. 范围

本期的主题只有一个：**把 P1.3a/b/c 已经做完、但在控制台上完全够不着的密钥能力接出来**。轮换、按子树批量吊销、全局紧急吊销这三件事今天只能用 `curl` 打，界面上没有任何入口。

### 做什么

- **平台管理 → 虚拟密钥页**：左树右列表；按节点查、可切子树；直接签发；单把吊销；单把轮换；子树批量吊销（先预览再确认）；全局紧急吊销（隔离的危险区 + 手打确认串）。
- **我的空间 → 我的密钥页**：列出「我是责任人」的全部密钥；自助轮换（可选共存窗口）；自助吊销。
- 后端补四处，见 §4。
- 把 P1.4a 内联在组织页里的组织树抽成共享组件。

### 明确的范围外

| 项 | 去向与理由 |
|---|---|
| 密钥的额度 / 限流编辑 | 今天**没有** PATCH 类接口。改不了，本期不做半截入口 |
| 用量与余额 | 要 ClickHouse 分析接口，P1.5 |
| 模型池、模型供应商、模型试用台 | 无任何后端，与 P1.4a 同一判断 |
| 角色与权限页 | 后端齐全，但与本期主题（密钥生命周期）不同，留 P1.4c，不混在一期里 |
| 组织页补齐（改名 / 移动 / 密钥边界开关 / LDAP 导入） | 同上，留 P1.4c。改名与密钥边界开关是 P1.4a 验收记录里记下的空缺 |

## 2. 设计前的查证

沿用「先查证既有代码、不靠推断」的纪律。四条查证直接改变了设计，其中两条把可用性问题揭成了安全问题。

| # | 查证 | 对设计的影响 |
|---|---|---|
| **C1** | `ListByOrg` 是**单节点**查询（`keystore.go`：`WHERE org_id = $1`），不是子树；而 `RevokeByOrgSubtree` 吊销的是**整个子树**（`path = $1 OR path LIKE $1 \|\| '/%'`，且限定 `status IN ('active','pending')`） | **能开火，却看不见会打到谁**。子树批量吊销没有任何办法预览影响范围。直接决定 D1 |
| **C2** | `KeyIssuer.Rotate` 里 `window == 0` 会被替换成**默认 24 小时**，`window < 0` 直接 `ErrWindowTooLong` | **API 根本无法表达「轮换并立刻废掉旧凭据」**。密钥泄露时轮换不是止血手段——旧凭据仍有效 24 小时 |
| **C3** | `HandleRotate` 允许**责任人本人或**节点上持 `key:write` 的管理员；而 `HandleRevoke` **只认** `key:write`，没有 owner 分支 | 与 C2 合起来：泄露了密钥的开发者，既不能立刻废掉旧凭据，也无权吊销，**没有任何自助止血路径**。直接决定 D2 |
| **C4** | `KeyStore` 没有任何按用户的查询方法；`keyView`（`keyapi.go:29`）不含 `PrevKeyExpiresAt`/`RotatedAt`，尽管 `APIKey` 模型里两者都有 | 「我的密钥」要连 store 方法一起补；轮换后界面说不出「旧凭据还能用多久」。决定 D3、B4 |

## 3. 关键决策

### D1：子树查询与子树吊销共用同一套节点选择子句

新增的 `KeyStore.ListByOrgSubtree(ctx, orgPath)` 与既有的 `RevokeByOrgSubtree` 使用**逐字相同**的节点选择子句：

```sql
org_id IN (SELECT id FROM organizations WHERE path = $1 OR path LIKE $1 || '/%')
```

这是这条查询存在的理由。子树批量吊销是不可逆操作，预览的唯一价值是「让人看见即将发生什么」；两处匹配规则一旦分叉，预览就是在撒谎，比没有预览更危险。

**预览是快照，不是锁。** 预览与确认之间行仍可能变（另一个管理员刚签发了一把、审批 worker 刚落一把）。因此确认后的成功提示以响应里的实际 `revoked` 条数为准，而不是回显预览时算出的 N。这个 TOCTOU 缺口不打算用加锁消除——为一个「break glass 前看一眼」的功能引入跨请求锁不划算，如实告诉用户实际吊销了多少更诚实。

浏览用的列表返回子树下**全部**状态的密钥（包括已吊销的历史记录，管理员需要看得见）；而确认文案里的「将吊销 N 把」只数 `active`/`pending`——与 `RevokeByOrgSubtree` 的 `WHERE` 条件对齐。

### D2：责任人本人可以吊销自己的密钥

`HandleRevoke` 增加 owner 分支，判定与 `HandleRotate` 完全对齐：**责任人本人，或在该密钥所属节点上持 `key:write` 的管理员**。

理由是 C2 + C3 合起来构成的缺口：密钥泄露时，轮换不是止血手段（旧凭据仍有效 24 小时），而吊销他没有权限。要止血只能去找管理员——这恰恰是泄露事件中最不该有的延迟。自己吊销自己的密钥，爆炸半径限于自身。

**代价要如实说**：如果这把密钥正在跑生产，责任人手滑就能当场断服。这靠界面的二次确认拦，而不是靠收走权限——把止血能力从责任人手里拿走，代价比手滑更大。

考虑过另一条路：让 `Rotate` 支持显式的零共存窗口。否决的理由是语义拧巴——共存窗口是为**计划内轮换**设计的，把它重载成事故响应通道，既模糊了两件事的边界，事后还留着一把 active 的密钥，而事故响应真正想要的是「这把密钥现在就作废」。

### D3：`keyView` 增加轮换状态字段

补 `rotated_at`、`prev_key_expires_at` 两个可空字段。纯增量，不动既有字段。

没有它们，轮换完界面只能说「轮换成功」，说不出**旧凭据还能用多久**——而共存窗口的存在意义，就是给客户端一段替换凭据的时间。这段时间还剩多少，是这个功能唯一需要被看见的信息。

### D4：破坏性操作与后端已有的两道闸对齐

- **子树批量吊销**：先拉子树列表展示命中项与条数，再确认。
- **全局紧急吊销**：单独隔离的「危险操作」区块，必须在输入框**原样手打** `REVOKE ALL KEYS` 才启用按钮。前端**不代填**这个字符串。

后端 `HandleRevokeAll` 的注释写得很清楚：全局权限管住「谁能按」，确认字符串管住「不会手滑按到」。前端若从常量里自动填上确认串，第二道闸就沦为摆设——那不是省一步操作，那是把后端刻意加的防护拆了。

提示文案会告诉用户该打什么（否则无人知晓），这与「必须手打」不矛盾：这道闸防的是手滑，不是防猜。

### D5：危险区的可见性用 `global_permissions` 判定

危险操作区块只在调用者持有全局 `key:revoke_all` 时渲染。

这看似与 P1.4a 的 D2（「不能用 `global_permissions` 判定可见性」）打架，其实不。P1.4a 那条的理由是 `global_permissions` 会漏掉**节点级**授予；而 `key:revoke_all` 是 `ScopeGlobal` 权限，**只可能全局持有**，不存在节点级授予可漏。对它而言 `global_permissions` 恰好是准确的判定依据。

且这只是界面便利——隐藏入口不是授权。真正的闸仍在后端的路由中间件（`Permission: authz.PermKeyRevokeAll, Target: TargetGlobal()`），验收里会专门用无权限账号直接打接口确认 403。

### D6：抽两个共享组件，不抽第三个

- `components/OrgTree.tsx`：P1.4a 把 `toTree` 与树渲染内联在组织页里，本期出现第二个消费者。
- `components/PlaintextKeyModal.tsx`：一次性 `ak-` 明文弹窗，本期出现**三个**消费者（直接签发、平台侧轮换、我的密钥轮换）。

**不抽**密钥表格：两个页面的列不同（平台侧要「责任人」，我的密钥要「所属节点」），共享收益抵不上参数化的代价。抽象等第三个消费者出现再说——这也正是前两个组件现在该抽的理由。

`toTree` 抽出来后补上它一直没有的单测，包括「可见范围不含根节点时以最浅的那些作为根」这条回退分支。

## 4. 后端补口

四处，都小且有先例。

### B1：子树查询 —— `GET /api/orgs/{id}/keys?subtree=true`

复用既有路由 pattern，不新开路由。新增 `KeyStore.ListByOrgSubtree(ctx, orgPath)`，SQL 见 D1。

权限不变（`key:read` on `{id}`，`TargetFromPath`）：节点上的授予本就覆盖其子树，这一点 P1.4a 的验收已经在真实链路上验证过（`org_admin@p14root` 能看到 `p14rd` 下的申请）。因此子树读不需要额外的权限逻辑。

缺省（不带参数）行为完全不变，仍是单节点查询。

### B2：责任人自助吊销 —— `HandleRevoke` 加 owner 分支

判定改为 `u.ID == k.UserID || resolver.Can(..., PermKeyWrite, &k.OrgID)`，与 `HandleRotate` 的写法对齐。

### B3：`keyView` 增加 `rotated_at`、`prev_key_expires_at`

改 `keyView` 结构体与 `viewOf`。两个字段都是 `*time.Time`，序列化为可空。

### B4：`GET /api/keys/mine`

- 新增 `KeyStore.ListByUser(ctx, userID)`（`WHERE user_id = $1 ORDER BY created_at DESC`）
- 新增 `KeyAPI.HandleMine`，从上下文取调用者、只返回本人的密钥
- 路由 `AccessAuthenticated`，按调用者本人过滤，与 `GET /api/requests` 同一先例——不需要节点级判定，因为过滤维度就是调用者自己

本期**只新增这一条**路由；`?subtree=true` 复用既有 pattern。

### 虚拟密钥页（`/platform/keys`）

左侧 `OrgTree`，右侧随选中节点变化：

- 工具条：`[签发密钥]`、`[包含子树]` 开关
- 表格列：名称、前缀、责任人、状态、模型、创建时间、轮换状态、操作（轮换 / 吊销）
- 「轮换状态」列在 `prev_key_expires_at` 未过期时显示「旧凭据 X 前仍可用」，否则显示 `rotated_at` 或空
- 底部：`[吊销该子树的全部密钥]` → 预览弹窗（列出命中项 + 「将吊销其中 N 把」）→ 确认 → 成功提示显示响应里的实际条数
- 危险操作区：仅在持全局 `key:revoke_all` 时渲染，见 D4、D5

### 我的密钥页（`/my/keys`）

- 数据来自 `GET /api/keys/mine`
- 表格列：名称、前缀、所属节点、状态、模型、轮换状态、操作（轮换 / 吊销）
- 轮换弹窗可填共存窗口（默认 24 小时、上限 30 天，与后端 `maxRotationWindow` 一致），拿到明文走 `PlaintextKeyModal`
- 吊销走二次确认
- 「所属节点」客户端 join `/api/orgs` 取节点名，取不到就显示原始 ID——与 P1.4a 同样的降级方式

### 错误处理

沿用 P1.4a 的 D5：后端的错误文案本来就是写给人看的中文，且随业务逻辑一起维护，前端直接透传 `ApiError.message`，不另维护一份文案表。本期会真实用到的几条：`key_not_active`（轮换已吊销的密钥 → 409）、`window_too_long`（→ 400）、`confirm_required`（→ 400）、`permission_denied`（→ 403）。

## 6. 测试策略

沿用 P1.4a 的三层：Go 单测 / 集成测试（真实 Postgres）、前端 Vitest（纯逻辑与条件渲染）、手工端到端验收。不引入 Playwright（P1.4a D7 已定）。

**Go 侧**

- `ListByOrgSubtree`：**同前缀兄弟节点**（`/root/rd` vs `/root/rd2`，本项目**第五次**测这个陷阱）、`active`/`pending`/`revoked` 都返回、空子树返回空切片
- `HandleRevoke`：责任人本人可吊销（新增）、节点上持 `key:write` 可吊销（回归）、无关用户 403
- `keyView`：轮换后 `rotated_at`/`prev_key_expires_at` 确实出现在 JSON 里
- `ListByUser` + `HandleMine`：只返回本人的、跨节点都返回、未登录 401
- 路由机械检查：`GET /api/keys/mine` 加进覆盖清单

**前端 Vitest**

- `toTree`：层级组装、「可见范围不含根节点」的回退分支
- 危险区仅在持 `key:revoke_all` 时渲染
- 确认串未原样打出时按钮保持禁用

## 7. 验收标准

对真实运行的 Postgres + Casdoor + control 完整链路验证，每项记录真实输出。

1. 虚拟密钥页选中节点看到该节点的密钥；打开「包含子树」后看到子树下全部
2. 直接签发拿到一次性 `ak-` 明文，关闭后刷新不再出现
3. 单把轮换：`id` 不变、`key_prefix` 变、拿到新明文，界面显示旧凭据到期时间
4. 单把吊销：状态变为 `revoked`
5. **子树吊销预览命中的那一批，与实际吊销的那一批一致；同前缀兄弟节点毫发无伤**（第五次踩这个陷阱的证据）
6. 全局紧急吊销：确认串不对 → 按钮禁用、直接打接口 400；正确 → 返回实际吊销条数
7. 无 `key:revoke_all` 的账号看不到危险区，且**直接打接口 403**（证明隐藏入口不是授权）
8. 我的密钥页只看到本人的密钥（跨节点都在），别人的密钥不出现
9. 责任人自助吊销自己的密钥成功；吊销他人的密钥 403
10. `internal/edge` 33 PASS / 0 FAIL，零回归

### 一条操作纪律

**全局紧急吊销（验收项 6）必须排在验收序列的最后一项。** 它会吊销**全系统**密钥，包括前几期留在开发库里的夹具；先做它，后面所有项的夹具就都没了。这与 P1.3b 记下的「手工 E2E 与 `make test` 不能共库并发」是同一类坑，同样值得在验收文档里写明。
