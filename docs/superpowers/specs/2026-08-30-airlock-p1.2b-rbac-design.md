| 项目 | 内容 |

## 1. 背景与范围

P1.2a 交付了身份接入与组织树，但权限只有 `users.is_platform_admin` 一个布尔位，且**这个布尔位从未被当作授权判据读取过**——合并前的代码复审确认，所有 `/api/*` 接口只校验「已登录」。本阶段补齐真正的权限模型与判定层。

Roadmap 原本把 RBAC 与 LiteLLM 同步一起放在 P1.2。二者几乎不相干：RBAC 触碰 users / 组织树 / HTTP 中间件，LiteLLM 同步触碰组织存储 + 一个对外 HTTP 客户端；唯一交集是「同步管理接口需要 RBAC 保护」这一单向依赖。因此拆开，RBAC 先行。

### 本阶段范围

- 权限模型（资源 × 操作，带作用域类型）与 6 个内置角色
- 角色在组织节点上的授予，沿祖先链的判定
- 用户 → 组织归属（`primary_org_id`）的手工指派
- 路由声明式的强制执行与两条机械检查
- 收编 P1.2a 合并前代码复审的全部 6 条发现（见 `../findings/2026-08-30-p1.2a-code-review.md`）
- `is_platform_admin` 迁移为角色授予

### 明确的范围外

| 项 | 去向 |
|---|---|
| 自定义角色的 CRUD 接口 | P1.4（有控制台界面才有真实使用场景） |
| 组织树 ↔ LiteLLM 映射与同步 | P1.2c |
| 从 LDAP 自动推导用户归属 | 未排期（需要读通讯录里人挂在哪个 OU，属通讯录同步逻辑） |
| 多身份来源的离职对账协调 | 未排期（P1.2a 验收发现，见该验收记录遗留问题 #1） |
| 密钥、配额、审批流 | P1.3 |
| 拒绝规则（deny rule）、权限的时效性授予 | 不做，YAGNI |

## 2. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| D1 | P1.2 拆为 P1.2b（RBAC）+ P1.2c（LiteLLM 同步） | 两个不相干子系统，合计 35–40 个任务对单份计划过大 |
| D2 | 权限模型做满，但只预置内置角色、不做角色 CRUD | 编辑自定义角色的界面要到 P1.4 才存在，在那之前自定义角色没有真实使用场景；数据模型做满则 P1.4 加 CRUD 是纯增量 |
| D3 | 内置角色取 6 个（PRD §4 画像与 FR-1.2 角色表合并） | 二者原本矛盾：§4 有「财务/FinOps」画像而 FR-1.2 无对应角色，FR-1.2 有「审计员」而 §4 无对应画像。FinOps（看钱）与审计员（看行为）职责确实不同，强行合并会让某一方拿到多余权限 |
| D4 | 权限带作用域类型（global / org-scoped），全局权限只能由全局授予赋予 | 防止「平台管理员被授予在某节点上」时泄漏出 SSO 配置这类全局能力。边界写在数据里而非依赖约定 |
| D5 | 用户 → 组织归属只做手工指派 | 自动推导需要读通讯录中人员的 OU 挂载，属另一块同步逻辑；手工指派已足够解锁开发者角色作用域、Key 计费归属与删除保护 |
| D6 | 普通员工的基线权限走「隐式基线」 | 授予是 `(用户, 角色, 节点)` 三元组、每条只对一人生效，「给根节点授予开发者」并不能覆盖全公司。隐式基线运维成本最低，符合「入职即可用」的企业直觉 |
| D7 | 独立 `internal/authz` 包 + 路由声明式中间件 | 本阶段核心目标之一是收编「忘了校验」这类缺陷，选结构上不可能忘的方案优于更灵活但依赖自觉的方案 |
| D8 | 删除 `is_platform_admin` 列而非保留 | 两个「谁是管理员」的真相来源迟早漂移，而这正是最容易长出安全漏洞的地方 |

## 3. 数据模型

三张新表：

```sql
CREATE TABLE roles (
    id          TEXT PRIMARY KEY,          -- 'platform_admin' 等稳定标识
    name        TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    is_builtin  BOOLEAN NOT NULL DEFAULT false,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE role_permissions (
    role_id    TEXT NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
    permission TEXT NOT NULL,
    PRIMARY KEY (role_id, permission)
);

CREATE TABLE role_grants (
    id         TEXT PRIMARY KEY,
    user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role_id    TEXT NOT NULL REFERENCES roles(id) ON DELETE RESTRICT,
    org_id     TEXT REFERENCES organizations(id) ON DELETE CASCADE,  -- NULL = 全局授予
    granted_by TEXT REFERENCES users(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### 唯一索引对 NULL 的陷阱

`(user_id, role_id, org_id)` 上的普通唯一索引**挡不住重复的全局授予**——Postgres 认为 NULL 彼此不相等，同一条全局授予能被插入任意多次。必须用表达式索引：

```sql
CREATE UNIQUE INDEX role_grants_unique_idx
    ON role_grants (user_id, role_id, COALESCE(org_id, ''));
```

### 外键行为

- `user_id ON DELETE CASCADE`：用户删除时授予随之消失（当前系统只禁用不删除用户，此约束是防御性的）
- `role_id ON DELETE RESTRICT`：角色被引用时不可删（P1.4 加角色 CRUD 时这条约束开始起作用）
- `org_id ON DELETE CASCADE`：组织节点删除时其上的授予消失。节点删除本身有多重保护（见 §7 第 4 条），走到这一步时该节点已确认无子节点、无密钥、无归属用户

## 4. 权限清单与内置角色

### 权限定义在 Go 里，不在数据库里

作用域类型是权限的固有属性、不是可编辑的数据，因此权限清单（含作用域）定义为 Go 的注册表；`role_permissions` 只存权限字符串。

**启动时校验**：数据库里 `role_permissions` 的每个权限字符串都必须能在 Go 注册表里找到，找不到则拒绝启动。这防止迁移写错、或版本回退后残留的脏数据被静默忽略——静默忽略一条权限意味着某个角色悄悄少了能力，是很难排查的故障。

### 权限清单

| 权限 | 作用域 | 说明 | 本阶段是否有端点 |
|---|---|---|---|
| `org:read` | 节点 | 查看组织树 | 是 |
| `org:write` | 节点 | 创建、改名、移动 | 是 |
| `org:delete` | 节点 | 删除节点 | 是 |
| `org:import` | 节点 | 通讯录导入预览与应用 | 是 |
| `member:assign` | 节点 | 指派用户归属 | 是 |
| `grant:read` | 节点 | 查看角色授予 | 是 |
| `grant:write` | 节点 | 授予、撤销角色 | 是 |
| `audit:read` | 全局 | 审计日志 | 否（P1.4） |
| `cost:read_all` | 全局 | 全公司成本 | 否（P1.5） |
| `platform:configure` | 全局 | SSO、供应商、License | 否（P1.4） |

后三条现在没有对应端点，但必须现在定义——否则 6 个角色的权限集彼此无法区分，「平台管理员」与「组织管理员」会长得一模一样。

**`org:import` 的作用域标注要单独解释一句**：它标为「节点」而非「全局」，因为它操作的确实是组织数据；但导入的作用面覆盖整棵树、没有单一目标节点，所以路由把目标声明为 `Global`（见 §6），判定时走 §5「节点级权限但 target 为 nil → 要求全局授予」这条规则。两处标注不矛盾：权限的作用域类型描述它归属哪类资源，路由的目标形态描述这次调用打在哪个节点上。

### 内置角色

| 角色 ID | 名称 | 权限集 |
|---|---|---|
| `platform_admin` | 平台管理员 | 全部 |
| `org_admin` | 组织管理员 | `org:read`、`org:write`、`org:delete`、`org:import`、`member:assign`、`grant:read`、`grant:write` |
| `security_officer` | 安全合规官 | `audit:read`、`org:read` |
| `finops` | 财务 / FinOps | `cost:read_all`、`org:read` |
| `auditor` | 审计员 | `audit:read`、`org:read` |
| `developer` | 开发者 | `org:read` |

**如实标注**：现阶段 `security_officer` 与 `auditor` 的权限集完全相同。区分二者的护栏策略制定、误报申诉处理要到 P4 才有对应权限。这里不假装它们已经不同。

### 防提权规则

授予接口必须校验：**被授予角色的权限集 ⊆ 授予者在该节点上已持有的权限集**。

否则组织管理员可以给自己授予一个含 `platform:configure` 的角色，绕过 D4 的作用域限制拿到全局权限。这条校验是 D4 的必要补充——D4 挡住「节点级授予直接赋予全局权限」，这条挡住「通过授予他人/自己新角色来间接获得」。

## 5. 判定逻辑

### 入口

```go
Can(ctx context.Context, u *User, permission string, target *string) (bool, error)
```

`target` 为组织节点 ID；为 `nil` 表示无特定目标。

### 祖先链无需查库

组织树用物化路径（`path` 形如 `/id1/id2/id3`），取到目标节点后切分 `path` 即得完整祖先链。这是 P1.2a 那个数据模型选择在本阶段的回报。

### 算法

1. **查权限的作用域类型**（Go 注册表）。
2. **全局权限**：只统计 `org_id IS NULL` 的授予。
3. **节点级权限**：统计「全局授予」+「`org_id` 落在目标节点祖先链上（含目标节点自身）的授予」。全局授予的组织管理员在任何节点都算数。
4. **叠加隐式开发者基线**：目标节点落在用户 `primary_org_id` 的子树内（含自身）时，并入 `developer` 角色的权限集。以下两种情况跳过此步——用户 `primary_org_id` 为空，或 `target` 为 nil（无目标节点时无从判断是否落在子树内，且这类操作按边界规则本就要求全局授予）。
5. **并集判定**：权限出现在并集里即通过。无拒绝规则，纯正向并集。

前置条件：`u.Status` 必须为 active。`RequireSession` 已经拦过一次，判定层再查一次作为纵深防御。

### 两个边界情况

**节点级权限但 `target` 为 nil**（例如 `POST /api/orgs` 且 `parent_id` 为空，即创建根节点）：要求全局授予。否则任何节点管理员都能凭自己那点作用域创建平级的新根，绕出自己的管辖范围。

**移动节点需要两处权限**：把 X 移到 P 之下，要求在 X 上有 `org:write`（在改 X），**也要求在 P 上有 `org:write`（在往 P 底下塞东西）**。只查其中一个都能构造越权：只查 X 能把自己管的子树塞进别人的部门，只查 P 能把别人的子树拽到自己名下。

### 可见范围

`GET /api/orgs` 返回过滤后的结果。可见范围**以 `org:read` 这一条权限为准**，而不是「持有任何授予即可见」——被授予的角色若不含 `org:read`（P1.4 出现自定义角色后就会有这种角色），不应因此看见该节点。

可见集合为以下三者的并集：

- 用户在其上通过授予持有 `org:read` 的节点，及各自的整棵子树
- 用户 `primary_org_id` 的整棵子树（隐式开发者基线含 `org:read`）
- 上述所有节点的祖先链

祖先链只暴露节点名与层级关系，这个泄漏面可以接受——不给祖先链，前端会拿到一片没有根的孤立子树，无法渲染。持有 `org:read` 全局授予的用户可见全树。

## 6. 强制执行

### 路由表声明

```go
type Route struct {
    Pattern    string           // "DELETE /api/orgs/{id}"
    Permission string           // authz.PermOrgDelete；公开端点显式标记为 Public
    Target     TargetExtractor  // FromPath("id") / FromBody("parent_id") / Global / Filtered
    Handler    http.HandlerFunc
}
```

`TargetExtractor` 的四种形态：

| 形态 | 含义 | 用例 |
|---|---|---|
| `FromPath(name)` | 从路径参数取目标节点 | `DELETE /api/orgs/{id}` |
| `FromBody(field)` | 从请求体字段取目标节点（可为空 → 要求全局授予） | `POST /api/orgs` 取 `parent_id` |
| `Global` | 无目标节点，要求全局授予 | 通讯录导入 |
| `Filtered` | 判定交给处理器（列表类接口按可见范围过滤） | `GET /api/orgs` |

注册路由**只能**走这张表，中间件在表上统一判定。

### 通讯录导入要求全局 `org:import`

导入会按 LDAP DN 在任意位置建节点、改名、标记孤儿，作用面覆盖整棵树，无法归到某一个节点上判定，因此声明为 `Global`。

### 两条机械检查

1. 遍历路由表，任何一条既没声明权限、也没显式标记 `Public` 则测试失败。
2. 比对 mux 实际注册的 pattern 集合与路由表，两边不一致则测试失败——堵住绕过表直接 `mux.HandleFunc` 的旁路。

第 1 条保证「新加端点忘了想权限」立刻挂测试，第 2 条保证第 1 条不能被绕过。这与 P1.2a 加的包边界 lint 是同一个思路：把纪律变成机器检查。

### 包边界

新增 `internal/authz` 包：权限注册表、内置角色定义、Resolver（纯逻辑，通过接口拿授予与祖先链）。不含 HTTP、不含 OIDC、不 import `internal/control`。

`internal/control` 负责路由表声明、中间件、授予管理与归属指派的 HTTP 接口。

`make lint` 现有的包边界检查追加一条：`internal/authz` 不得依赖 `internal/control` 或 `internal/edge`。

## 7. 收编代码复审的 6 条发现

对应 `../findings/2026-08-30-p1.2a-code-review.md`。

### 第 1 条：管理接口只校验已登录

由 §6 的路由表 + 中间件直接解决。这是把它推迟到本阶段的全部理由。

### 第 2 条：bootstrap 经未验证 email 提权

三处改动：

- **一次性**：只在系统内平台管理员数为 0 时才可能触发。一旦有了管理员，这条路径彻底关闭，即使配置项仍留在环境变量里。这是最关键的一改。
- **email 必须已验证**：读 `email_verified` claim，为 false 或**缺失**时拒绝按 email 匹配（缺失按未验证处理，fail closed），日志明确提示改用 OIDC sub。
- **优先 sub**：配置值同时支持 email 与 sub；sub 匹配无条件安全（IdP 分配、用户改不了）。

**待实测**：Casdoor 是否发送 `email_verified` claim。若不发，本地开发环境装机只能用 sub。这一点在 §10 验收项 7 里实测确认，不做假设。

### 第 3 条：导入 apply 信任客户端提交的差异项

apply 时服务端**重新拉取通讯录、重新计算差异**，客户端只提交勾选了哪些 `external_id`。客户端因此完全失去对 `Kind` / `Name` / `OrgID` / `ParentExternalID` 的控制权。

代价是 apply 多一次通讯录拉取。预览与应用之间目录发生变化时，服务端按最新事实动作（更安全），并把实际执行的差异项回传给调用方。

### 第 4 条：Delete 漏检 `users.primary_org_id` 外键

本阶段开始给 `primary_org_id` 赋值，这条从潜在问题变成真实问题。加 `ErrOrgHasUsers` 哨兵与对应计数检查，映射为 409，与另两种删除保护一致。

### 第 5 条：`RECONCILE_INTERVAL=0` 导致 panic

`config.Load` 增加正数校验，非正值返回明确的配置错误。

### 第 6 条：空差异序列化成 JSON `null`

`ComputeDiff` 改为返回 `[]DiffItem{}` 而非 nil slice。

## 8. 迁移

单个迁移文件完成以下动作，顺序不可调换：

1. 建 `roles`、`role_permissions`、`role_grants` 三表与索引
2. 预置 6 个内置角色及其权限集（`is_builtin = true`）
3. 为每个 `is_platform_admin = true` 的用户插入一条 `platform_admin` 的全局授予
4. 删除 `users.is_platform_admin` 列

Down 迁移反向重建该列，并从全局 `platform_admin` 授予回填。

### 连带改动

- `CountPlatformAdmins` 改为统计全局 `platform_admin` 授予
- `User` 结构体去掉 `IsPlatformAdmin` 字段
- `/api/whoami` 改为返回用户画像 + 角色授予列表 + 全局权限集（对将来的控制台也更有用）

### 一个让人安心的失败模式

若迁移出 bug、一条授予都没生成，系统即为零管理员，`CheckBootstrapConfig` 会直接拒绝启动。是响亮的失败，不是静默降权。

## 9. 测试策略

| 层次 | 覆盖 |
|---|---|
| `internal/authz` 纯单测 | 判定的全部分支：全局 vs 节点级、祖先链命中与未命中、隐式基线、`target` 为 nil、防提权校验。不碰数据库 |
| Postgres 集成测试 | 授予存储；迁移正确性——**原管理员迁移后实际权限不增不减** |
| 路由级测试 | 每个端点覆盖「无授予 / 授予足够 / 授予不足」三种状态码 |
| 机械检查测试 | §6 的两条；且第 2 条本身要验证真能拦住（临时制造违规，确认测试变红，再撤回） |

判定逻辑是本阶段最容易藏 bug 的地方，也最容易脱库测到底，因此纯单测是最有价值的测试面。

## 10. 验收标准

对着真实 Casdoor + OpenLDAP 逐项验证：

1. 6 个内置角色预置正确，权限集与 §4 一致
2. 节点级授予沿祖先链生效，**同前缀兄弟节点不受影响**（复用 P1.2a 抓到过的 `/root/rd` vs `/root/rd2` 陷阱）
3. 全局权限拿不到——把 `platform_admin` 授予在某节点上，仍然改不了全局配置类权限
4. 移动节点需要源与目标两处 `org:write`，只有一处时被拒
5. 隐式开发者基线生效，且不越出 `primary_org_id` 子树
6. 防提权：组织管理员授予不出自己没有的权限
7. bootstrap 一次性生效；`email_verified` 行为符合 §7 第 2 条，**并给出 Casdoor 是否发送该 claim 的实测结论**
