## 1. 背景与范围

P1.2c 把组织树映射成了 LiteLLM 的 Organization/Team 骨架，但**至今没有一把密钥挂上去**：全代码库对 `/key/*` 零调用，`api_keys` 表里的行都是历次验收手工插入的。同时 Edge 侧还有一条 P1.1 明确记录的欠账——`internal/app/edge.go` 用的是**空的内存 store**，也就是说控制面即便签发了密钥，它今天也无法被真实使用。

本阶段把这两件事一起做完：让密钥能被签发出来，并且能被真正用起来。

### 本阶段范围

- 控制面签发虚拟密钥：生成 `ak-`、调 `/key/generate` 拿上游密钥、加密入库
- 模型可见性白名单与 Key 级配额（金额/周期/RPM/TPM）一次下发
- 吊销（本地 + 上游）
- **Edge 的密钥读取从空内存 store 换成 Postgres**

### 明确的范围外

| 项 | 去向 |
|---|---|
| 申请 → 审批流 | P1.3b |
| 告警通道（钉钉/企业微信/邮件） | P1.3b |
| 密钥轮换 | 未排期（探针 E 已确认 `/key/regenerate` 是 Enterprise 功能，必须自建） |
| Org / Team 级预算 | 未排期（见 D1） |
| `model_prices` 的数据库读取 | 未排期（P1.1 的另一条同源欠账，与密钥无关） |
| Key 级配额的漂移对账 | 未排期（见「已知缺口」） |

## 2. 设计前的实测

沿用 P0 与 P1.2c 建立的纪律：先对真实 LiteLLM 跑探针，不靠文档推断。本轮 15 条探针里有五条直接改变了设计。

| 探针 | 结论 | 对设计的影响 |
|---|---|---|
| A | `/key/generate` 返回 `key`（明文）与 `token`（其哈希） | 上游密钥即返回值 |
| **B** | **接受调用方自带的 key 值** | 与 I 合起来使签发幂等（D3） |
| **C** | Key 挂到**不存在的 `team_id` 上照样返回 200** | ⚠️ 与 `/team/new`（挂不存在的 org 会 400）**行为不对称**。上游不兜底 → D4 |
| D | `models` + `max_budget` + `budget_duration` + `rpm_limit` + `tpm_limit` 单次调用全部下发成功 | 签发是一次调用，不必分步 |
| **E** | `/key/regenerate` → 500，明确要求 Enterprise License | 印证 Roadmap：轮换必须自建。这是 PRD §5.2 警告的 `premium_user` 运行时校验的真实实例 |
| F | 白名单真拦截：`403 key_model_access_denied` | 白名单可靠 |
| **G** | `models: []` 或不传 = **放行全部模型** | ⚠️ fail-open 默认值 → D5 |
| H | `max_budget: 0` = 零额度，`429 budget_exceeded` | fail-closed；且证明**预算在请求路径上硬拦截**，验收不需要真实上游 key |
| **I** | 用同一个 key 值重复创建 → **200，静默无操作，响应体却回显你传的新参数** | 重试安全，但响应体不可信 → D3 与测试重点 |
| J | `/key/info` 可按 key 值回查 | pending 清理靠它判断上游是否已建 |
| K | `/key/block` → 调用 401；`/key/delete` → info 404 | 吊销的两种语义 → D6 |
| L | `duration: "30d"` → 上游算出绝对 `expires` | 上游只认相对时长 |
| **M** | 传绝对时间 `expires` 被**静默丢弃**（返回 `None`） | ⚠️ 与 P0 的 `parent_team_id` 同类陷阱 |
| N | `duration: "3600s"` 正常生效，秒级精度可用 | 过期时间须换算成相对秒数下发 |
| **O** | **删 Team 会级联删掉其上全部密钥** | 见下方「一条顺带加固了 P1.2c 的发现」 |

### 一条顺带加固了 P1.2c 的发现

额外探针确认：**删除 Team 会级联删掉挂在其上的全部密钥**（`/key/info` 404，密钥彻底消失）。结合 P1.2c 探针 D 的「删 Organization 级联删其下 Team」，完整链条是：

```
删 Organization → 删其下全部 Team → 删这些 Team 上的全部 Key
```

**两级静默级联。** P1.2c 论证「删除节点安全」时依赖 `ErrOrgHasChildren` 与 `ErrOrgHasKeys` 两条守卫，当时只知道要防一级。这两条守卫实际挡住的比当初以为的更多，其重要性应被重新认识——任何未来放宽它们的改动都必须重新做这个论证。

## 3. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| D1 | 配额只做 Key 级 | 覆盖「每个开发者/应用各自限额」这一主场景，且**完全不动 P1.2c 的对账器**。多级预算会把预算字段拽进期望态与漂移判定，还要回答「有人在上游改了团队预算，算该纠正的漂移还是合法的临时上调」——那是个独立的产品问题，不该顺手带过 |
| D2 | Edge 每请求查库，不做缓存 | 吊销立即生效，且不需要任何 control→edge 的失效通知通道（当前不存在该基础设施）。按唯一索引查约 1ms，相对 LLM 调用本身的数百毫秒可忽略；而缓存 TTL 会让离职员工的密钥在整个窗口内仍然可用——P1.2a 的离职对账正是靠吊销密钥生效的 |
| D3 | 先落库 `pending` 再调上游 | 结构性消除「上游有、本地无」的无主凭据——那是一把能用、但 Airlock 界面上看不见因而无法吊销的密钥。本地先生成两把密钥并写 pending 行，再用自带 key 值调上游。探针 B+I 使重试天然幂等；失败只留下**看得见的** pending 行 |
| D4 | 只能给 `is_key_holder = true` 的节点签发 | 探针 C 证明上游不校验 team 存在性，挂到不存在的 team 上会静默成功并失去团队级约束。这条规则同时让 `is_key_holder` 从 P1.2c 的「同步标记」升格为真实的业务语义 |
| D5 | `models` 字段在 API 边界**必填** | 探针 G 的 fail-open 只能在边界堵：缺字段直接 400，而不是默默签发一把不受限的密钥。空数组仍表示放行全部，但必须是**显式**的空 |
| D6 | 吊销用 `/key/block` 而非 `/key/delete` | 保留上游的用量与审计关联。Edge 的本地校验才是主闸门（`Key.Validate` 已拒绝非 active），上游 block 是上游密钥泄漏时的第二道防线 |
| D7 | 取消 `is_key_holder` 时**不回收上游 Team** | P1.2c 把这条留给本阶段，理由是「无法判断上面有没有在用的 Key」。现在能判断了，但新探针显示删 Team 会级联销毁其上全部密钥记录。回收换来的只是上游少一个空 Team（观感收益），代价却是新增一条会销毁密钥记录的删除路径。**新证据支持 P1.2c 当初的保守直觉，而不是推翻它**——该不对称就此定为长期设计，Team 继续在同步状态接口里显示为 extra |

## 4. 数据模型

```sql
ALTER TABLE api_keys
    ADD COLUMN models          JSONB   NOT NULL DEFAULT '[]'::jsonb,
    ADD COLUMN max_budget      NUMERIC,
    ADD COLUMN budget_duration TEXT,
    ADD COLUMN rpm_limit       INTEGER,
    ADD COLUMN tpm_limit       INTEGER;
-- status 的 CHECK 约束重建为 ('pending', 'active', 'revoked')
```

Airlock 侧存的是**签发时的意图**；执行方始终是 LiteLLM。本阶段不做 Key 级配额的漂移对账（D1 已排除 Key 对账器），两者若不一致，以 LiteLLM 为准——它才是真正在请求路径上拦截的那一方。这是明确的已知缺口，见 §8。

| 文件 | 职责 |

`internal/litellm` 的包独立性约束（不得依赖 `internal/control`/`internal/edge`）已由 P1.2c 的 lint 检查覆盖，新增文件自动受其保护。

## 6. 签发流程

```
POST /api/keys  {org_id, name, models[], max_budget?, budget_duration?,
                 rpm_limit?, tpm_limit?, expires_at?}

1. 校验 org 节点存在且 is_key_holder = true        → 否则 409（D4）
2. 校验 models 字段存在（空数组可以，缺字段不行）    → 否则 400（D5）
3. 本地生成两把密钥：
     ak- 明文/哈希/前缀（复用 apikey.Generate）
     上游 sk-airlock-<random>（crypto/rand）
4. 写 pending 行（上游密钥加密后入库，配额字段一并写入）
5. 调 /key/generate：
     key             = 我们自己生成的上游密钥值（探针 B）
     team_id         = org 节点 ID
     models / max_budget / budget_duration / rpm_limit / tpm_limit
     duration        = (expires_at - now) 的秒数，形如 "3600s"（探针 M/N）
6. 成功 → status = active，返回 ak- 明文（仅此一次，库里只存哈希）
   失败 → 尽力删上游 + 删 pending 行，返回 502
```

### 崩溃兜底与一个不能颠倒的顺序

步骤 5 与 6 之间进程崩溃，会留下一行 pending 加一把可能已经建成的上游密钥。一个轻量周期任务扫描停留超过阈值的 pending 行，用 `/key/info` 查上游：**存在则先 `/key/delete` 删上游，再删本地行。**

这个顺序不能颠倒——先删本地行就正好制造出 D3 要消灭的无主凭据。

**为什么是清理而不是补成 active**：用户在步骤 6 已经收到错误、并不知道存在这把密钥。把它补成 active 等于凭空多出一把没人知道却能用的密钥，比留一个 pending 危险得多。

## 7. 吊销、Edge 读取与守卫

### 一个统一的顺序原则：本地记录先行

签发与吊销的顺序看似相反，其实是同一条规则的两面：

| 操作 | 危险方向 | 因此 |
|---|---|---|
| 签发 | 上游有、本地无 → 无法吊销的凭据 | 先写 pending 本地行 |
| 吊销 | 本地说已吊销、实际还能用 | 先写本地 `revoked` |

两者都是**本地先行**，因为 **Edge 读的是本地**——本地状态一改，下一个请求立即生效（D2）。上游的 `block` 是第二道防线，尽力而为、失败可重试。

### Edge 读取路径

`internal/apikey/postgres.go` 实现既有的 `apikey.Store` 接口：按 `key_hash` 唯一索引查一行，解密 `upstream_key_enc` 填入 `Key.UpstreamKey`。`internal/app/edge.go` 的装配从 `NewMemoryStore(nil)` 换成它——**`internal/edge` 包本身零改动**，只换注入的实现，延续「Edge 热路径不动」的纪律。

一个顺带的好性质：既有的 `Key.Validate` 写法是 `if k.Status != StatusActive { 拒绝 }`，因此新增的 `pending` 状态**天然被拒**，无需改动判定逻辑。这是既有代码 fail-closed 写法白捡的收益，值得加一条测试固定住，免得日后有人把它"优化"成逐个状态枚举而漏掉 pending。

### 取消 `is_key_holder` 的守卫

既然不回收 Team（D7），取消标记本身无副作用——已有密钥仍绑在 Team 上照常工作。但那会留下「此节点不再是密钥边界，却挂着若干在用密钥」这种自相矛盾的状态。因此：**存在 active 或 pending 密钥时拒绝取消标记（409）**，要取消得先把密钥吊销。一次查询的成本，换 `is_key_holder` 的语义诚实。

## 8. 已知缺口

1. **Key 级配额不做漂移对账**：有人直接在 LiteLLM 侧改了某把密钥的预算或白名单，Airlock 侧存的意图值会变陈旧。执行以 LiteLLM 为准，所以不影响安全性，但展示会不准。做对账需要一个 Key 级的 reconcile 循环，与 D1 保持范围克制的取舍一致，留待后续。
2. **上游密钥不做轮换**：探针 E 确认 `/key/regenerate` 是 Enterprise 功能。自建轮换涉及新旧密钥共存窗口期，是一块独立的状态机，未排期。
3. **过期时间的下发是近似的**：Airlock 存绝对时间，上游只接受相对时长（探针 M/N），换算发生在签发瞬间，因此上游的过期点会比本地晚上几毫秒（请求往返时间）。对密钥过期这个量级无实际影响，且 Edge 的本地校验是主闸门。

## 9. 测试策略

| 层次 | 覆盖 |
|---|---|
| `internal/litellm/keys.go`（httptest） | 正常路径、4xx、5xx、超时、响应体畸形；**重点：重复创建返回 200 静默无操作（探针 I），客户端与调用方都不能把它当作「新参数已生效」** |
| 签发编排（fake client） | pending → active；上游失败时清理；**清理顺序必须先上游后本地**；崩溃残留的 pending 被回收；重试幂等 |
| 校验规则 | 非 key_holder 节点签发 409；`models` 缺字段 400；有密钥时取消标记 409 |
| Edge 读取（Postgres 集成） | 按 hash 查、解密正确；pending / revoked / 已过期一律拒绝 |
| 路由级 | 新端点的「无授予 / 授予足够 / 节点级授予拿不到全局权限」三态 |
| 机械检查 | P1.2b 的两条路由检查自动覆盖新端点；P1.2c 的包独立性检查自动覆盖 `internal/litellm` 新文件 |

## 10. 验收标准

本机没有真实上游 API key，但白名单与预算的判定都发生在转发之前（探针 F/H），因此关键项都能实测：

1. 给 key_holder 节点签发 → 上游 `/key/info` 可见，`team_id`、`models`、预算全部正确
2. **Edge 用签发出的 `ak-` 发起真实调用** → 穿透到上游（因无上游 API key 得到 401 上游错误），证明鉴权与密钥交换链路打通
3. 白名单外的模型 → `403 key_model_access_denied`
4. `max_budget = 0` 的密钥 → `429 budget_exceeded`（配额真实阻断）
5. 吊销 → Edge 立即拒绝；上游 `block` 生效
6. 非 key_holder 节点签发 → 409
7. `models` 字段缺失 → 400
8. 存在 active 密钥时取消 `is_key_holder` → 409
9. 注入上游失败以模拟签发中断 → 无 pending 残留、上游无孤儿密钥
10. `internal/edge` 33 PASS / 0 FAIL，零回归
