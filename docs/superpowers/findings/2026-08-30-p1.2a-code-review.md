## 复审发现

### 1. 所有 `/api/*` 管理接口只校验「已登录」，不校验「是管理员」

**位置**：`internal/control/server.go:50`

`RequireSession` 只验证会话有效 + 用户状态为 active，从不检查 `IsPlatformAdmin`。
grep 确认 `IsPlatformAdmin` 在全代码库里只出现在三处：bootstrap.go 里被授予、
model.go 的结构体字段、userstore.go 的数据库扫描——**从未被当作授权判据读取过**。

**后果**：任何能通过企业 IdP 登录的普通员工，都可以调用
`DELETE /api/orgs/{id}`、`PATCH /api/orgs/{id}/parent`、
`POST /api/orgs/import/apply`，重构或删除承载计费/配额归属的整棵组织树。

这直接架空了 `CheckBootstrapConfig` 自己写在注释里的目的
（「不允许出现『谁都能登、登进去就是管理员』的窗口期」）：管理员标志位在启动时
被建立起来，之后从未被强制执行。

**P1.2b 处理方式**：这正是 RBAC 权限判定层要解决的核心问题。组织树的写操作
（创建/改名/移动/删除）与导入操作都应要求平台管理员或对应组织节点的管理权限。

### 2. bootstrap 管理员每次登录都会重新授予，且匹配的是未经验证的 email

**位置**：`internal/control/bootstrap.go:22`、`internal/control/oidc.go`

`maybeGrantBootstrapAdmin` 在**每一次**成功登录后运行（不只是首次），且用
`strings.EqualFold(want, u.Email)` 匹配 email。而 `oidc.go` 的 claims 结构体只
解析 `email` / `name` / `preferred_username`，**从不检查 `email_verified`**。

**后果**：`AIRLOCK_BOOTSTRAP_ADMIN=admin@example.com` 在初始化完成后会一直留在
配置里。Casdoor 的 application 默认开启 "Enable signup"（Task 22 验收时创建的
`airlock` application 就是默认开着的）。攻击者自助注册一个 email 为
`admin@example.com` 的账号（或把已有账号的 email 改成这个值）后登录 Airlock，
`SetPlatformAdmin(true)` 就会触发，攻击者拿到平台管理员。

**P1.2b 处理方式**：
- 检查 `email_verified` claim，未验证的 email 不参与任何授权判定
- bootstrap 授予改为「仅当系统内还没有任何管理员时」才生效（一次性），
  而不是每次登录都尝试
- 考虑把 bootstrap 匹配限定到 OIDC `sub` 而非 email，`sub` 才是 IdP 侧稳定且
  不可由用户自行修改的标识

### 3. `RECONCILE_INTERVAL=0` 会 panic 并杀死整个 control 进程

**位置**：`internal/config/config.go:62`、`internal/control/reconciler.go:107`

`config.Load` 只检查 `time.ParseDuration` 是否报错，不检查结果是否为正数。
`time.ParseDuration("0")` 返回 `(0, nil)`——无错误。随后
`go reconciler.Run(runCtx, cfg.ReconcileInterval)` 的第一句是
`time.NewTicker(interval)`，而 `NewTicker` 在 `d <= 0` 时 **panic**。
该 panic 发生在无 recover 的 goroutine 里，整个进程崩溃。

**后果**：运维把 `RECONCILE_INTERVAL` 设为 `0`（一个很自然的「关掉对账」的写法，
实际关掉对账的方式是留空 `LDAP_URL`）或误写成负值，control 启动即崩溃，
且不会给出「配置错误」这样的清晰信息。

**注**：这条与 RBAC 无关，是个独立的小修复（config 加一行正数校验即可），
可以在 P1.2b 里顺手做掉，也可以任何时候单独修。

### 4. `Delete` 漏检 `users.primary_org_id` 外键，冲突时返回 500 而非 409

**位置**：`internal/control/orgstore.go:244`

`Delete` 检查了子节点和 api_keys，但没检查 `users.primary_org_id`——而
`migrations/20260828000001_identity.sql` 里这个列带着
`REFERENCES organizations(id) ON DELETE RESTRICT`。

**后果**：P1.2b 开始给 `primary_org_id` 赋值后，删除某个用户的主组织时，
两个已有前置检查都会通过，DELETE 执行到数据库层才被外键拒绝。该错误被包成
`"删除组织节点失败: %w"`，匹配不上 `writeOrgError` 的任何哨兵分支，落到 default
→ 500 internal_error，而不是像另外两种删除保护那样返回带错误码的 409。
调用方无法区分「服务器故障」和「合法的删除冲突」。

**P1.2b 处理方式**：P1.2b 正是开始使用 `primary_org_id` 的阶段，届时补上
第三个前置检查与对应的 `ErrOrgHasUsers` 哨兵错误。

### 5. 导入 apply 完全信任客户端提交的差异项

**位置**：`internal/control/orgapi.go:124`

`HandleImportApply` 把客户端 POST 上来的 `DiffItem` 列表直接交给 `ApplyImport`，
不重新拉取通讯录校验。客户端因此完全控制 `Kind` / `OrgID` / `Name` /
`ExternalID` / `ParentExternalID`。

**后果**：客户端可以提交一条 LDAP 里根本不存在的
`{"Kind":"added","ExternalID":"ou=finance,dc=example,dc=org","Name":"Finance"}`，
在本地建出一个 `external_source='ldap'` 且 external_id 为攻击者指定值的节点。
之后真实的 `ou=finance` 出现在 LDAP 里时，`ComputeDiff` 会按 external_id 匹配到
这个被污染的节点，判定为「无变化」（或 `ApplyImport` 判定为 Skipped），
真实的目录节点因此静默地永远不会被导入，攻击者命名的节点取而代之。

与第 1 条不同，这是一个**独立于组织树 CRUD 的额外能力**：改名接口无法写入
攻击者指定的外部来源身份，只有这个接口可以。

**P1.2b 处理方式**：随 RBAC 一起收口——apply 时服务端重新拉取通讯录并重新计算
差异，只接受客户端「勾选了哪些项」的选择（例如只接受 external_id 列表），
而不是接受客户端提交的完整差异内容。

### 6. 空差异序列化成 JSON `null` 而非 `[]`

**位置**：`internal/control/importdiff.go:110`

`ComputeDiff` 无差异时返回未经 append 的 nil slice，`encoding/json` 把 nil slice
编码成 `null`。

**后果**：导入完成后调用 `GET /api/orgs/import/preview` 确认无残留时，响应是
`{"items":null,"source":"ldap"}`。任何前端写 `preview.items.length` 或直接遍历
`items` 都会抛异常——Task 22 验收过程中真实撞到过这个异常
（见 `2026-08-28-p1.2a-acceptance.md` 验收项 5）。幂等无变化是这个接口最常见的
稳态返回，P1.4 控制台一定会撞上。

**修法**：`items := []DiffItem{}` 即可。与已标记的后续任务
「给 DiffItem 加 JSON tag、收敛 import-apply 错误信息」属于同一批 API 契约打磨，
建议一起做。
