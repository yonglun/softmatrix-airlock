## 验收项 2：深链登录后回到原路径（发现并修复一处真实缺陷）

第一次尝试：清掉 `airlock_session`（调 `POST /auth/logout`）后直接访问 `http://localhost:8081/platform/orgs`，走完 Casdoor 登录（`admin`/`123`），落地 URL 却是 `http://localhost:8081/my/requests`，不是预期的 `/platform/orgs`。

排查发现这不是登录回调的问题——`redirect_to` 全程正确带到了 `/auth/callback`。问题在 `ConsoleHandler`（[static.go](../../../internal/control/static.go)）：Next.js `output: 'export'`（未设 `trailingSlash`）把 `/platform/orgs` 产出成扁平文件 `platform/orgs.html`，不是 `platform/orgs` 或 `platform/orgs/index.html`。硬刷新 `GET /platform/orgs` 时，`ConsoleHandler` 对路径 `platform/orgs` 做 `fs.Stat` 找不到匹配文件，于是落到「不是真实文件 → 回 index.html」的兜底分支——**把根页面（`/`）的组件当成响应发了回去，HTTP 200，但内容是根页面而不是组织与成员页**。根页面的逻辑是「按 `session.workbenches[0]` 跳转落点」，而 URL 栏此时仍显示 `/platform/orgs`（浏览器地址栏不变，因为响应本身就是 200，不是重定向），页面挂载的 JS 却是根页面的 bundle，触发它自己的客户端跳转，把用户带去了 `/my/requests`。

复现证据（对比同一次构建产物、`.html` 后缀 vs 不带后缀）：

```
$ curl -sS http://localhost:8081/platform/orgs -o /tmp/orgs_response.html && grep -o 'app/[a-zA-Z/]*page-[a-z0-9]*\.js' /tmp/orgs_response.html
app/page-7cafced205492fcb.js          # 根页面的 bundle，不是 orgs 页面的

$ curl -sS http://localhost:8081/platform/orgs.html -o /tmp/orgs_direct.html && grep -o 'app/[a-zA-Z/]*page-[a-z0-9]*\.js' /tmp/orgs_direct.html
app/platform/orgs/page-ebc06460352debb4.js   # 真正的 orgs 页面 bundle
```

**修复**（[static.go](../../../internal/control/static.go)）：`ConsoleHandler` 增加中间一档——精确文件不存在时，先试 `<路径>.html`，命中就发它；都不命中才回退 `index.html`。按 TDD 补了失败测试 `TestConsoleDeepLinkServesMatchingPageNotRootIndex`（先红后绿），`go test ./... -race -count=1` 全绿后单独提交（`fix: 深链硬刷新按 next export 的 <路由>.html 命名匹配页面`）。

修复后重新验证：

```
$ curl -sS http://localhost:8081/platform/orgs -o /tmp/orgs_response2.html -w "%{http_code}\n" && grep -o 'app/[a-zA-Z/]*page-[a-z0-9]*\.js' /tmp/orgs_response2.html
200
app/platform/orgs/page-ebc06460352debb4.js
```

浏览器复测：清会话、访问 `/platform/orgs`、走完 Casdoor 登录，登录完成后：

```
window.location.href === "http://localhost:8081/platform/orgs"
```

页面内容也正确渲染成组织与成员页（能看到「新建节点」「删除所选」按钮与组织树），不再是根页面的空跳转。**深链落点问题已修复并复测通过。**

## 验收项 3：三类用户看到的工作台不同（D2 硬证据）

| 账号 | 授予 | `workbenches` | `global_permissions` |
|---|---|---|---|
| 平台管理员（`admin@example.com`，浏览器真实登录 + 全局 `platform_admin`） | 全局 `platform_admin` | `["my-space","platform","finops"]` | `["audit:read","cost:read_all","grant:read","grant:write","key:read","key:request","key:revoke_all","key:write","member:assign","org:delete","org:import","org:read","org:write","platform:configure"]` |
| 子树管理员（`u-orgadmin-root-p14a`，`org_admin` 只授在 `p14root`） | 节点授予 | `["my-space","platform","finops"]` | `[]` |
| 普通开发者（`u-dev-p14a`，无任何授予，归属 `p14rd`） | 无 | `["my-space"]` | `[]` |

关键项命令与输出（子树管理员）：

```
$ curl -sS http://localhost:8081/api/whoami -H "Cookie: airlock_session=p14a-orgadmin-root-token-abc123" \
    | python3 -c 'import json,sys; d=json.load(sys.stdin); print("workbenches =", d["workbenches"], "| global_permissions =", d["global_permissions"])'
workbenches = ['my-space', 'platform', 'finops'] | global_permissions = []
```

普通开发者：

```
$ curl -sS http://localhost:8081/api/whoami -H "Cookie: airlock_session=p14a-dev-token-def456" \
    | python3 -c 'import json,sys; d=json.load(sys.stdin); print("workbenches =", d["workbenches"], "| global_permissions =", d["global_permissions"])'
workbenches = ['my-space'] | global_permissions = []
```

**子树管理员的 `global_permissions` 是空数组、`workbenches` 却含 `platform`（连带 `finops`，因为 `org_admin` 角色同时持有 `org:write` 与 `key:write`）——这正是当初设计上不能用 `global_permissions` 判定工作台可见性、必须用 `Resolver.Scopes`（`global || len(nodes) > 0`）的原因，`internal/control/workbench.go` 的判定逻辑在真实请求链路下按预期工作。**

## 验收项 4：组织与成员的增删改与 409

用平台管理员账号（浏览器登录后授予全局 `platform_admin`）在「平台管理 → 组织与成员」页操作：

1. 新建根节点「验收根A」→ `POST /api/orgs` → `201 Created`
2. 选中「验收根A」新建子节点「验收子A1」→ `POST /api/orgs` → `201 Created`
3. 改名 →（**说明**：本期页面没有改名的 UI 控件——`web/src/app/platform/orgs/page.tsx` 只提供新建与删除，改名是已知的页面范围空缺，后端接口已具备。直接同源调用页面本可以调用的同一个接口验证能力存在）：
   ```
   PATCH /api/orgs/de4e4163-9d0d-475d-9803-87bd04c420c3/name {"name":"验收子A1-改名"} → 204
   ```
   DB 复核：`name` 确实变为「验收子A1-改名」。
4. 删除该子节点（页面「删除所选」+ 二次确认）→ `DELETE /api/orgs/de4e4163-...` → `204 No Content`，消息提示「已删除」，DB 复核该行已不存在。
5. 选中仍有两个子节点（`p14rd`、`p14rd2`）的「验收P14根」，点「删除所选」→ `DELETE /api/orgs/p14root` → **`409 Conflict`**，页面弹出的提示原样是后端中文：「该节点下还有子节点，无法删除」。DB 复核 `p14root`/`p14rd`/`p14rd2` 三行均未被删除。

前四步全部成功，第五步按预期失败并展示后端中文提示，符合设计文档 D5（前端直接透传后端 message，不另维护文案表）。

## 过程中发现的问题及处置

1. **深链硬刷新落错页面组件（真实缺陷，已修复）**——见验收项 2。根因是 `ConsoleHandler` 只判断「精确路径命中真实文件」与「兜底 index.html」两档，漏了 next export（无 `trailingSlash`）产出的 `<路由>.html` 命名这一档。修复为三档判断，按 TDD 补了 `TestConsoleDeepLinkServesMatchingPageNotRootIndex`，单独提交（`fix: 深链硬刷新按 next export 的 <路由>.html 命名匹配页面`）。这也解释了为什么 Task 5 当初写的 `TestConsoleDeepLinkFallsBackToIndex`（用完全没有对应页面产物的合成 FS）没能提前捕获——那个测试夹具里根本没有 `<路由>.html` 这个文件，测的是「真没有页面时兜底」，不是「有页面时优先命中」，两者是不同的分支。
2. **组织与成员页没有改名的 UI 控件**——已知的页面范围空缺（design/plan 都没有提到改名按钮），验收项 4 里改名步骤直接调页面本可调用的同一个后端接口验证能力存在，不影响本期验收结论，记为后续页面迭代的候选项。
3. **Bootstrap 的「首个管理员自动授权」在本次验收里对新登录的 `admin@example.com` 没有生效**——因为这个开发库经过多轮此前的验收，早已存在别的 `platform_admin` 授予，bootstrap 的「无任何管理员时才自动授权」条件不成立。这不是缺陷（bootstrap 的语义就是「只在冷启动、一个管理员都没有时」生效），验收时手工给这个账号补授了一条全局 `platform_admin` 记录。
4. **浏览器自动化工具的坐标点击在这个页面上不可靠**——`computer` 工具的 `left_click`（无论传 `coordinate` 还是 `ref`）多次点在了错误的元素上，且 antd `Modal`/`Popconfirm` 弹出时截图工具偶尔没能正确渲染出弹层内容（但 DOM 状态其实是对的）。改用 `javascript_tool` 直接操作 DOM（`element.click()`、原生 setter 触发 React 受控 input 的 `onChange`）后所有操作准确可靠。这是验收环境的工具限制，不是被验收系统的问题。
