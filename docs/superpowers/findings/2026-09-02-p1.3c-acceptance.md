### 手工造夹具

跳过浏览器 OIDC 登录，直接用 `HashSessionToken`（普通 sha256 hex，`python3 -c` 计算避免手误，并用 `SELECT length(id)=64` 校验）手工造两个用户：

- `admin`（`u-admin-p13c`，持全局 `platform_admin` 授予）

`gw-p13c` 是手工插入的 `is_key_holder=true` 组织节点。以 admin 身份经 `POST /api/keys` 给 member 签发一把密钥（ID `c1dd957b-aac6-4c2a-84c7-e415a0f840cb`）。

```
$ curl -X POST http://localhost:8081/api/keys/c1dd957b.../rotate \
    -H "Cookie: airlock_session=p13c-member-token-xyz" -d '{"window_seconds":3600}'

{"id":"c1dd957b-aac6-4c2a-84c7-e415a0f840cb","key_prefix":"ak-EPkIbT-DH", ...,
 "key":"ak-EPkIbT-DHwTP2GNPtGxfX4QN_PYY532DdUfVV-sIjQ4"}
```

`id` 与轮换前完全相同，`key_prefix` 与 `key` 都换新了。

```
$ curl -X POST http://localhost:8080/v1/chat/completions \
    -H "Authorization: Bearer ak-EPkIbT-DHwTP2GNPtGxfX4QN_PYY532DdUfVV-sIjQ4" \
    -d '{"model":"qwen-plus", ...}'
HTTP=401
{"error":{"message":"... You didn't provide an API key. ... Model Group=qwen-plus"}}
```

**环境限制（非 Airlock 缺陷，与 P1.3b 验收记录同一结论）**：用 LiteLLM 的 master key 打同一条 `/v1/chat/completions`，得到**完全相同**的错误——本机 LiteLLM 实例的 `qwen-plus` 模型组缺少真实的供应商凭据，与 Airlock 的密钥翻译无关。证据：解密上游密文后查 `/key/info`，`last_active` 被刚才的 Edge 调用更新为 `2026-09-02T09:52:31.167000+00:00`——证明 Edge 正确解密并把请求带着真实 `sk-` 密钥转发到了上游，请求在 LiteLLM 的密钥鉴权层通过、只在模型分发层因供应商凭据缺失而失败。

## 验收项 4：窗口一过旧凭据当场失效（D5 硬证据）

这是整个设计里最值得留证据的一条，做得比计划更严格：**不只是不主动跑 worker，而是把控制面进程完全杀掉**，证明失效判断纯粹活在 Edge 自己的 SQL 查询里。

为拿到干净证据，先对同一把密钥再轮换一次（`ak-EPkIbT...` 变成新的 `prev_key_hash`），然后：

```
$ pkill -f "bin/airlock control"
$ pgrep -f "bin/airlock control"; echo "exit=$?"
exit=1
```

控制面（含密钥维护循环）确认完全停止。此时旧凭据仍可用：

```
$ curl -X POST http://localhost:8080/v1/chat/completions \
    -H "Authorization: Bearer ak-EPkIbT-DHwTP2GNPtGxfX4QN_PYY532DdUfVV-sIjQ4" \
    -d '{"model":"qwen-plus", ...}'
HTTP=401  （模型分发层错误，与新凭据同样的失败模式，证明鉴权已通过）
```

把到期时间改到过去：

```
$ docker exec deploy-postgres-1 psql -U airlock -d airlock -c \
    "UPDATE api_keys SET prev_key_expires_at = now() - interval '1 minute' WHERE id='c1dd957b...'"
UPDATE 1
```

立刻再试：

```
$ curl -X POST http://localhost:8080/v1/chat/completions \
    -H "Authorization: Bearer ak-EPkIbT-DHwTP2GNPtGxfX4QN_PYY532DdUfVV-sIjQ4" \
    -d '{"model":"qwen-plus", ...}'
HTTP=401
{"error":{"code":"invalid_api_key","message":"密钥格式非法或不存在"}}
```

同时确认 `prev_key_hash` 仍在库里（因为清理 worker 根本没在运行）：

```
$ docker exec deploy-postgres-1 psql -U airlock -d airlock -c \
    "SELECT prev_key_hash IS NOT NULL AS still_there FROM api_keys WHERE id='c1dd957b...'"
 still_there
-------------
 t
```

**控制面进程不存在、清理 worker 一次都没跑过、`prev_key_hash` 仍然是那一串旧哈希本身，Edge 依然正确拒绝了过期的旧凭据**——到期判断完全由 Edge 自己那条 SQL 里的 `prev_key_expires_at > now()` 决定，与任何后台任务无关。

（补充说明：第一次不严格的尝试中，因为 `KEY_MAINTENANCE_INTERVAL=10s`、命令间隔恰好跨过一个周期，`still_there` 一度显示 `f`——这本身也是扫描正常工作的证据，但为了拿到「零依赖后台任务」的干净证据，重做了上面这次控制面完全停机的版本。）

重新启动 `control`：

```
2026/09/02 17:54:20 INFO 密钥维护循环已启动 interval=10s
2026/09/02 17:54:20 INFO 已清理过期的轮换旧凭据 count=1
```

## 验收项 7：按子树吊销，同前缀兄弟毫发无伤

手工造 `/p13c-root/p13c-rd`（key holder）与 `/p13c-root/p13c-rd2`（key holder，与前者共享 `p13c-rd` 前缀）两个节点，各签一把密钥：

```
$ curl -X POST http://localhost:8081/api/orgs/p13c-rd/keys/revoke \
    -H "Cookie: airlock_session=p13c-admin-token-xyz"
{"revoked":1}
HTTP=200

$ docker exec deploy-postgres-1 psql -U airlock -d airlock -c \
    "SELECT org_id, status FROM api_keys WHERE org_id IN ('p13c-rd','p13c-rd2')"
  org_id  | status
----------+---------
 p13c-rd2 | active
 p13c-rd  | revoked
```

`p13c-rd` 的密钥被吊销，同前缀兄弟 `p13c-rd2` 的密钥**毫发无伤**——D-陷阱第三次验证成功（P1.2b 权限判定、P1.3b 审批人查找各踩过一次）。

## 验收项 8：全局紧急吊销

缺确认字符串：

```
$ curl -X POST http://localhost:8081/api/keys/revoke-all \
    -H "Cookie: airlock_session=p13c-admin-token-xyz" -d '{}'
HTTP=400
{"error":{"code":"confirm_required", ...}}
```

无 `key:revoke_all` 权限的普通成员：

```
$ curl -X POST http://localhost:8081/api/keys/revoke-all \
    -H "Cookie: airlock_session=p13c-member-token-xyz" -d '{"confirm":"REVOKE ALL KEYS"}'
HTTP=403
{"error":{"code":"permission_denied", ...}}
```

带上正确确认字符串的管理员：

```
$ curl -X POST http://localhost:8081/api/keys/revoke-all \
    -H "Cookie: airlock_session=p13c-admin-token-xyz" -d '{"confirm":"REVOKE ALL KEYS"}'
{"revoked":1}
HTTP=200

$ docker exec deploy-postgres-1 psql -U airlock -d airlock -c \
    "SELECT count(*) FROM api_keys WHERE status IN ('active','pending')"
 count
-------
     0
```

全系统再无一把 `active`/`pending` 的密钥。

## 验收项 10：收敛历史上封禁失败的密钥

模拟一把「本地已 revoked、上游仍活着」的历史遗留：先用 `/key/unblock` 把它在上游解封，同时把本地 `upstream_blocked_at`/`upstream_block_attempts` 清空：

```
$ curl -X POST http://localhost:4000/key/unblock -d '{"key":"sk-airlock-nibTrBSSssdhme8IIpRkEz_viLZs132LQDCr0sbD-hA"}'
HTTP=200

$ curl "http://localhost:4000/key/info?key=sk-airlock-nibTrBSSssdhme8IIpRkEz_viLZs132LQDCr0sbD-hA"
blocked (right after unblock) = False

$ docker exec deploy-postgres-1 psql -U airlock -d airlock -c \
    "UPDATE api_keys SET upstream_blocked_at = NULL, upstream_block_attempts = 0 WHERE id='47f7c433...'"
```

等一轮扫描：

```
$ sleep 12 && curl "http://localhost:4000/key/info?key=sk-airlock-nibTrBSSssdhme8IIpRkEz_viLZs132LQDCr0sbD-hA"
blocked (after scan) = True
```

**在「刚解封、确认为 False」与「一轮扫描后、确认为 True」之间没有任何人工干预**——证明本阶段补上的既有缺口（封禁失败永不重试）确实能收敛历史遗留问题。
