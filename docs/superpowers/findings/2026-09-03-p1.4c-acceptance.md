## 验收项 1：有效权限视图三类来源齐全

在 `p14c-rd` 上先有直授（`rdadmin` 的 `org_admin`）与全局授予（`admin` 的 `platform_admin`），再对 `p14c-root` 补一条 `auditor` 授予制造继承来源：

```
$ curl -sS -X POST http://localhost:8081/api/grants -d '{"user_id":"u-p14c-member","role_id":"auditor","org_id":"p14c-root"}'
{"ID":"45bcf4a1-...","UserID":"u-p14c-member","RoleID":"auditor","OrgID":"p14c-root",...}
HTTP=201

$ curl -sS http://localhost:8081/api/orgs/p14c-rd/effective-grants
[('platform_admin','global',None), ('org_admin','direct','p14c-rd'), ('auditor','inherited','p14c-root')]
```

三类来源齐全，`source_org_id` 分别指向 `p14c-rd`（直授节点自身）、`p14c-root`（继承的来源节点）、`None`（全局）。

界面复测（`/platform/grants` 选中 `P14c-RD`）：

```
"P14c管理员（admin@p14c.test） 平台管理员 全局 ... 全局授予，需在全局撤销"
"P14cRD管理员（rdadmin@p14c.test） 组织管理员 直授 ... 撤销"
"P14c普通成员（member@p14c.test） 审计员 继承 ... 需在「P14c根」上撤销"
"admin（admin@example.com） 平台管理员 全局 ... 全局授予，需在全局撤销"
```

用户名、角色名都正确还原成人话；三种来源 Tag（直授/继承/全局）与各自的操作列文案完全符合设计。

## 验收项 2：同前缀兄弟节点不混入（第六次陷阱）

```
$ curl -sS http://localhost:8081/api/orgs/p14c-rd/effective-grants | python3 -c '...sorted(set(source_org_id))'
[None, 'p14c-rd', 'p14c-root']

$ curl -sS http://localhost:8081/api/orgs/p14c-rd2/effective-grants | python3 -c '...sorted(set(source_org_id))'
[None, 'p14c-rd2', 'p14c-root']
```

`p14c-rd` 与 `p14c-rd2` 路径同前缀但互不为祖先，两个方向查询都只看到各自的直授节点 + 共同祖先 `p14c-root` + 全局，**互不越界**。

**这是本项目第六次专门测试「同前缀兄弟节点」陷阱**（P1.2b 权限判定、P1.3b 审批人查找、P1.3c 子树吊销、P1.4a 待审列表、P1.4b 子树密钥查询各一次）。这次验证的是 `authz.Resolver.ancestorChain` 同款手法——把物化路径切成 ID 段后逐个精确比较，而不是字符串前缀匹配——在有效权限查询上同样成立。

## 验收项 3：只有直授行可撤销

界面上点 `rdadmin` 那一行（`direct`）的「撤销」：

```
popconfirm: "确认撤销该授予？撤销后该用户将失去这个节点上的这个角色。"

撤销后：
after = [('platform_admin','global'), ('auditor','inherited'), ('platform_admin','global')]
```

直授行消失，`inherited` 与 `global` 两行未受影响——撤销一条直授不会误伤继承或全局授予。（这条同时也是 P1.4c 特有的坑：撤销的正是 `rdadmin` 自己在 `p14c-rd` 上的授予，导致他此刻在该节点上一条授予都没有，为验收项 4 做准备时需要先把这条授予补回来——见下方「过程中发现的问题」。）

## 验收项 4、5：可授角色过滤与服务端反提权闸

补回 `rdadmin` 在 `p14c-rd` 上的 `org_admin` 授予后：

```
$ curl -sS "http://localhost:8081/api/roles?grantable_at=p14c-rd" -H "Cookie: airlock_session=p14c-rdadmin-token-bbb222"
['developer', 'org_admin']
```

`org_admin`（他自己持有的角色）与 `developer`（权限集是 `org_admin` 的子集）都在，**`platform_admin` 不在**——反提权判定 `CanGrant` 正确工作：能授出去的角色，权限集必须是授予者已持有权限的子集。

```
$ curl -sS -X POST http://localhost:8081/api/grants -H "Cookie: airlock_session=p14c-rdadmin-token-bbb222" -d '{"user_id":"u-p14c-member","role_id":"platform_admin","org_id":"p14c-rd"}'
{"error":{"code":"permission_denied","message":"没有执行该操作的权限"}}
HTTP=403
```

绕开下拉直接打接口试图越权授予 `platform_admin`，同样被拦下。**下拉过滤只是便利，真正的闸在服务端的 `CanGrant`。**

## 验收项 9：成员加入与移出（含权限不对称的实证）

界面上把 `P14c普通成员`（此刻归属为空）加入 `P14c-RD`：

```
notices: ["已加入该节点"]
$ psql -c "SELECT primary_org_id FROM users WHERE id='u-p14c-member';"  →  p14c-rd
```

再把他移出（以全局 `platform_admin` 身份）：

```
popconfirm: "确认移出该节点？移出后该用户将没有归属节点。这一步需要全局的成员指派权限。"
notices: [..., "已移出"]
$ psql -c "SELECT primary_org_id FROM users WHERE id='u-p14c-member';"  →  (null)
```

**权限不对称的实证**（设计文档 §5 记下的那处）：`rdadmin` 在 `p14c-rd` 上持有完整的 `org_admin`（含 `member:assign`），把人**移进**这个节点没有问题；但尝试把人**移出**（`org_id: null`）：

```
$ curl -sS -X PUT http://localhost:8081/api/users/u-p14c-rdadmin/primary-org -H "Cookie: airlock_session=p14c-rdadmin-token-bbb222" -d '{"org_id":null}'
{"error":{"code":"permission_denied","message":"没有执行该操作的权限"}}
HTTP=403
```

`TargetFromBody("org_id")` 在 `org_id` 为 `null` 时取到 nil，判定退化为**全局** `member:assign`——`rdadmin` 只在节点上持有该权限，没有全局授予，因此拿到 403。这正是设计文档记下的、本期刻意不改的既有行为，界面上的提示文案（「这一步需要全局的成员指派权限」）让这个 403 说得通。

## 过程中发现的问题及处置

1. **`internal/apikey` 在 `go test ./...` 全量跑时偶发失败，单独跑或重跑一次都是绿的**——这是共享开发库上的跨包竞态（P1.3b 验收记录里就记过同一类问题）：`go test ./...` 并行跑多个包，`internal/control` 与 `internal/apikey` 的测试各自 `cleanTables` 同一个 Postgres 实例，两边的清表/建数据窗口偶尔重叠。不是本期改动引入的回归——重跑 `go test ./...` 后全绿，且 `internal/apikey` 单独跑（含 `-v` 全量）稳定通过。未改代码，只是记录下来避免以后被误判为本期缺陷。
2. **验收项 3 消费了验收项 4 所需的夹具**——撤销 `rdadmin` 在 `p14c-rd` 上的直授授予（用于验证撤销功能）之后，他在该节点上就没有任何授予了，导致紧接着测「他能授出哪些角色」时结果失真（只剩 `developer`，`org_admin` 也不见了，这本身是正确行为而非 bug，但不是我想验证的场景）。发现后立刻用 `admin` 身份把这条授予重新建回去，再测验收项 4/5，拿到了预期结果（`['developer', 'org_admin']`，不含 `platform_admin`）。记录进这份文档，作为「验收步骤之间会互相消费夹具」的一个新例子（与设计文档 §7 已经点出的「移动/删除节点会打乱夹具」是同一类坑）。
3. **antd `<Table>` 在 Vitest/jsdom 下需要 `window.matchMedia`**——这是项目里第一次直接给 `<Table>`（而非只用 `Layout`/`Menu`）写渲染测试（`GrantsTable.test.tsx`），jsdom 不实现 `matchMedia`，antd 的响应式断点钩子挂载时就调用它，不 polyfill 会让任何渲染 `Table` 的测试直接崩溃。修法是在 `vitest.setup.ts`（全局配置，不是单个测试文件）里补一个最小 `matchMedia` 桩——这样以后任何测试渲染 antd 的 `Table`/`Grid` 都不会再撞到这个坑。
4. **浏览器自动化对 antd `Select` 的驱动需要 `mousedown` + `focus`，纯 `.click()` 不够**——继 P1.4a/b 记录的坐标点击不可靠之后，这次多踩了一个坑：antd `Select`（`showSearch` 模式）的下拉不会被对搜索框的原生 `.click()` 打开，必须先 `dispatchEvent(new MouseEvent('mousedown', {bubbles:true}))` 再 `.focus()`。另外要注意 antd 按钮的两字文案会被自动插入一个不可见空格（`改名` 渲染成 `改 名`），用 `textContent === '改名'` 做选择器会精确匹配失败，需要先 `replace(/\s/g,'')`。这两条都是自动化环境的工具限制，不是被验收系统的问题。
