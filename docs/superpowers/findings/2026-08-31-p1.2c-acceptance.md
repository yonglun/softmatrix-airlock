## 验收项 1 —— 建树、标记、同步出正确实体

标记 `网关组` 为 key holder：

```
$ curl -X PUT .../api/orgs/99e4e091.../key-holder -d '{"is_key_holder":true}'
204
```

等待一轮同步后直接查 LiteLLM：

```json
GET /team/info?team_id=99e4e091-ee3e-4494-aa66-26fc8d3ae6e0
{"team_id":"99e4e091-...","organization_id":"a4b549db-..."}
```

`organization_id` 恰好等于**研发中心**的节点 ID（不是集团、不是销售部）——祖先链取值正确。

## 验收项 2 —— 改名两侧收敛

## 验收项 3 —— 跨子树移动，team_id 不变

把 `网关组` 从 `研发中心` 移到 `销售部` 之下：

```
$ curl -X PATCH .../api/orgs/99e4e091.../parent -d '{"parent_id":"3e173b17-..."}'
204

$ curl .../team/info?team_id=99e4e091-ee3e-4494-aa66-26fc8d3ae6e0
team_id = 99e4e091-ee3e-4494-aa66-26fc8d3ae6e0   # 与移动前完全一致
organization_id = 3e173b17-1c25-47c5-ba54-f93ea1627f72   # 正确改挂到销售部
```

`team_id` 字节级一致，`organization_id` 正确改挂——探针阶段确认的「原地改挂、Key 归属不受影响」在真实同步路径上复现。

## 验收项 4 —— depth-3 移成 depth-2，成为新 Organization

把当前挂在 `销售部` 下（depth 3）的 `网关组` 移到根节点下（成为 depth 2）：

```
$ curl -X PATCH .../api/orgs/99e4e091.../parent -d '{"parent_id":"33e934f4-..."}'
204

$ curl .../organization/list
[..., "3e173b17-...", "a4b549db-...", "99e4e091-ee3e-4494-aa66-26fc8d3ae6e0"]

$ curl .../team/info?team_id=99e4e091-...
organization_id = 99e4e091-ee3e-4494-aa66-26fc8d3ae6e0   # 挂到自己身上
```

`网关组` 现在同时出现在 Organization 列表里，且它自己的 Team 挂在自己名下——设计文档 §4「depth-2 节点被标记时既是 Org 又是 Team」这条退化情况的真实复现。

## 验收项 9 —— 删除被标记节点删掉其 Team，且守卫拦得住

```
$ curl -X DELETE .../api/orgs/99e4e091-...
204

$ curl .../team/info?team_id=99e4e091-...
404   # 传播删除立即生效，不必等下一轮对账
```

复验删除守卫（`root` 有子节点，必须拒绝）：

```
$ curl -X DELETE .../api/orgs/33e934f4-...
409 {"error":{"code":"org_has_children","message":"该节点下还有子节点，无法删除"}}
```

这条守卫正是设计文档 §6 删除传播安全性论证的前提——被删节点必然无子节点，级联删除因此波及不到不该删的实体。

## 验收项 10 —— 节点级 org_admin 调不动同步

手工造一个只在 `研发中心`（`a4b549db-...`）节点持有 `org_admin` 授予的测试用户（非全局）：

```
$ curl -X POST .../api/litellm/sync -H "Cookie: airlock_session=<该用户 token>"
403 {"error":{"code":"permission_denied","message":"没有执行该操作的权限"}}
```

`platform:configure` 是全局作用域权限，节点级授予拿不到——这条边界规则由 P1.2b 的 authz 判定器保证，本阶段只是复用它。

## 验收中一处需要记录的操作插曲

Step 11 手工插入测试用户的会话哈希时，第一次复制 SHA-256 十六进制值时漏掉了最后一位字符（63 位而非 64 位），导致该会话在数据库里是一条永远匹配不上任何真实 token 的死记录。在真正拿它测试之前，主动用 `SELECT length(id)` 复查了一遍，发现长度不对，删除重插后确认为 64 位再继续。记录此事不是因为它影响了验收结论（插曲发生在使用前，未产生任何误判），而是这类「复制一个长字符串时丢一位」的失误具有代表性——凡是手工构造哈希、Token、密钥这类定长字符串的场景，操作后自查长度是一个几乎零成本、能可靠拦下这类问题的习惯。

## 与设计文档的对照

11 项验收标准全部通过，且验收过程本身也印证了设计阶段那 11 条 LiteLLM 探针（见设计文档 §2）的结论在真实同步路径上同样成立，不只是在 httptest 模拟里成立：

- 探针 A/E「可自带 ID」→ 验收项 1、4：`network`/`team` 的 ID 全程等于 Airlock 节点 UUID，从未见过映射表

设计阶段花时间跑通的探针，在真实同步路径上没有一条打折扣。
