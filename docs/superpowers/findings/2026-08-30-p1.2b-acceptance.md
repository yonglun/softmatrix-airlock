## 验收项 2 —— 祖先链、同前缀兄弟隔离、全局权限拿不到（设计 §10 第 2、3 条）

用平台管理员建树：`集团(root) / 研发中心(rd) / 销售部(rd2，rd 的兄弟) / 网关组(gw，rd 的子节点)`。给测试用户 `test-orgadmin-1`（`external_id=test-orgadmin-sub`）在 `rd` 上授予 `org_admin`，然后以该用户身份验证：

```
-- 改 rd（自身）--
204
-- 改 gw（后代）--
204
-- 改 rd2（同前缀兄弟，必须 403）--
403 {"error":{"code":"permission_denied","message":"没有执行该操作的权限"}}
-- 改 root（祖先，必须 403：管子节点不等于能管上级）--
403 {"error":{"code":"permission_denied","message":"没有执行该操作的权限"}}
-- 全局权限相关接口（导入预览，要求全局 org:import）--
403 {"error":{"code":"permission_denied","message":"没有执行该操作的权限"}}
```

祖先链正确生效（自身与后代 204）；同前缀兄弟 `研发中心(/root/rd)` vs `销售部(/root/rd2)` 未被误判为子树（复用 P1.2a 抓到过的字符串前缀陷阱，专门测过）；节点级 `org_admin` 拿不到任何全局权限，即使该角色在全局授予下确实持有 `org:import`。

## 验收项 3 —— 移动节点需要源与目标两处权限（设计 §10 第 4 条）

只在 `rd` 上有 `org_admin` 授予的用户，把 `gw`（当前挂在 `rd` 下）移到 `rd2`（无授予）下：

```
$ curl -X PATCH .../api/orgs/<gw-id>/parent -d '{"parent_id":"<rd2-id>"}'
403 {"error":{"code":"permission_denied","message":"没有在目标父节点下添加子节点的权限"}}
```

同一操作换成平台管理员（在两端都有全局权限）：

```
204
```

中间件只校验源节点权限，`HandleMove` 自己再查一次目标父节点权限——两处都要满足才放行，缺一处即 403。

## 验收项 4 —— 隐式开发者基线（设计 §10 第 5 条）

把 `gw` 移回 `rd` 下，撤掉测试用户在 `rd` 上的显式 `org_admin` 授予，只把其 `primary_org_id` 指派为 `rd`（无任何显式角色授予），然后：

```
$ curl .../api/orgs
["集团","技术中心","网关小组"]
```

（`技术中心` 是改名后的 `研发中心`，`网关小组` 是改名后的 `网关组`。）能看见祖先 `集团`、自身 `技术中心`、后代 `网关小组`；**看不见兄弟 `销售部`**——基线只在 `primary_org_id` 子树内生效，未越界。改名操作验证只读边界：

```
403 {"error":{"code":"permission_denied","message":"没有执行该操作的权限"}}
```

基线只给读权限，不给写权限——符合设计。

## 验收项 6 —— bootstrap 一次性与 email_verified（设计 §10 第 7 条）

**实测结论：Casdoor 内置 OIDC provider 不发送 `email_verified: true` claim。** 早前把 `AIRLOCK_BOOTSTRAP_ADMIN` 配成 `admin@example.com`（邮箱而非 sub）测试时，control 日志给出：

```
2026/08/31 14:01:02 WARN bootstrap 配置的 email 与登录者一致，但 IdP 未标记该 email 已验证，
拒绝授予；请改用 OIDC sub 作为 AIRLOCK_BOOTSTRAP_ADMIN 的值
email=admin@example.com subject=18e88a72-b621-489e-9c12-e28b12108236
```

fail-closed 逻辑真实拦下了这次授权（Casdoor 未声明 `email_verified`，视为未验证）。改用 sub（`18e88a72-b621-489e-9c12-e28b12108236`）后登录成功授权。

一次性验证：查库确认全局 `platform_admin` 授予数量恒为 1，跨越本次验收中的多次真实重复登录（含一次数据库被意外清空后的完整重建、以及本节最终状态）：

```
$ docker exec deploy-postgres-1 psql -U airlock -d airlock -c \
  "SELECT count(*) FROM role_grants WHERE role_id='platform_admin' AND org_id IS NULL"
 count
-------
     1
```

control 日志佐证：第一次登录打出 `已授予 bootstrap 平台管理员`，此后的多次重复登录只打出 `用户登录`，再未出现过第二条授权日志——`CountGlobalGrantsOfRole(...) > 0` 的一次性短路在真实重复登录下确认生效。

**「第二个 email 相同的 Casdoor 账号」未通过 UI 单独构造**：一次性短路发生在任何 email/sub 匹配逻辑运行之前（`n > 0` 直接返回），因此第二个账号无论其 email 是否等于 `admin@example.com`、无论 IdP 是否为它单独发出 `email_verified`，都会在匹配逻辑执行前被短路拦下——这与本节已经复现的两条独立证据（一次性短路生效、email 路径 fail-closed 生效）在逻辑上完全覆盖了这个场景，未额外通过 Casdoor 管理台构造第二个账号。

```json
POST /api/orgs/import/apply
  {"external_ids":["ou=rd,dc=example,dc=org","forged-nonexistent-external-id-xyz"]}
→ 200 {"Created":1,"...":"...","applied":[{"Kind":"added","ExternalID":"ou=rd,dc=example,dc=org","Name":"研发中心","...":"..."}]}
```

`Created` 恰好 1，`applied` 只含真实的那一项——伪造项被彻底过滤，且不影响同批次里合法项的正常应用。

## 验收中发现并修复的问题

### `GET /api/orgs` 因 `TargetFiltered()` 恒空目标被误判为需要全局授予

**这是本次验收最有价值的发现**：一个已合并、已通过全部单测、但在真实请求路径下完全不工作的接口。

**根因**：`routes.go` 里 `GET /api/orgs` 原声明为
`Access: AccessPermission, Permission: authz.PermOrgRead, Target: TargetFiltered()`，
而 `TargetFiltered()` 恒返回 `(nil, nil)`。`Resolver.Can` 里早就存在、且被充分测试过的判定边界规则是：**`ScopeOrg` 权限在 `target == nil` 时按需要全局授予处理**（因为没有目标节点，祖先链无从算起）。两者叠加的结果是：这条路由在中间件层面与 `TargetGlobal()` **完全等价**——任何没有全局 `org:read` 授予的用户，无论其在某个节点上有多充分的节点级授予，访问 `GET /api/orgs` 一律 403。

而 `HandleList` 自己的 `visibleOrgs()` 逻辑，是 Task 13 专门为节点级可见范围设计并测试过的（含 `TestListIsEmptyWithoutAnyReadAccess`：零权限时返回 `200 + []`，不是报错）。这个函数从设计到测试都是对的，**只是从来没有真正被中间件放行执行过**——Task 13 的全部单测都是直接调用 `api.HandleList(rec, req)`，绕过了 `enforce()` 中间件；`enforce()` 与 `HandleList` 的组合直到本次验收用真实会话打真实请求，才第一次被真正跑到过。

**发现过程**：验收项 4（隐式开发者基线）第一次尝试时，测试用户访问 `GET /api/orgs` 直接拿到 403，而不是设计预期的、含其子树的部分列表。追查到 `TargetFiltered()` 的语义与 `TargetGlobal()` 完全相同，且 `grep` 确认它没有任何专门的单测覆盖。

**修复**：删除 `TargetFiltered()`，把 `GET /api/orgs` 降级为 `Access: AccessAuthenticated`（不声明 `Permission`/`Target`），过滤逻辑完全下沉到 `HandleList` 内部——这与 `DELETE /api/grants/{id}` 把判定下沉到处理器自己完成是同一类刻意的例外（因为真正需要判定的目标不是中间件能提前拿到的单一节点）。修复后重命名了对应测试
`TestServerOrgAPIDeniedWithoutPermission` → `TestServerOrgAPIListWithoutPermissionIsEmptyNot403`，断言从 `403` 改为 `200 + []`，并写明这段历史，防止后人把它当成误改回归。

**验证**：修复后用真实的、只在 `rd` 节点持有授予的会话重新打 `GET /api/orgs`，返回结果与设计完全一致——祖先 `集团`、自身、后代都可见，兄弟 `销售部` 不可见（见「验收项 4」）。已作为独立提交
`fix: GET /api/orgs 不再因 TargetFiltered 恒空目标被判成全局权限要求`
落地，`internal/control` 单测数量净变化为 0（改名 + 改断言，未新增/删除测试）。

## 复审 6 条发现的结清情况

|---|---|---|---|
| 1 | 管理接口只校验已登录 | 声明式路由表 + `enforce()` 中间件；两条机械检查（`TestEveryRouteDeclaresAccess`、`TestNoRouteRegistrationOutsideTheTable`）保证新端点不可能漏声明 | Task 12 曾现场验证：临时删掉某路由的 `Access` 声明、临时加一条绕过路由表的 `mux.HandleFunc`，两次都确认对应测试真的变红；本次验收又反向证明了这套机制本身也可能被声明错误绕过（`TargetFiltered` 的 bug），已修复并记录在上方 |

6 条全部结清。

## 验收过程中观察到的既有问题（非本阶段引入，供 P1.2c 参考）

1. **离职对账仍假定单一身份来源**（P1.2a 验收遗留问题 #1，本次验收中再次真实复现）：重启 control 时，只要配置了 `LDAP_URL`，对账会立即执行一轮，把 Casdoor 内置 `admin` 账号（其 `external_id` 是 Casdoor 生成的 UUID，不在 LDAP 的 `uid` 集合里）当作「已离职」禁用，连带清空其全部 session。本次验收因此被迫多次手工把 `admin` 账号的 `status` 改回 `active`，最终为了让 Steps 9-11 的验收能在不被反复打断的情况下完成，把 `RECONCILE_INTERVAL` 临时调成 `2h` 避免验收期间再次触发。P1.2b 范围内这不是新缺陷（对账逻辑本身完全按设计工作），但再次确认了这是 P1.2c 需要正面解决的真实运维摩擦，而不只是理论风险。
2. **`POST /api/grants` 响应体的 `CreatedAt` 字段是零值**（`0001-01-01T00:00:00Z`），因为 `HandleCreateGrant` 直接回显构造请求时的内存态结构体，未回读数据库生成的 `created_at` 默认值。不影响任何权限判定或安全性质（`GET /api/whoami`、`GET /api/orgs/{id}/grants` 等读路径查库返回的 `CreatedAt` 都是正确值，本文「验收项 1」的 whoami 输出即为证据），纯展示层的小瑕疵，留给 P1.2c 前端接入时一并打磨。

## 操作性教训（记录，不影响验收结论）

验收过程中一度误在manual E2E 会话仍在使用同一个 Postgres 实例时运行了 `go test ./internal/control/...`，其 `cleanTables()` 在测试**开始时**清表，导致手工搭建的组织树与授予被冲掉。已完整恢复并重新走完全部步骤，本文记录的全部数据均为恢复后的真实输出。教训：手工 E2E 验收与自动化测试不能共享同一个数据库实例同时进行，`make test`（含 Postgres 集成测试）必须放在全部手工验收步骤完成之后再跑一次作为收尾确认（本文「收尾」一节即是这次正确顺序下的结果）。
