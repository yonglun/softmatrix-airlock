# P0 结论：流式缓冲窗口对首字延迟的影响

| 项目 | 内容 |
|---|---|
| 日期 | 2026-08-27 |
| 原型 | `spike/streambuffer/main.go` |
| 模型 | `gpt-5.6-luna`（Azure AI Foundry OpenAI 兼容部署，经 LiteLLM 转发；`deepseek-chat` 当前无可用 key，未使用） |
| 原始输出 | `/tmp/streambuffer.txt` |

## 实测数据

| 缓冲窗口（字符） | 样本数 | TTFT p50 | TTFT p95 | TTFT max |
|---|---|---|---|---|
| 0（不缓冲） | 5/5 | 4.355s | 4.783s | 4.783s |
| 32 | 5/5 | 4.275s | 4.972s | 4.972s |
| 128 | 4/5（1 次因响应总长不足 128 字符而失败，实际仅攒到 70 字符） | 4.34s | 4.504s | 4.504s |
| 512 | 0/5，全部失败（5 次实际输出分别只攒到 109/238/216/262/218 字符，全部低于 512） | — | — | — |

## 结论

1. 相对不缓冲的基线（p50 = 4.355s），窗口 32 和 128 引入的额外首字延迟在测量噪声范围内（分别约 -80ms 和 -15ms，即没有统计上可辨的额外延迟）。这说明 TTFT 的主要构成不是"攒够 N 个字符"所需的流式吐字时间，而是请求发出到模型开始产出第一批 token 之前的固定开销（网络往返 + LiteLLM 路由 + Azure AI Foundry 排队/推理启动，实测约 4.3s）。一旦流开始产出内容，几十到一百多个字符会在很短时间内连续到达，所以在这个量级上加缓冲窗口，代价几乎为零。
2. 窗口 512 在本次测试中 5/5 全部失败——不是因为延迟太高，而是因为提示词"用两百字介绍一下长江"配合 `max_tokens=400` 产出的真实响应长度通常只有 100~260 个字符，从未达到 512 的门槛，流在到达 `[DONE]` 时窗口仍未攒满。这暴露了一个比"延迟"更根本的风险：**窗口不是越大代价越高，而是可能永远攒不满**，导致设计如果没有"流结束即强制吐出已缓冲内容"的兜底逻辑，短回复会在护栏后完全卡死、永不下发。因此"保持可接受体验"的窗口上限，与其说是一个延迟数字，不如说是要显著小于典型响应长度——按本次实测，128 字符是安全的（多数回复能达到或接近这个量级），512 对当前这种较短回复的场景不现实。
3. 32~128 字符大约是中文一到两句话的长度。这个粒度对单次缓冲区内的关键词/正则匹配基本够用（大多数敏感词、身份证号、简单 PII 模式长度远小于此），但对跨越窗口边界被截断的模式（例如一个敏感短语恰好被切在两次 flush 之间）会漏检——本原型的"攒够就吐"策略完全没有重叠/回看机制，是当前测法的已知盲区，需要在 P4 设计检测器时专门处理（例如保留上一窗口的尾部若干字符作为下一次检测的上下文）。

## 对 P4 的输入

- 推荐的默认缓冲窗口：32~128 字符。这个区间对 TTFT 几乎没有可辨的额外影响，同时大概率能在典型回复长度内被攒满触发正常检测流程；不建议采用类似 512 这种量级的固定窗口，本次实测中它对短回复根本触发不了缓冲判定，等同于退化成"等到流结束再判定"，还必须配合强制 flush 逻辑，否则短回复会挂起不下发。
- 需要在 P4 进一步验证的问题：
  1. 窗口边界切断敏感模式的漏检问题——需要设计重叠缓冲（sliding window / 尾部回看）而不是简单的"攒够 N 个字符清空"。
  2. 必须有"流正常结束但窗口未攒满"时的强制 flush 兜底，否则短回复会被护栏卡死（本次 512 窗口 5/5 复现了这个问题）。
  3. 本次测试的 4.3s 基线延迟本身主要来自模型侧（首 token 到达时间），与缓冲逻辑无关；需要在更接近生产网络环境、更多并发、以及使用其他模型（如 deepseek-chat 一旦有可用 key）时复测，确认结论不是 gpt-5.6-luna 或本地环境的特例。
  4. 当前样本量小（每个窗口仅 5 次），且只测了一种较短的 prompt/响应场景；需要用更长的典型生产响应（例如客服问答、代码生成等真实场景的响应长度分布）重新验证 128 字符窗口是否仍然"总能攒满"。
- 若客户对 TTFT 极度敏感，可提供的降级选项：仅对非流式请求开启出向护栏（先完整生成、一次性检测再返回），流式请求要么关闭内容检测、要么退化为"流式下发 + 流末尾对完整拼接内容做一次全量复核"（复核发现问题时通过后续机制处理，如记录告警或阻断会话，而不是拦截已下发的内容）。
