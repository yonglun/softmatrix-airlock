### 部署准备中发现并修复的问题

在起全栈之前，即发现并修复了三个 Task 22 自身及其上游代码引入、事先未被任何单测覆盖的问题（这类问题正是本任务把它们全部推迟到真实容器验收的原因）：

1. **`bitnami/openldap:2.6` 镜像已下架**——Bitnami 2025 年把非付费镜像迁到了 `bitnamilegacy` 命名空间。`docker compose up` 报 `failed to resolve reference "docker.io/bitnami/openldap:2.6": not found`。改为 `bitnamilegacy/openldap:2.6`（同一镜像、同一套环境变量接口，只是仓库路径变了）。
2. **`bootstrap.ldif` 缺根节点**——原文件第一条记录就是 `ou=rd,dc=example,dc=org`，从未定义 `dc=example,dc=org` 本身。Bitnami 镜像在设置了 `LDAP_CUSTOM_LDIF_DIR` 时会跳过默认建根逻辑，若不在自定义 LDIF 里补上根节点，加载会报 `No such object`，导致容器看起来正常启动、实际组织树是空的。已在 `bootstrap.ldif` 开头补上 `dn: dc=example,dc=org`（`objectClass: dcObject` + `organization`）。
3. **`casdoor` 数据库从未真正建出来**——`01_litellm_db.sql` 里新增的 `CREATE DATABASE casdoor;` 只在 Postgres 数据卷首次初始化时执行，而本机的 `pgdata` 卷早已存在（来自数周前的 P0/P1.1 工作），所以这条语句从未被执行过。`casdoor` 容器启动后立即 panic：`pq: database "casdoor" does not exist`。手动执行 `CREATE DATABASE casdoor;` 后 `casdoor` 正常起来。

以上三处均已直接修复并纳入 Task 22 的提交，不留占位符。

### 验收项 5 —— 重复导入不产生重复节点

对已导入完成的三个节点再次预览：

```json
{"items":null,"source":"ldap"}
```

`items` 为空（`null`，非重复导入产出的重复节点）——幂等生效。

**顺带发现的小问题**：这里返回的是 JSON `null` 而不是 `[]`，是因为 `ComputeDiff` 在无差异时返回的是从未 `append` 过的 nil slice，Go 的 `encoding/json` 会把 nil slice 编码成 `null`。写一个天真的前端 `preview.items.length` 会在这里直接抛异常（验收过程中真的复现了这个异常）。已随「JSON 标签与错误信息」那条已知问题一起记录到遗留问题里。

### 验收项 6 —— 离职对账

为让对账测试不撞上「IdP 返回空集合视为故障」的保护，先在 LDAP 里添加了 `keepuser`（保持在线），确认对账周期内 LDAP 的 `inetOrgPerson` 集合非空；随后在 Postgres 里手工插入一条模拟「已登录过」的用户记录（`external_id=testuser1`，对齐 LDAP 的 `uid=testuser1`），并为其插入一条会话和一把状态为 `active` 的 Key；再从 LDAP 删除 `uid=testuser1`；把 `RECONCILE_INTERVAL` 设为 `10s` 重启 control 触发对账：

```
2026/08/30 13:51:40 INFO 检测到 IdP 侧已离职或禁用 user_id=... email=testuser1@example.com external_id=testuser1
2026/08/30 13:51:40 WARN 离职对账完成 disabled=3 keys_revoked=1 sessions_removed=2
```

```
$ psql -c "SELECT external_id, status FROM users ORDER BY created_at"
 external_id                          | status
--------------------------------------+----------
 s1                                   | disabled
 18e88a72-b621-489e-9c12-e28b12108236 | disabled
 testuser1                            | disabled

$ psql -c "SELECT id, user_id, status FROM api_keys"
 id        | user_id                              | status
-----------+--------------------------------------+---------
 key-test1 | 11111111-1111-1111-1111-111111111111 | revoked

$ psql -c "SELECT count(*) FROM sessions"
 count
-------
 0
```

`testuser1` 的 `status` 变 `disabled`；其名下 Key 变 `revoked`；其 session 已被清除——验收项本身通过。

**一个意料之外、但很有价值的真实发现**：这一轮对账同时禁用了另外两个账号——`s1`（数据库里遗留的旧测试用户）和 `18e88a72-...`（也就是本次验收登录用的 Casdoor 内置 `admin` 账号本身）。原因是 `LDAPIdentitySource.ActiveExternalIDs` 只查询这一个 LDAP 目录的 `uid` 集合，而 `admin` 是 Casdoor 的**本地内置账号**，其 OIDC `sub`（`18e88a72-...`）是 Casdoor 生成的 UUID，根本不是任何 LDAP `uid`——对账逻辑因此把它当成「IdP 侧已离职」处理，禁用了正在测试的管理员自己的账号。这不是本次任务代码的 bug（Task 18 的单测已经完整覆盖了对账的核心安全性质：空结果中止、出错中止、禁用顺序），而是**架构层面一个真实存在的约束**：P1.2a 的离职对账假定「LDAP 是用户在线状态的唯一权威来源」，任何通过其他身份来源（Casdoor 本地账号、未来可能接入的钉钉/企微/飞书连接器）登录、但其 external_id 不在这唯一 LDAP 目录里的用户，都会在下一轮对账时被错误地当作「已离职」处理并踢下线。已记录到下方「遗留问题」，作为 P1.2b 及以后需要正面解决的设计缺口（多来源身份的对账协调），而不是留到生产环境里被真实客户撞见。

（验收后已手动把 `admin` 账号的 `status` 改回 `active`，未影响后续步骤；`s1` 保持 `disabled`，因为它本来就是历史遗留的验收残留数据，不影响任何在用功能。）

## 连接器实测边界

**钉钉 / 企业微信 / 飞书：未实测。** 本次验收只覆盖了 LDAP（openldap 容器）与 Casdoor 本地账号。
这三家的连接器配置在 Casdoor 侧，Airlock 代码不感知，但「Casdoor 文档声称支持」与
「在真实企业租户里跑通」是两件事——取得真实租户前，不在任何交付物里写「支持」。

（此纪律来自 P1.1 教训：gpt-5.6-luna 的 usage 块形状 bug 只有真实上游能暴露。）

同样地，本次也**没有**验证「Casdoor 从 LDAP 同步用户、使得 OIDC sub 与 LDAP uid 对齐」这条设计文档 §3.1 假设的路径本身——受限于本地验收环境搭建成本，直接用 Postgres 手工插入一行模拟「已登录过」的用户来测试对账逻辑本身。对账逻辑（Task 18）与 LDAP 取数逻辑（Task 20/22 的 `ActiveExternalIDs`）各自都有独立证据支持其正确性，但「Casdoor LDAP Provider 同步」这一环尚未连成一条完整链路验证过，见下方遗留问题。

## 遗留问题

1. **离职对账假定单一身份来源，多来源场景会误伤**（验收项 6 中真实复现，非假设）。`LDAPIdentitySource.ActiveExternalIDs` 只知道一个 LDAP 目录，任何 external_id 不在这个目录里的账号（本次验收里的 Casdoor 本地 `admin` 账号即是一例）都会在下一轮对账中被当作「已离职」禁用、吊销 Key、清空 session。P1.2a 范围内这是可接受的（唯一身份来源场景下行为完全正确，且已有详尽单测），但在真实企业环境里，只要存在任何一个未接入该 LDAP 对账源的登录路径（本地账号、临时授权、别的连接器），就会被误伤。P1.2b 需要正面设计「对账的身份来源应该与登录时实际使用的身份来源保持一致」，而不是硬编码单一 `IdentitySource`。
2. **`ComputeDiff` 空结果的 JSON 序列化是 `null` 而非 `[]`**（验收项 5 中复现：天真的前端 `.items.length` 直接抛异常）。已与 Task 19 复审时发现的「`DiffItem` 无 JSON tag、被迫用大写字段名」一起，作为 P1.2 前端接入前需要处理的 API 契约打磨项。
3. **导入差异引擎无法感知「仅移动、未改名」的 IdP 变更**（Task 16 复审已记录，此处不重复展开）。
4. **LDAP 通讯录源在非 OU 中间容器下会静默拍平子树**（Task 20 复审已记录，此处不重复展开）。
5. **`bootstrap.ldif` 与 `bitnami/openldap` 镜像标签在本次验收前双双失效**——已直接修复（见上方「部署准备中发现并修复的问题」），但提醒：这类"部署脚本从未真正跑过就先被记录为完成"的风险，在任何后续新增的 docker-compose 服务上都要重复防一遍，不能假设 AI 编写的 YAML/LDIF 第一次就能跑通。
