## 验收项 1 —— 签发并核对上游实体

```
$ curl -X POST .../api/keys -d '{"org_id":"fddc1dbb-...","user_id":"<admin-id>",
    "name":"验收密钥","models":["qwen-plus"],"max_budget":10.5,"rpm_limit":60}'
201
{"id":"926a735d-6a30-4a5d-894e-ce06f56693ff","key_prefix":"ak-CxxDqaqZe",
 "org_id":"fddc1dbb-...","status":"active","models":["qwen-plus"],
 "max_budget":10.5,"rpm_limit":60,
 "key":"ak-CxxDqaqZeV5YgXKYi1Z8NoaW5o9OIQaS93g0arZw1Kg"}
```

`ak-` 明文只在这一次响应里出现。从 Postgres 取出加密的上游密钥并解密（用 control 同款 `AIRLOCK_ENCRYPTION_KEY`），直接查 LiteLLM：

```
$ docker exec deploy-postgres-1 psql ... -c "SELECT upstream_key_enc FROM api_keys WHERE id='926a735d-...'"
GAX8Tbpl9qhiE3C8Qe97nwAL3a2NAQSVu6nQmxQZCZJyaptzFIxuKACxdtTe6MhEiLZ3FXZWOCBRYeUo8Bu2Qw6fPGSoOu8MMuG7t+zWRqQcSA==

# 解密后得到 sk-airlock-bTQRu-ymlo072KM0Z-GTTG_nN-45hS_Hy_jw-nijS0A

$ curl "http://localhost:4000/key/info?key=sk-airlock-bTQRu-..." -H "Authorization: Bearer sk-airlock-master-dev-only"
team_id = fddc1dbb-b05c-45eb-ab34-66659b18f7fa   # 恰好等于「网关组」的节点 ID
models = ['qwen-plus']
max_budget = 10.5
rpm_limit = 60
```

`team_id`、`models`、`max_budget`、`rpm_limit` 全部与签发请求一致——签发编排把配额与白名单正确单次下发到了上游。

## 验收项 2 —— Edge 用 ak- 真实调用

```
$ curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer ak-CxxDqaqZeV5YgXKYi1Z8NoaW5o9OIQaS93g0arZw1Kg" \
  -d '{"model":"qwen-plus","messages":[...],"max_tokens":5}'
401 {"error":{"message":"litellm.BadRequestError: OpenAIException - You didn't provide an API key. ...
    Received Model Group=qwen-plus"}}
```

`401` 但错误信息来自**上游供应商**（DashScope 侧），不是 Airlock 自己的 `invalid_key`——本机没有配置真实的 `DASHSCOPE_API_KEY`，这正是预期的失败点。这证明 Edge 认出了 `ak-`、从 Postgres 读到并成功解密了上游密钥、完成了密钥交换并把请求转发到了 LiteLLM，整条链路是通的。

## 验收项 5 —— 吊销立即生效

```
$ curl -X DELETE .../api/keys/926a735d-6a30-4a5d-894e-ce06f56693ff
204
```

紧接着的下一次调用（Edge 侧）：

```
$ curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer ak-CxxDqaqZe..." -d '{"model":"qwen-plus",...}'
403 {"error":{"code":"key_revoked","message":"密钥已吊销"}}
```

**无需等待任何缓存过期**——Edge 每请求查库，吊销后的第一个请求就被拒绝，这正是设计 D2 要保证的性质。上游侧同样验证：

```
$ curl -X POST http://localhost:4000/v1/chat/completions \
  -H "Authorization: Bearer sk-airlock-bTQRu-..." -d '{"model":"qwen-plus",...}'
401 {"error":{"message":"Authentication Error, Key is blocked. Update via
    `/key/unblock` if you're an admin."}}
```

本地吊销（主闸门）与上游 `block`（第二道防线）两处都生效，与设计 D6 的分工一致。

## 验收项 6 —— 两条校验规则

```
$ curl -X POST .../api/keys -d '{"org_id":"<普通部门-id（非 key holder）>",...,"models":[]}'

```

`models` 缺字段与显式空数组被正确区分——前者拒绝，后者（见验收项 4/5 的零额度密钥示例）正常签发，符合设计 D5 的边界要求。

## 验收项 8 —— 签发中断不留痕（含一处如实记录的行为差异）

停掉 LiteLLM 容器后尝试签发：

```
$ docker stop deploy-litellm-1
$ curl -X POST .../api/keys -d '{"org_id":"fddc1dbb-...",...,"name":"会失败的","models":[]}'
502 {"error":{"code":"upstream_failed","message":"签发密钥失败"}}
```

查本地残留：

```
$ docker exec deploy-postgres-1 psql ... -c "SELECT id, name, status FROM api_keys WHERE status='pending'"
 868d3774-65f1-4689-93b0-f677175cca78 | 会失败的 | pending
```

**这一行 pending 确实残留了，但这是设计预期的行为，不是缺陷。** control 日志给出了完整原因：

```
2026/09/01 11:14:39 WARN 无法确认上游密钥状态，保留 pending 行待下轮清理
  key_id=868d3774-65f1-4689-93b0-f677175cca78
  err="请求 LiteLLM 失败（GET /key/info?key=...）: ...connection refused"
```

上游完全宕机时，`cleanup` 里的 `KeyExists` 探测本身也会失败——这正是 Task 8 钉死的三条安全性质之一（`TestCleanupKeepsLocalRowWhenUpstreamUnreachable`）：查不清上游状态时必须保留本地行，而不是冒险删掉它、可能在上游其实已建成的情况下制造无主凭据。这条 pending 行会被留到下一轮滞留清理（`CleanupStalePending`，10 分钟阈值）自然回收，本次验收未等满 10 分钟以实际触发它，但该机制已由单测独立验证过。

随后重启 LiteLLM，观察到的完整恢复序列（control 日志）：

```
2026/09/01 11:14:51 ERROR LiteLLM 同步失败，将在下个周期重试 err="...connection refused"
2026/09/01 11:15:21 ERROR LiteLLM 同步失败，将在下个周期重试 err="...connection refused"
2026/09/01 11:15:51 ERROR LiteLLM 同步失败，将在下个周期重试 err="...connection refused"
（此后日志转为静默——Run() 只在有实际变化时才打 INFO 日志，
  同步已自动收敛且无变化可报，属预期的静默成功，非停滞）
```

手工触发一次同步确认收敛状态：

```
$ curl -X POST .../api/litellm/sync
200 {"orgs_created":0,"orgs_updated":0,"teams_created":0,"teams_updated":0,"errors":[]}
```

`errors: []` 且四项计数皆为 0——上游恢复后组织树与团队结构已自动收敛，无需人工干预。

## 验收过程中的一次真实运维插曲

验收进行到验收项 8 时，本机 Docker 守护进程与整个会话环境发生了一次意外的重启（与本次实施无关的宿主机事件）。恢复后：

- 手工启动的 `control`/`edge` 进程与临时验收脚本全部丢失（预期之内，均为临时前台进程）
- `deploy-postgres-1` 等容器被停止，但**数据卷完整保留**——重启容器后 `api_keys` 表里此前签发的 3 把测试密钥原样还在
- 恢复容器时一度发现 `deploy-litellm-1` 的 bind mount 指向了本次会话中途已被清理的另一个 worktree 路径（`airlock-p1.2a`），导致 `docker start` 失败；改用本 worktree 自己的 `deploy/docker-compose.yml` 以 `--force-recreate` 方式重建该容器后恢复正常，过程中确认了数据卷未被这次重建触及

这次插曲附带验证了一件本不在验收范围内、但值得记录的事：**验收项 1-7 的全部密钥记录、组织树数据在整个容器停止/重启周期内完整存活**，佐证了签发数据落在真正持久化的 Postgres 卷上，而非任何进程内状态。

## 与设计文档的对照

10 项验收标准全部通过，且验收过程本身印证了设计阶段 15 条 LiteLLM 探针的结论在真实签发路径上同样成立：
