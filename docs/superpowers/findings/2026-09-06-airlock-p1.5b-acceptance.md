## 1. 验收项 1：在期 + 临期横幅

用 `soon.lic` 启动 control。

**启动日志：**

```
INFO 授权已加载 customer=验收客户 license_id=AL-ACC-0001 seats=200 \
     expires_at=2026-09-27T00:00:00.000Z status=valid
```

`expires_at` 是 **09-27 零点**而不是 09-26 零点——`-expires 2026-09-26` 被签成次日零点，语义是「9 月 26 日当天仍然可用」。这正是设计 §3 那条排他上界，与 P1.5a 的 `parseRangeEnd` 同一决策。

**`GET /api/license`：**

```json
{"status":"valid","customer":"验收客户","expires_at":"2026-09-27T00:00:00Z",
 "seats":200,"seats_used":2,"days_remaining":21}
```

`days_remaining` 是 21 而不是 20：距到期还有 20.4 天，按设计的向上取整规则显示 21。**计划里写的「20 天」是我预估时算漏了取整**，实现行为是对的。

**无授予的普通成员**（`u-p15b-plain`，一条 role_grant 都没有）用同一个端点拿到了完全相同的响应——设计 §5.1 那条「不加权限门槛，红条要对所有人显示」成立。

**在期写操作正常：**

```
POST /api/orgs {"parent_id":"p15b-root","name":"在期时建的子节点"}  → 201
```

✅ 通过

## 2. 验收项 2：过期后的四件事

换成 `expired.lic` 重启。

**启动日志**（注意进程照常启动，过期不是启动失败）：

```
INFO 授权已加载 customer=验收客户 license_id=AL-ACC-0003 seats=200 \
     expires_at=2026-09-05T15:10:59.712+08:00 status=expired
```

### 2.1 横幅变红条

`GET /api/license` → `{"status":"expired",...,"days_remaining":-1}`

浏览器实测（截图确认）红条文案：

> 授权已于 2026-09-05 到期，管理操作已暂停；查询与吊销不受影响，**AI 调用不受影响**。

最后半句是刻意写的——不写的话运维第一反应是拔电源。

### 2.2 写操作被拦

```
POST /api/orgs → 402
{"error":{"code":"license_expired","message":"授权已过期，该操作已暂停"}}
```

### 2.3 吊销仍然放行

```
DELETE /api/keys/k-p15b-victim → 204
```

而且不只是「没被拦」——查库确认密钥真的被吊销了：

```
 k-p15b-victim | revoked
```

设计 §3 那条止损豁免端到端成立。

### 2.4 数据面不受影响

**结构性证明**（比单次请求更强——它说明 Edge *不可能*受任何 license 状态影响）：

```
$ go list -deps ./internal/edge/... | grep -c license
0
$ grep -c "license\|License" internal/app/edge.go internal/edge/*.go
（全部为 0）
```

**真实流量验证**：起 Edge 时**故意**把 `AIRLOCK_LICENSE_FILE` 也指向那份过期 license。Edge 启动日志里对它只字未提（读都没读），随后用一把真实的 Airlock 密钥打了一次 `/v1/chat/completions`：

```
HTTP 401
{"error":{"message":"litellm.AuthenticationError: AuthenticationError:
 DeepseekException - Authentication Fails ..."}}
```

**这个 401 来自 DeepSeek 上游**，经 LiteLLM、经 Edge 转回。也就是说请求穿过了整条数据面：Edge 认下了 Airlock 密钥、转发给了 LiteLLM、LiteLLM 调了 DeepSeek。失败原因是这台开发机的 `DEEPSEEK_API_KEY` 为空——**已知环境限制，不是缺陷，更不是 license 拦截**（若 Edge 被 license 管住，请求根本到不了 DeepSeek）。这与 P1.5a 记录的上游凭据缺失是同一件事。

✅ 四项全部通过

## 4. 验收项 4：试用模式与席位闸

不设 `AIRLOCK_LICENSE_FILE` 启动。

```
WARN 未配置 AIRLOCK_LICENSE_FILE，以试用模式运行 seats=5
```

`GET /api/license` → `{"status":"trial","seats":5,"seats_used":2}`——没有 `expires_at`、没有 `days_remaining`，与设计一致（试用不设到期）。

补了三个填位用户把席位占满：`{"status":"trial","seats":5,"seats_used":5}`。

**席位闸走的是真实 OIDC 登录**，不是模拟。Casdoor 里只有内置的 `admin`（`admin@example.com`），而它在 Airlock 侧还没建档——正好就是席位闸要拦的「新人」。用浏览器完整走了一遍 Casdoor 登录：

```
回调地址 localhost:8081/auth/callback?code=e04645e8...&state=HKgHOfTx...
响应：{"error":{"code":"seats_exhausted",
       "message":"席位已满（5/5）；请联系管理员停用离职成员以腾出席位"}}
```

这一条是单元测试无法覆盖的部分——它证明的是 **`RunControl` 真的把 gate 装进了 `AuthDeps`**（若没装，`AdmitNewUser` 在 nil 接收者上会放行，登录就成功了）。

被拒的人**没有留下任何用户记录**：

```
SELECT count(*) FROM users WHERE email='admin@example.com';  →  0
SELECT count(*) FROM users WHERE status='active';            →  5
```

这一点很重要：留了记录的话，第二次登录就会走「已建档」分支溜进来。

✅ 通过

## 5. 验收项 5：停用腾出席位

```
UPDATE users SET status='disabled' WHERE id='u-p15b-f3';
GET /api/license → {"status":"trial","seats":5,"seats_used":4}
```

同一个 Casdoor 账号再登一次——**成功进入控制台**，并且建档了：

```
 18e88a72-b621-489e-9c12-e28b12108236 | admin@example.com | active
 活跃用户数：5
```

控制台横幅同时显示（截图确认）：

> 未配置授权文件，当前为试用模式（上限 5 席位）。席位已满，新成员将无法登录；停用离职成员可腾出席位。

后半句正是刚才那位管理员需要的操作说明——把解法写在问题旁边这条设计意图落地了。

✅ 通过

## 7. 与计划的偏离

1. **`web/src/lib/api.ts` 没改。** 设计 §5.3 说给 402 加专门映射。读过 `api.ts:44-52` 后确认没必要：`handle()` 已经把后端 `error.message` 原样抛出，而后端给 402 的消息就是「授权已过期，该操作已暂停」这句中文。再加一层前端映射只会让同一句话有两个来源、日后漂移。计划的文件结构一节已记下这条偏离。

2. **验收项 1 的 `days_remaining` 是 21 不是 20。** 向上取整的结果，实现正确，是计划里的预估写漏了。

3. **`.gitignore` 多加了一条 `/licensegen`。** `go build ./cmd/licensegen` 会在仓库根留下二进制；仓库里已有 `/streambuffer` 这个先例，照同样写法处理。

## 8. 记下来的环境事实（非本阶段缺陷）

- **`POST /api/keys` 在本机签发失败，502 `upstream_failed`。** 处理器把底层错误映射成 502 时**没有记日志**（`keyapi.go:94` 的 `writeKeyError`），所以看不到真实原因。这是既有的可观测性缺口，与 P1.5b 的改动无关；验收改用直接造密钥行的方式绕开了它。值得单开一个小任务给签发失败补上 `slog.Error`。
- 开发机的 `DEEPSEEK_API_KEY` / `DASHSCOPE_API_KEY` 均为空，任何真实模型调用都会拿到上游 401。
