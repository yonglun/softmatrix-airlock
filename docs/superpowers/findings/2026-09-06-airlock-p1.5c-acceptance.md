## 2. 发现并修复的真实缺陷

### 2.1 打包脚本把第三方镜像静默拉成了错误架构

**现象**：第一次打出 amd64 包后，没有直接信任 `docker image inspect`（这台构建机同时缓存过 arm64 与 amd64 两份），改成直接读 `images.tar` 里每个镜像的 config JSON——发现四个第三方镜像（postgres/clickhouse/litellm/casdoor）全部是 **arm64**，只有 airlock 自己是对的 amd64。

**根因**：manifest-list digest 在所有架构下完全一致（这正是"按它钉死可跨架构复用"的设计初衷）。当本机已经用另一种架构拉过同一个 `name:tag@digest` 引用时，`docker pull --platform` 会认为"本地已经满足这个引用"而不真正替换内容——且不报任何错误。

**修复**：`build-release.sh` 改成先用 `docker buildx imagetools inspect --raw` 解析出目标架构**专属**的 manifest digest（不是清单列表 digest，这个值本身带架构信息，不会有歧义），用它去 pull，拉完立刻用 `docker image inspect --format '{{.Architecture}}'` 硬校验，不对就整个流程失败。校验通过后打回本地 tag 供 `docker save` 使用。

**重新验证**：重建两个包，直接读 `images.tar` 内容确认五个镜像（airlock + 4 个第三方）在 amd64 包里全部是 `amd64`，在 arm64 包里全部是 `arm64`。

### 2.2 install.sh 必填项校验的正则表达式坑

**现象**：填好 `DEEPSEEK_API_KEY=verify-only-placeholder` 后重跑安装脚本，仍然报"至少一个模型供应商密钥"没填，卡在第 3 步出不去。

**根因**：`grep -qE '^(DEEPSEEK|DASHSCOPE|OPENAI)_API_KEY=.\+'`——ERE 模式（`-E`）下 `\+` 是**字面量加号**，不是"一个或多个"（那是 BRE 模式下 GNU 的扩展写法）。`verify-only-placeholder` 不含字面 `+`，永远匹配不上。前两条校验（`AIRLOCK_BOOTSTRAP_ADMIN`、`OIDC_CLIENT_SECRET`）没写 `-E`，恰好用对了 BRE 语义，侥幸没暴露。

**修复**：统一改成标准 ERE 的 `.+`（不转义），三条校验写法一致。

### 2.3 建库时机与起栈顺序颠倒，Casdoor 无法启动

**现象**：修完前两个问题后重跑，`airlock-control` 依赖的 `casdoor` 一直不健康，日志是无限重启。查 `casdoor` 自己的日志：`panic: pq: database "casdoor" does not exist`。

**根因**：原设计是"起全部容器 → 最后才建 litellm/casdoor 的数据库"。Casdoor 连接时如果目标数据库不存在会直接 panic 退出（不会像 LiteLLM/Prisma 那样自己把库建出来），根本撑不到"最后一步"建库的时候。

**修复**：把 `install.sh` 的第 4 步拆成两段——先只起 `postgres`/`clickhouse` 并等健康，创建 litellm/casdoor 数据库，再起其余服务。ClickHouse 的用量表不影响任何容器能否启动，继续留在第 5 步。用户可见的仍然是五步，只是第 4 步内部多了一段。

### 2.4 OIDC issuer 与 discovery 地址的根本冲突（本次最大的一个）

这个问题分两轮才修对，记录完整过程：

**第一轮（错误方向）**：修完 2.3 后重跑，`airlock-control` 报 `OIDC discovery 失败: connect: connection refused`。原因是 `.env.example` 把 `OIDC_ISSUER` 设成了浏览器地址（`http://localhost:...`），而 `airlock-control` 是在容器里发起这次请求，容器自己的 `localhost` 只是它自己，根本连不到 Casdoor。**当时的修法**：把 `OIDC_ISSUER` 改成 compose 内部服务名 `http://casdoor:8000`。

**第二轮（发现第一轮修错了）**：重新打包重装，这次报了一个新错误：`oidc: issuer URL provided to client ("http://casdoor:8000") did not match the issuer URL returned by provider ("http://localhost:18000")`。直接 `curl` 了一下开发环境 Casdoor 的真实 discovery 文档，确认 `issuer`/`authorization_endpoint`/`token_endpoint` 全部跟着它自己的 `origin` 配置走——而 `origin` 就是 `CASDOOR_ORIGIN`（浏览器地址）。

这揭示了一个结构性冲突：**go-oidc 强制要求 discovery 响应里的 issuer 字段与请求 URL 完全一致**（OIDC 规范要求），而 Casdoor 自报的 issuer 只能是浏览器地址；`airlock-control` 发起 discovery/token 交换/取 JWKS 这三次服务端调用又只能走内部网络。两个地址不可能是同一个字符串，规范的强匹配没有绕过的余地——第一轮把 `OIDC_ISSUER` 改成内部地址，只是把"连不上"换成了"issuer 对不上"，问题从没解决过。

**真正的修复**：查到 go-oidc 库自己就为这类场景（文档原话："off-spec providers such as Azure"）提供了 `InsecureIssuerURLContext`。给 `OIDCConfig` 加一个可选的 `DiscoveryURL` 字段（留空时行为与之前完全一致，开发环境零改动）：
- discovery 走 `DiscoveryURL`（内部地址），用 `InsecureIssuerURLContext` 告诉库按 `Issuer`（外部地址）校验
- `authorization_endpoint`（浏览器重定向目标）保持 provider 自报的原样不动
- `token_endpoint` 与 `jwks_uri`（服务端自己发起的调用）手工改写成走 `DiscoveryURL` 那一侧——这两个同样跟着 `Issuer` 的 origin 走，只解决 discovery 一处的话，`Exchange()` 与 ID token 验签会接着炸（这是我在写单元测试时才发现的第三层坑，一开始只顾了 discovery 和 token，漏了 JWKS，测试跑起来直接报 `dial tcp: lookup casdoor-public.example.com: no such host`）

写了两个新单元测试锁住这个行为：`TestNewOIDCClientRejectsIssuerMismatchWithoutDiscoveryURL`（不给 `DiscoveryURL` 时该拒绝的必须还拒绝）与 `TestNewOIDCClientAllowsDiscoveryURLDifferentFromIssuer`（给了之后，discovery、AuthURL、Exchange、JWKS 验签全部要通过）。

生产配置相应调整：`OIDC_ISSUER` 改回等于 `CASDOOR_ORIGIN`（浏览器地址），新增 `OIDC_DISCOVERY_URL=http://casdoor:8000`（compose 内部地址，客户不用改，模板里已经填好默认值）。

**重新验证**：完整重新打包、重装，五步全部走完，`airlock-control` 与 `airlock-edge` 都是 healthy。另外用真实浏览器登录了一次开发环境的 Casdoor 管理界面，确认它的 discovery 文档结构与我在单元测试里模拟的完全一致（这也是我判断"单元测试已经足够、不需要走完整浏览器 OAuth 流程"的依据——真实容器已经证明能对真实 Casdoor 完成 discovery 并通过健康检查，这本身就是服务端路径工作的证据）。

## 3. 验收环境事故：docker compose 项目名冲突（如实记录）

为了给验收腾出 8080/8081/8000 端口，跑了 `docker compose -p deploy stop`。这台机器上 **"deploy" 这个 compose 项目名字不止被 Airlock 开发栈用**——命令输出显示它还停掉了一批与 Airlock 完全无关的容器（minio、keycloak、opensearch、samba、nfs、search-service、model-gateway、portal、connector-service 等），这些在此前的任何 `docker ps` 里都没出现过，说明它们属于这台共享机器上的其他项目，只是恰好共用了这个项目名。

**处理过程**：
1. 立刻用 `docker compose -p deploy start` 尝试整体恢复，触发了一次端口竞争：`deploy-minio-1` 抢到了 9000 端口，导致 Airlock 自己的 `deploy-clickhouse-1` 启动失败。
2. `deploy-litellm-1` 恢复时报错——它的 bind mount 源指向一个早已被清理的旧 worktree（`airlock-p1.3a`）路径，说明这个容器从 P1.3a 就一直没重建过。用当前 worktree 的 compose 文件重新 `up -d litellm` 修复，但这一步**误用了空的环境变量**（没传 `--env-file .env`），意外把 `deploy-postgres-1` 用空口令重建了一次。
3. 立刻发现并用正确的口令（`airlock`/`airlock_dev`，来自 `.env.example` 的既有开发默认值）重新生成 `.env`、正确地 `docker compose up -d` 恢复整个开发栈。事后确认 Postgres 数据卷完整无损（`organizations`/`users` 两张表当时是空的——但这是 Task 12 Step 1 一开始跑 `go test ./internal/control/...` 的 `cleanTables()` 清空的，发生在这次事故**之前**，与事故本身无关）。
4. `deploy-clickhouse-1` 与 `deploy-minio-1` 的端口 9000 冲突是**这台共享机器上早就存在的结构性问题**（谁先启动谁占用），不是这次改动引入的。事后没有反复切换尝试"两个都要"，而是保留 Airlock 自己的服务（ClickHouse）持有该端口，`minio` 保持停止状态。

**最终状态**：Airlock 自己的六个开发服务全部恢复健康（`postgres`/`clickhouse`/`litellm`/`casdoor`/`openldap`/`mailpit`）。`deploy-minio-1` 因端口冲突保持停止；`deploy-connector-service-1`、`deploy-portal-1`、`deploy-search-service-1`、`deploy-nfs-seed-1`、`deploy-smb-seed-1`、`deploy-createbuckets-1` 这几个不属于 Airlock 的容器，有的本来就是一次性任务、有的在恢复过程中未能完全干净地重启——它们不属于本项目范畴，没有进一步处理。

这件事的教训：**这台开发机上的 `deploy` compose 项目名被多个不相关的项目共用**，日后任何需要 `docker compose -p deploy` 之类项目级操作的场景都要先确认清楚实际影响范围，不能假设项目名与目录一一对应。

## 5. 验收局限（如实说明，不含糊）

构建机是 arm64，**amd64 交付包无法在本机端到端运行**（容器起不来）。验收因此拆成两半：安装流程在 arm64 包上验证，架构正确性在 amd64 包上通过直接读取 `images.tar` 内容验证（没有用 `docker image inspect` 走本机 daemon——本机同时缓存过两种架构，会有歧义，这正是 2.1 那个 bug 的教训）。

**没有任何一步在真实的 x86_64 无外网机器上跑过。** 真正的 x86 首装仍然是首个客户现场的风险点。

**没有走完整的浏览器 OAuth 授权码流程**（点击登录 → Casdoor 认证 → 回调 → 建会话）。已验证的是：真实 `airlock-control` 容器针对真实 Casdoor 完成 discovery 并通过健康检查，加上单元测试完整覆盖了 discovery/AuthURL/Exchange/JWKS 四个环节的地址分离逻辑。这是有意的取舍，不是遗漏——权衡了验证深度与本次验收已经消耗的时间。

**未验证真实模型调用**：`DEEPSEEK_API_KEY` 用的是占位值（`verify-only-placeholder`），验证的是安装流程本身，不是与真实供应商的连通性。

## 6. 与计划的偏离

1. **`internal/control/oidc.go` 有代码改动**，超出了 P1.5c "只做打包"的原计划范围。这是验收中发现的真实缺陷（§2.4），且找到了 go-oidc 库官方支持的解决方式，判断为必须在本阶段修，不能留给下一阶段——否则整个交付包对"provider 与消费者同在一套 compose 里跑"这个最基本的场景就是打不通的。

2. **`deploy/release/docker-compose.yml` 的镜像引用从"钉 digest"改成了"只写 tag"**，与设计文档 §3.1 的原设计相反。这是走真实安装流程时发现的：生产环境完全离线、`pull_policy: never`，Docker 运行时根本不会用 digest 去校验什么，钉在 compose 里没有任何效果；而 `docker save`/`load` 之间 `RepoDigests` 的保真程度因 Docker 版本与存储驱动而异（不同于 `RepoTags`，后者才是从不含糊的保证）,钉 digest 反而可能在客户机器上解析不到本地镜像。"钉死到实测跑通的那一份"这个目标改为在打包阶段（`build-release.sh`）强制执行，`VERSION` 文件里仍然完整记录每个镜像的 digest 供审计。

3. **`install.sh` 的"起栈"步骤从一步拆成了两段**（先起数据存储、建库，再起其余服务），与设计文档 §4.2 的描述略有出入。用户可见的仍然是五步。
