## 验收项 1：节点列表与子树列表

在 `p14b-rd` 与 `p14b-rd2` 下各签一把密钥后：

```
$ curl -sS "http://localhost:8081/api/orgs/p14b-rd/keys" -H "Cookie: ..."
1 [('RD密钥A', 'p14b-rd')]

$ curl -sS "http://localhost:8081/api/orgs/p14b-root/keys?subtree=true" -H "Cookie: ..."
2 [('RD2密钥B', 'p14b-rd2'), ('RD密钥A', 'p14b-rd')]

$ curl -sS "http://localhost:8081/api/orgs/p14b-rd/keys?subtree=true" -H "Cookie: ..."
1 [('RD密钥A', 'p14b-rd')]
```

第三条顺带就是同前缀兄弟节点的隔离证据：`p14b-rd` 的子树查询没有把 `p14b-rd2` 的密钥卷进来。

界面上选中 `P14b根`、打开「包含子树」开关：


关掉开关时该节点自身没有密钥，列表显示「该范围下没有密钥」——与 API 的单节点查询一致。

## 验收项 5：子树吊销的预览与实际命中一致（第五次陷阱）

此刻 `p14b-rd` 下有一把 `active`（界面签发密钥C）与一把 `revoked`（RD密钥A），同前缀兄弟 `p14b-rd2` 下有一把 `active`（RD2密钥B）。

选中 `P14b-RD`，点「吊销该子树的全部密钥」，先弹出「先看一眼影响范围」，确认后进入预览：

```
title: "吊销「P14b-RD」子树下的全部密钥"
paragraphs: [
  "将吊销其中 1 把（可用与签发中的）。不可逆，使用它们的客户端会立刻失效。",
  "下面是这一刻的快照。确认之间若有新密钥签发，实际条数可能不同——以吊销后的提示为准。"
]
previewRows: ["界面签发密钥C ak-IWlwB5K42 p14b-rd 可用",
              "RD密钥A ak-yCaEWP5hL p14b-rd 已吊销"]
```

三点都对上了：列出子树下**全部状态**（含已吊销的历史，管理员要看得见）、「将吊销其中 **1** 把」只数 `active`/`pending`（与后端 `RevokeByOrgSubtree` 的 `WHERE status IN ('active','pending')` 对齐）、**`p14b-rd2` 的 `RD2密钥B` 一行都没有出现**。

点「确认吊销」后：

```
notices:      ["已吊销 1 把密钥"]           ← 与预览算出的 N 一致
rd:           [["界面签发密钥C","revoked"], ["RD密钥A","revoked"]]
rd2_sibling:  [["RD2密钥B","active"]]        ← 同前缀兄弟节点毫发无伤
```

**这是本项目第五次专门测试「同前缀兄弟节点」陷阱**（P1.2b 权限判定、P1.3b 审批人查找、P1.3c 子树吊销、P1.4a 待审列表各一次）。这次的特殊之处在于：预览与开火共用逐字相同的节点选择子句（`path = $1 OR path LIKE $1 || '/%'`），所以「预览里没有兄弟节点」与「吊销没打到兄弟节点」是同一件事的两面，而不是两处各自正确的巧合。

## 验收项 7：无 `key:revoke_all` 的账号看不到危险区，且直接打接口 403

把浏览器账号的授予从全局 `platform_admin` 临时换成 `p14b-root` 上的 `org_admin`（这样界面检查用的就是一个真实的 org_admin 会话），刷新虚拟密钥页：

```
global_permissions:  []
workbenches:         ["my-space", "platform", "finops"]
dangerZonePresent:   false
pageUsable_rows:     ["RD2密钥B ak-cizo6Maix u-p14b-dev p14b-rd2 可用 qwen-plus — 轮换 吊销"]
```

**页面完全可用**（进得了平台管理、看得到树与密钥列表），但**危险操作区块不出现**。

随后用同为 org_admin 的 `u-p14b-orgadmin` 绕开界面直接打接口，且**带上完全正确的确认串**：

```
$ curl -sS -X POST http://localhost:8081/api/keys/revoke-all \
    -H "Cookie: airlock_session=<orgadmin token>" \
    -d '{"confirm":"REVOKE ALL KEYS"}'
{"error":{"code":"permission_denied","message":"没有执行该操作的权限"}}
HTTP=403
```

**隐藏入口不是授权**：确认串对了也过不去，真正的闸在路由中间件的 `Permission: key:revoke_all, Target: 全局` 上。这也正面印证了设计文档 D5——`key:revoke_all` 是 `ScopeGlobal` 权限，用 `global_permissions` 判定界面可见性是准确的，且它只是便利、不承担安全责任。

## 验收项 8：我的密钥只见本人

给 `u-p14b-dev` 在两个节点下都签了密钥，另给 `u-p14b-admin` 签一把：

```
$ curl -sS http://localhost:8081/api/keys/mine -H "Cookie: <dev token>"
5 [('RD2密钥B','p14b-rd2','u-p14b-dev'), ('RD密钥A','p14b-rd','u-p14b-dev'),
   ('dev在RD2的密钥','p14b-rd2','u-p14b-dev'), ('dev在RD的密钥','p14b-rd','u-p14b-dev'),
   ('界面签发密钥C','p14b-rd','u-p14b-dev')]

$ curl -sS http://localhost:8081/api/keys/mine -H "Cookie: <admin token>"
1 [('admin自己的密钥', 'u-p14b-admin')]
```

dev 的五把跨 `p14b-rd` 与 `p14b-rd2` 两个节点全都在；admin 的视角里**没有 dev 的任何一把**。

界面部分（给浏览器账号单独签了一把挂在 `p14b-rd2` 下）：

```
rows: ["浏览器账号的密钥 ak-5MkgaeFeX P14b-RD2（同前缀兄弟节点） 可用 qwen-plus — 轮换 吊销"]
```

「所属节点」列显示的是节点**名称**而非原始 ID，客户端 join `/api/orgs` 生效。名下无密钥时显示「你名下还没有密钥」。

## 验收项 9：责任人自助吊销

`u-p14b-dev` **一条授予都没有**。用他的会话：

```
$ curl -sS -X DELETE http://localhost:8081/api/keys/<dev 自己的密钥> -H "Cookie: <dev token>"
HTTP=204

$ curl -sS -X DELETE http://localhost:8081/api/keys/<admin 名下的密钥> -H "Cookie: <dev token>"
{"error":{"code":"permission_denied","message":"没有吊销该密钥的权限"}}
HTTP=403

$ 复核状态
[('dev在RD的密钥', 'revoked')]      ← 自己的，吊掉了
[('admin自己的密钥', 'active')]      ← 别人的，动不了
```

**两条一起才构成证据**：owner 分支放开的恰好只有「自己的」，一寸不多。这条修复的是设计文档 §2 C2+C3 揭出的缺口——`Rotate` 的 `window == 0` 会变成默认 24 小时、`window < 0` 直接报错，API 根本表达不了「立刻废掉旧凭据」，所以在补上自助吊销之前，泄露了密钥的开发者没有任何自助止血路径。

## 验收项 6：全局紧急吊销（按纪律排在最后）

界面上的确认串闸门：

```
emptyDisabled:     true    ← 空
lowercaseDisabled: true    ← 打成 "revoke all keys"（小写）
exactDisabled:     false   ← 原样打出 "REVOKE ALL KEYS"
```

后端那道闸独立成立（有权限的账号，确认串写错）：

```
$ curl -sS -X POST http://localhost:8081/api/keys/revoke-all -H "Cookie: <admin token>" -d '{"confirm":"nope"}'
{"error":{"code":"confirm_required","message":"紧急全局吊销不可逆，请在请求体中带上 {\"confirm\":\"REVOKE ALL KEYS\"}"}}
HTTP=400
```

吊销前的状态分布：

```
 status  | count
---------+-------
 active  |     7
 revoked |     3
```

在页面上原样输入确认串并点按钮：

```
notices: ["已紧急吊销 7 把密钥"]      ← 与吊销前的 active=7 一致
inputClearedAfter: ""                 ← 输入框已清空，不会误触第二次
```

吊销后：

```
 status  | count
---------+-------
 revoked |    10
```

全系统再无任何 `active` 或 `pending`。

## 过程中发现的问题及处置

1. **验收项 7 的账号在计划撰写期就被换掉了**。初稿打算用「一条授予都没有的 dev」验证「看不到危险区」，写计划时发现这毫无意义——那种账号连平台管理工作台都进不去（`workbenches = ['my-space']`），看不到危险区证明不了任何事。改为专门造一个 `org_admin` 账号：他能正常用整个虚拟密钥页，只是没有 `key:revoke_all`。这才是真实场景里「该被挡住的人」。
2. **浏览器自动化的坐标点击依旧不可靠**（与 P1.4a 验收同一结论）。`computer` 工具的 `left_click` 多次点到错误元素，antd 的 `Modal`/`Popconfirm` 弹层在截图里也偶尔渲染不出（但 DOM 状态是对的）。全程改用 `javascript_tool` 直接操作 DOM（`element.click()`、用原生 setter 触发 React 受控 input 的 `onChange`），准确可靠。这是验收环境的工具限制，不是被验收系统的问题。
3. **取「一次性明文」时选择器撞车**。用 `.ant-typography code` 取轮换后的明文，结果取到了危险区里作为示例展示的 `REVOKE ALL KEYS`（那也是个 `<code>`）。改用 `.ant-modal-content code` 限定在弹窗内后正确。纯属验收脚本的问题，页面本身没有缺陷。
4. **没有发现被验收系统的功能缺陷**。与 P1.4a 不同（那次在验收中发现并修复了深链路由缺陷），本期 10 项一次通过，未产生修复提交。

## 与设计文档的对照

| 设计决策 | 验收证据 |
|---|---|
| D1 预览与开火共用同一套节点选择子句 | 验收项 5：预览的 N=1 与实际「已吊销 1 把」一致，兄弟节点两处都没被卷入 |
| D1 预览是快照不是锁 | 弹窗里如实写明「确认之间若有新密钥签发，实际条数可能不同——以吊销后的提示为准」 |
| D2 责任人自助吊销 | 验收项 9：自己的 204、别人的 403 |
| D3 `keyView` 暴露轮换状态 | 验收项 3：列表显示「旧凭据 2026/9/3 17:10:56 前仍可用」 |
| D4 与后端两道闸对齐 | 验收项 5（预览）、验收项 6（空/小写禁用，原样才启用；后端 400） |
| D5 危险区用 `global_permissions` 判定 | 验收项 7：org_admin 看不到区块，且带对确认串直接打接口仍 403 |
| D6 抽共享组件 | `OrgTree` 被组织页与虚拟密钥页共用；`PlaintextKeyModal` 被申请页、签发、轮换三处共用 |
